# 会话存算分离：让容器变成「可丢的缓存」

本篇是「会话正文出容器」这条改造的实施记录。做完这一条，「销毁容器」才从「删数据」变成「清缓存」，
L3（stop/down 分档）、L4（自动重建）才有意义。

## 一、问题

会话日志在 `dsh-home` 卷里，是**唯一副本**。所以平台不敢真删容器：
`pvc.yaml` 两个卷都带 `helm.sh/resource-policy: keep`，归档是唯一走 `down -v` 的动作，
而且还得先 `tar` 打包。改造目标只有一句：**对象层是副本，卷是缓存。**

## 二、不走「写一个 persistence 后端」

`dsh-session-persistence-jsonl` 是唯一的第一方 provider。换实现要完整复刻
handle / append / fsync / 格式迁移 / 撕裂尾部恢复的语义，而且会随 dsh 升级失配。

改成**旁路读取 + 增量上推**：dsh 一行不改，本地文件仍是它的事实来源；
容器丢了就按对象层重建出同样的文件，dsh 起来自然看见历史。

## 三、数据模型

两张表，都是会话数据的（不是市场那套）。

| 表 | 定位 | 一行是什么 | 关键字段 |
|---|---|---|---|
| `team_sessions` | 会话索引表 | 团队里的一个会话 | `id`（目录名，即 dsh 转义后的 session id）、`log_path`（卷内相对路径）、`generation`（`session.vN` 的 N）、`log_bytes`、`digest`（清单摘要）、`last_active_at`、`missing_at` |
| `session_sync` | 会话同步进度表 | 一个会话推到了第几个字节 | `uploaded_bytes`、`segment_count`、`synced_at`、`status`、`error` |

三个设计决定：

- **`id` 用目录名而不是原始 session id**。dsh 对 id 做了单段注射式转义（实测形如
  `session-597da409-7120-4a95-a97b-6affdcb9a56d`），反解规则未公开；用目录名当主键，
  恢复时原样写回去就不会错。
- **`digest` 是清单摘要**，等于「各分段 sha256 按顺序再取一次 sha256」。不读日志内容
  就能判断清单有没有变，也不需要为算整文件摘要而全量读一遍。
- **`missing_at` 而不是删行**。卷里没了不代表数据没了（内容在对象层），
  行删了下次就不知道该恢复什么。

## 四、分段：为什么是「区间对象」

```
sessions/<team>/<sessionId>/<offset 12位>-<bytes>-<sha256>
```

日志是 append-only 的（persistence README 与实测都确认），**已上传的字节前缀永不改变**，
所以增量天然就是 `[uploaded_bytes, size)`。

| 方案 | 代价 |
|---|---|
| 整文件每次覆盖 | 20 MB 的会话聊 50 轮 = GB 级重传 |
| **区间对象（采用）** | 只在内容真变了的地方产生新对象，天然幂等 |

`offset` 写进键里而不是靠顺序：恢复时按 offset 排序并**校验连续性**，
少一段会立刻报「分段不连续」，而不是拼出一个错位的文件让 dsh 去猜。

## 五、增量算法

```
syncSession(entry)
  ① 收缩自愈：删掉 offset+bytes > 文件大小的分段
     游标 = 最后一段的末尾（对象层里有什么才是事实，不信 session_sync 里的数字）
  ② 增量上传：delta = 文件大小 - 游标
     delta ≥ 阈值 或 强制 或 会话闲置 → 读 [游标, 大小) → 存成新分段
     否则先攒着（否则每次 append 几十字节就多一个对象）
  ③ 回写：team_sessions 的字节数与清单摘要、session_sync 的游标
```

**① 是必须的**：dsh 崩溃恢复会「截掉撕裂的尾部再重写」，文件变小是正常路径，
不是异常。不处理就会留下一个越过文件末尾的分段，恢复时拼出来的文件多一段垃圾。

阈值默认 256 KiB（`CONSOLE_SEGMENT_BYTES`）。**只有阈值是不够的**：
一个只聊了几轮、尾巴一直小于阈值的会话将永远不上传，卷丢了就少最后一段。
所以还有一条闲置兜底：会话超过 10 分钟没写（`CONSOLE_SESSION_IDLE_FORCE_MS`）就强制传尾巴。

## 六、三条触发路径

| 时机 | 动作 | 为什么就在这里 |
|---|---|---|
| **睡前**（`sleepTeam`） | 强制同步 | 睡着的容器 CPU/IO 归零，下次访问可能是几天后；期间容器被重建，没推的尾巴就永久没了 |
| **周期扫描**（默认 5 分钟） | 增量同步 | 只有容器存在的团队才处理：容器不存在时卷可能也没了，起个容器去读会把卷凭空建出来 |
| **唤醒前**（`wakeTeam`） | 补齐缺失会话 | 顺序反了就是「dsh 先扫一个空的 `sessions/`，侧栏全空」——用户看到的是历史丢了 |

唤醒前那条还有两个细节：

- **只在卷已存在时做**。卷不存在意味着这是新建或归档过，会走 provision/restore 那条路；
  这里凭空 `-v` 一个卷会把它建成 root 所有，之后 dsh 用户写不进去，
  症状是「起得来但一聊就报持久化失败」。
- **补不回来也要让它起来**。宁可这次少几个历史，也别整个团队进不去。

## 七、卷 IO 抽象

sessions 模块不直接写 docker，而是依赖一个三方法接口：`list()` / `read(rel, from, to)` / `write(rel, buf)`。

| 实现 | 用途 |
|---|---|
| `createVolumeIo({team})` | 生产：容器在跑用 `docker exec`；停着用 `--volumes-from`；容器没了按卷名 `-v` 挂回 |
| `createLocalIo(dir)` | 校验脚本：让「增量/收缩/恢复」这些逻辑在没有 docker 的机器上被反复验证 |

三条 docker 路径**都挂在 `/home/dsh/.dsh`**，所以调用方拿到的路径永远是同一套，
不需要为「容器在不在」分叉。

### 两个踩过的坑

**① 起辅助容器必须 `--entrypoint sh`。**
镜像的 ENTRYPOINT 是 `tini -- entrypoint.sh`。直接 `docker run <image> sh -c '...'`
会把 `sh -c ...` 当成 entrypoint 的**参数**，结果是又拉起一个 dsh 服务端并永久挂着。
症状是备份/恢复卡住不返回，而且 `docker ps` 里多出一堆随机名字的容器
（这次排查时清掉了 8 个，其中两个已经跑了两天）。

**② 必须带 `-i`。**
`docker exec` / `docker run` 不带 `-i` 时 stdin 是关的，`cat > 文件` 会「成功」但写出 **0 字节**，
退出码还是 0。所以写完还要 `stat -c %s` 一次并比对字节数——只信退出码会得到一个
dsh 只会说「解不开」的空会话文件。

## 八、验证

**单测** `make verify-sessions`（37 条断言，临时卷 + 临时对象库 + 临时库，不需要 docker）：

| 组 | 验什么 |
|---|---|
| 清单解析 | 同目录多代只留数字最大的那份；`_no-cwd_` 不瞎猜 cwd |
| 增量 | 第二次同步只推新增字节；小尾巴先攒着，`pending` 可见 |
| 闲置兜底 | 一小时没动的 1 KB 会话也能传上去 |
| 收缩自愈 | 截掉尾部后越界分段被删、游标回退、后续续得上 |
| 重建 | 卷整个清空后拼出的文件字节完全一致 |
| 不覆盖 | 卷里有文件就跳过（它可能比对象层新） |
| 坏数据 | 分段被改 → `校验失败`；缺一段 → `分段不连续`；**失败时不落半成品文件** |

**端到端**（真实容器，跑完已清理）：

```
写 307200 B → 容器运行中同步（docker exec）→ 1 个分段
  → 容器 stop → 再同步（--volumes-from）→ 成功
  → 删掉卷里的会话目录 → restoreTeam → 307200 B 回来，sha256 与原文完全一致
  → 容器 start → 文件仍在，sha 不变
```

**真实数据**：team-a 里已有的两个会话（20563 B / 406 B，`session.v4.jsonl.zstd`）
首次同步就上去了，第二次 restore 正确跳过（卷里已有，不覆盖）。

## 九、接口

| 接口 | 作用 |
|---|---|
| `GET /sessions?team=` | 侧栏列表：只查表，不碰卷。容器睡着、卷丢了都能列 |
| `POST /sessions/sync {team, force}` | 手动触发同步（`force` 把尾巴一次推完） |
| `POST /sessions/restore {team, force, sessionId}` | 人工修复：按对象层重建缺失的会话 |

三个都要求团队在注册表里；`sync`/`restore` 还会先检查卷存在，避免把卷建出来。
