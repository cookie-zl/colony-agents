# 技能与连接器（按团队隔离 + 市场）

一个团队 = 一个 dsh 进程 + 一份 `$DSH_HOME` + 一个 workspace。模型凭据、技能、连接器都长在这份 `$DSH_HOME` 里，所以**天然按团队隔离**；新团队从空开始，不会继承任何别人的东西。

这份文档讲清楚三件事：每类配置到底落在哪个文件、市场怎么把东西在团队之间搬、哪些边界是 dsh 本身的限制而不是没做。

## 1. 各类配置的落点

| 配置 | 落点（容器内） | 是否随团队隔离 | 新团队初始状态 | 改完何时生效 |
| --- | --- | --- | --- | --- |
| 模型 API Key | `$DSH_HOME/openai-gateway/api-key` | 是（在卷里） | 镜像种子里带的那一份 | 立即 |
| 凭据 | `$DSH_HOME/.credentials.yaml` | 是 | 首次启动生成 | 立即 |
| 默认模型 | `$DSH_HOME/cordis.patch.yml` | 是（在卷里） | 跟镜像 | 热重载（约 2 秒） |
| 技能（市场来源） | **控制面 API** 为准；多文件包额外物化到 `$DSH_HOME/market-skills/` | 是（按 team token 过滤） | 空 | 新会话立刻；进行中的会话等缓存失效 |
| 技能（本地手工） | `$DSH_HOME/skills/<name>/SKILL.md` | 是 | 空 | 立即（watch 目录） |
| 连接器（MCP） | `$DSH_HOME/cordis.patch.yml` | 是（在卷里） | **空** | 热重载（约 2 秒），见 `docs/20` |

### 为什么连接器以前不是隔离的

dsh 的配置层优先级是：

```
bundles（镜像烘焙的 profile）
  → $DSH_HOME/profiles/web/cordis.patch.yml
  → $DSH_HOME/cordis.patch.yml        ← 团队级，在卷里
  → 命令行 --patch
```

我们镜像用 `DSH_PROFILE_SEED=refresh`，每次启动都拿镜像里的 profile 覆盖卷里的 `profiles/web`。所以写在 `profiles/web/cordis.patch.yml` 里的 MCP 是全团队共用一份、而且**重启就被冲掉**（UI 里改的也一样）。

改成写 `$DSH_HOME/cordis.patch.yml` 之后：在卷里、按团队隔离、优先级还比镜像 profile 高、不受 refresh 影响。代价是它必须在启动时读一次——**但改完不用重启进程**：dsh 的 `dsh-hmr` 在 watch 这个文件，落盘约 2 秒后自己重载（`docs/20` 有实测与三级判据）。只有改 `env` 才必须重建容器。

### 团队级模型 Key

`DEEPSEEK_API_KEY` 原本只从 `deploy/compose/.env` 读，**所有团队共用一份**：谁换了 key 全平台一起换，谁额度用完大家一起挂，账单也没法按团队切。

现在按团队覆盖：

```bash
make team-key TEAM=team-a KEY=sk-xxxxxx     # 给 team-a 配独立 key（会重启这个实例）
make team-key TEAM=team-a KEY=             # 清除，回落到全局 .env
make team-key-show TEAM=team-a             # 只看配没配，不显示内容
```

模型凭据不再落宿主明文文件：走控制面的模型网关（`docs/18`），密钥 AES-GCM 加密存在 `team_secrets` 表，
`team-up.sh` 起实例时注入的是「网关地址 + 可吊销 token」，容器里拿不到真 key。改 key **不用重启实例**。

两个容易踩的点：

- **改 `env` 必须重建容器，不能 `docker restart`。** 环境变量只在创建容器时注入，restart 沿用旧的 env——改完会「看起来成功了但根本不生效」。只改**配置文件**（`cordis.patch.yml` 这类）则不用动进程，dsh 自己热重载。控制面于是把重启分成两级：`restartDsh(team,'reload')` = `docker restart`（5 秒），`restartDsh(team,'recreate')` = `compose up --force-recreate`（9 秒/冷镜像 40 秒+）；装了连接器先等热重载窗口，超时才降级到 `reload`。细节见 `docs/20`。
- **明文在环境变量里。** 同机的 root 能通过 `docker inspect` 看到。要做到看不到，得把 key 写进 dsh 自己的凭据库（`$DSH_HOME/.credentials.yaml`，UI 的 Settings 就是这么存的），或者上 K8s Secret。

### 技能为什么不用重启
`dsh-skill-filesystem` 会 watch 扫描到的根目录，新增/改名/删除都会触发下一轮 catalog 刷新。它扫的根目录按 rank 排：

| rank | 名称 | 路径 |
| --- | --- | --- |
| 100 | project-dsh | `<项目根>/.dsh/skills` |
| 200 | project-agents | `<项目根>/.agents/skills` |
| 400 | user-dsh | `$DSH_HOME/skills` |
| 500 | user-agents | `~/.agents/skills` |

我们投放的是 rank 400，和项目目录无关，所以团队里任何会话都能看到。

**这条已经不再是主路径。** 市场技能现在由 `plugins/market-skill/` 从控制面 API 按需拉取，
卷里的 `skills/` 只留给团队手工放的本地技能。两种来源在 dsh 里靠 rank 共存：
市场是 550，本地 100/200/400/500 都比它小，**同名时本地赢**。

为什么能这么做：`@deepseek-ai/dsh-skill` 里 `skill` 是一张 **provider 注册表**，
`dsh-skill-filesystem` 只是其中一种实现。`SkillSummary.path` 的注释就写着
“absent for virtual skills”，`ctx.skills.get()` 只取 `skill.content` 字符串，从不打开路径。
内置的 `dsh-skill-badge` 就是纯虚拟技能的现成例子——整份实现 50 行。

三条硬边界，改之前先确认能接受：

| 边界（Constraint） | 后果 | 现在的处理 |
|---|---|---|
| 技能带 `scripts/` 要真实文件才能执行 | HTTP 拉不到可执行文件 | **已解决**（`docs/13` §12）：多文件包走 `/market/skills/:n/:v/bundle`，物化到 `$DSH_HOME/market-skills/<name>@<ver>-<digest:8>/` 再以 `resourceBase: directory` 交给内核；纯 prompt 技能仍走纯文本，不打 tar |
| 控制面不可达 | 新会话拉不到目录 | `list()` 返回 `complete:false`，内核保留进程内 last-good；不用磁盘副本兜底 |
| 内核目录缓存没有 TTL | `invalidate()` 之外永不重查 | 插件比对 `rev`（可见集合的摘要），变了才 `invalidate()` |

第三条决定了实际体验：**装完技能，新会话立刻能看到；正在进行的那个会话要等它自己
命中不了缓存才会更新**。之所以够用，是因为团队里总有人开新会话。

物化目录刻意不叫 `skills/`：后者是 `dsh-skill-filesystem` 的 rank 400 根，
放那儿会让同一个技能有两个 provider 提供，filesystem 那份赢——于是「门户里停用了，
容器里还在生效」。放在 `market-skills/` 下，技能是否可见完全由库决定。

## 2. 市场

市场就是仓库里一个目录，可以进 git，改动看得见 diff：

```
deploy/market/
├── index.json                 # 市场索引：有哪些包、谁发的、什么版本、公开还是私有
├── defaults.json              # 新建团队时自动装什么（默认空）
└── packages/
    ├── skills/<name>/         # 技能包，就是 dsh 认的那个目录格式（SKILL.md + references/ scripts/ 都行）
    └── mcp/<name>.json        # 连接器包，描述 transport/command/args/env
```

### 包格式

技能包不加任何东西，`SKILL.md` 的 frontmatter 就是元信息：

```yaml
---
name: hologres-query
description: 在 Hologres 上写查询的规范……
---
```

带脚本/references 的技能就是同一个目录多放几个文件，发布后整目录一起进市场
（`scripts/**` 的可执行位保留），运行时物化落盘——见 `docs/13`。

连接器包是一份 JSON：

```json
{
  "kind": "mcp", "name": "github", "version": "1.0.0",
  "spec": { "transport": "stdio", "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"], "env": { "GITHUB_TOKEN": "" } },
  "env": [{ "key": "GITHUB_TOKEN", "required": true, "desc": "repo 权限即可" }]
}
```

`env` 数组是给安装表单用的：必填项没填，安装会直接拒绝，不会写一个空 token 进去。

### 四种流向

| 动作 | 从哪里到哪里 | 会不会动源 |
| --- | --- | --- |
| 安装 | 市场 → 团队卷 | 只读市场 |
| 发布 | 团队卷 → 市场 | 只读团队卷，**不碰运行中的实例**（休眠中的团队也能发） |
| 卸载 | 从团队卷删掉 | 只动目标团队 |
| **分享（投递）** | 团队卷 → **接收方待接收区** | 只读源团队，**不进市场、不写对方卷** |
| **启用** | 待接收区 → 接收方团队卷 | 只动接收方 |

发布的包带 `owner` 和 `visibility`。`private` 的包只对拥有它的团队出现在市场里——别人的私有包连标题都看不到。

### 点对点分享：默认不生效

市场解决的是「让谁看得见」，分享解决的是「就这个包，给那个团队」。两者刻意分开：分享不写 `index.json`、不落 `deploy/market/`，接收方在市场里看不到这个包。

**投递 ≠ 生效。** 分享过来的包先落在控制面的 `deploy/orchestrator/inbox/<团队>/<分享id>/`，此时：

- skill 不在 `$DSH_HOME/skills` 里，dsh 根本扫不到；
- 连接器不在 `cordis.patch.yml` 里，不会被加载。

接收方在门户「待接收」里看到来源团队、分享人、时间、版本和**备注**，由 owner 决定启用还是拒收。启用那一刻才写进它的卷（连接器还要过一遍 `dsh --dump-config`，失败回滚、记录仍是待接收，可以改凭据重试）。拒收只留一条 `rejected` 流水，暂存内容立即删除。

这样设计的理由：分享是跨团队投递，默认生效等于「别人能单方面改我的配置」。默认关闭把最终决定权留在接收方，同时保留「谁给了谁、为什么给」的痕迹。

```bash
make share        FROM=team-a TO=team-c KIND=skill NAME=ad-report-audit NOTE="研发组本周要用"
make shares       TEAM=team-c          # 收发流水 + 待接收项（含 id）
make share-enable TEAM=team-c ID=<id>  # 接收方启用
make share-reject TEAM=team-c ID=<id>  # 接收方拒收
```

门户上在 `/__auth/packages`：owner 能看到「把本团队的技能/连接器分享给其他团队」表单（可填备注），目标团队限定为**你自己也在其中的团队**；接收方页面顶部的「待接收」卡片显示来源、分享人、备注，带启用/拒收按钮。

四条规则不是随口定的：

- **默认关闭。** 没有启用这一步，跨团队写入就等于单方面改配置。
- **目标团队必须是"你也在其中"，管理员除外。** 分享是跨租户投递，不该由一个只能管自己团队的人发起。
- **凭据不过河。** 源团队 `cordis.patch.yml` 里的 `env` 已经是解析后的真实值，原样搬过去等于把 A 团队的 token 送给 B 团队。分享只搬结构 + 键名，接收方启用时自己填。
- **只搬市场块/分享块。** 团队手写在同一个文件里的其他 MCP 是它自己的东西，不会因为分享了 filesystem 就跟着走。

### 操作日志

技能与连接器的每次变更都记一条，落在库里（SQLite 的 `ops` 表，见 `docs/12`），按团队可查：

| 字段 | 说明 |
| --- | --- |
| `action` | `install` / `uninstall` / `upgrade` / `publish` / `share` / `enable` / `disable` / `reject` |
| `team` | 被操作的团队（分享时是接收方） |
| `kind` / `name` | 技能或连接器、包名 |
| `by` | 操作者账号；脚本调用记 `make` / `console` |
| `note` | 分享备注等 |
| `detail` | 补充说明：版本、失败原因 |
| `from_team` / `to_team` | 分享类操作的双方（结构化，可按来源过滤） |

只留最近 500 条。它和访问审计（`deploy/auth/audit/*.jsonl`）是两个视角：审计回答「谁访问了哪个团队」，操作日志回答「谁把这个技能装上/分享/启用了」。门户页面底部列出本团队最近 20 条（含别人分享给本团队的），成员可见、owner 可操作。

> 历史包袱：`oplog.json` 曾经是这条日志的落点，逐 2026-11 迁到库里。旧文件仍在原地（作为回退基线），但业务路径已不再写入——此前正是「写表 + 写文件」两套并存，导致门户上「安装/卸载/停用/升级」整段缺失。

### 写入连接器时不会破坏手改

每个包写成一个带标记的块：

```yaml
# >>> market:mcp:filesystem v1.0.0 由市场安装，勿手改本块
- insert:
    - id: mcp-market-filesystem
      ...
# <<< market:mcp:filesystem
```

装新版时只替换这两行标记之间的内容；卸载时只删这一段。团队自己在同一个文件里手写的 MCP 原样保留。

行 id 固定为 `mcp-market-<name>`，而不是 `mcp-<name>`：dsh 允许团队手写自己的 `mcp-<name>`，装市场包不该把它顶掉。`serverName` 仍然用原名，因为模型看到的工具名是 `mcp__<serverName>__<tool>`，必须稳定。

## 3. 控制面接口

```bash
make market                                  # 市场清单（TEAM=team-a 时带已装版本）
make packages TEAM=team-a                    # 这个团队装了什么
make install  TEAM=team-a KIND=skill NAME=hologres-query
make uninstall TEAM=team-a KIND=mcp NAME=filesystem
make publish  TEAM=team-a KIND=skill NAME=ad-report-audit VISIBILITY=private
make share    FROM=team-a TO=team-c KIND=skill NAME=ad-report-audit NOTE=原因
make shares   TEAM=team-c
make share-enable TEAM=team-c ID=<id>
make share-reject TEAM=team-c ID=<id>
```

对应 HTTP：

| 端点 | 说明 |
| --- | --- |
| `GET /market?team=` | 市场目录（读表，当前发布版本）+ 该团队已装版本 |
| `GET /packages?team=` | 已装清单（`SKILL_MODE=db` 时读表，休眠/归档的团队也准确），附带 `origins`、`shares`、`pending`、`ops` |
| `POST /market/install` | `{team,kind,name,env,by?}` |
| `POST /market/uninstall` | `{team,kind,name,by?}` |
| `POST /market/publish` | `{team,kind,name,version,visibility,by?}` — 技能内容取自团队卷里的真实目录（手写的，或改过的物化目录），休眠中的团队回落成「从库里的当前版本 fork」 |
| `POST /market/upload` | `?team=&name=&version=&visibility=`，body 直接是 `tar.gz` — 不需要团队实例存在，也是唯一能发多文件包的外部入口 |
| `POST /market/toggle` | `{team,name,enabled,by?}` — 装了但不想让模型看见 |
| `POST /market/share` | `{from,to,kind,name,note?,by?}` — 记一行 pending，默认不生效 |
| `POST /market/share/enable` | `{id,team,by?,env?}` — 接收方启用，技能在这一刻才挂上 |
| `POST /market/share/reject` | `{id,team,by?}` — 接收方拒收，删除暂存 |
| `GET /shares?team=` | 分享流水 + 该团队的待接收项 |
| `GET /market/token?team=` | 该团队的只读市场 token（给 dsh 容器用） |

**给 dsh 用的三个端点**（鉴权用每团队一枚的 `market token`，不是 `console-token`）：

| 端点 | 返回 |
| --- | --- |
| `GET /market/skills` | `{team, rev, items[]}`，`items` 只含本团队已启用的技能，每项带 `bundle:{hasBundle,size,count,digest}` |
| `GET /market/skills/:name/:version` | `text/plain` 正文（已剥 frontmatter）；没装/停用/版本不符都回 404，不区分 |
| `GET /market/skills/:name/:version/bundle` | `application/gzip` 整包，带 `X-Dsh-Digest` / `X-Dsh-Manifest` 供客户端校验 |

后两个走的是**同一道闸门**（装了 → 启用了 → 版本对得上），否则「正文读不到但包能下」
就成了绕过私有可见性的旁路。

身份**只从 Bearer token 推导，不接受 `?team=`**——否则 team-c 的容器改一个 query 参数
就能读到 team-a 的私有技能。这一点和分享功能的原则一致：越权按记录或身份判，不按表单参数判。

控制面只校验「团队存在、两边不是同一个、包名合法、这条分享确实属于这个团队」；**谁能分享给谁、谁能启用，在账号服务那侧判**，因为那是权限问题，不是运维问题。启用/拒收还会校验 `record.to === team`，即使表单被改也写不进别人的卷。

## 4. 门户

团队卡片上多了「技能」按钮，进去是 `/__auth/packages`：

- **技能 / 连接器** 两个 tab
- **待接收**：别人分享过来、还没启用的包。显示来源团队、分享人、时间、版本、备注；owner 可启用或拒收。普通成员只读
- **本团队已装**：名称、已装版本、卸载；别人分享进来的标「来自 <团队> 分享」
- **分享**：把本团队当前 tab 的某一项投递给指定团队（仅 owner，目标限自己所在的团队，可写备注）
- **市场**：公开包 + 本团队发布的私有包；已装的标「已安装」，没装的给安装按钮（连接器会带出必填参数输入框）
- **发布**：选类型、包名、版本、私有/公开
- **分享记录**：最近的流转，含方向、分享人、状态（待接收/已启用/已拒收）、备注
- **操作日志**：本团队最近的安装/卸载/发布/分享/启用/拒收，含操作者与说明

权限沿用团队模型：成员能看，只有 owner（或管理员）能装、卸、发布、分享、启用、拒收。

## 5. 踩过的三个坑（都已修，写下来免得重犯）

**1. `@` 开头必须是带引号的 YAML 标量。**
`- @modelcontextprotocol/server-filesystem` 裸写会让整个 patch 解析失败，dsh 启动即崩（容器无限重启）。`@` 和反引号是 YAML 保留起始符。

**2. 写完配置必须让 dsh 自己解析一遍。**
上面那个错误是安装时发现的——现在 `installMcp` 写完立刻跑 `dsh --profile web --dump-config` 校验，不通过就回滚到安装前的内容（原本没有这个文件就删掉），实例不受影响。

**3. macOS 的 tar 会把 `._xxx` 元数据文件打进包。**
装进团队卷之后会和真文件混在一起出现在技能目录里。打包时加 `COPYFILE_DISABLE=1`。

## 6. 边界

- **连接器写完不用重启进程**：`dsh-hmr` watch 着 `cordis.patch.yml`，落盘约 2 秒后自动重载，MCP 子进程随之起落（实测 install 2.04s / uninstall 2.08s，会话不丢）。控制面先等热重载窗口并验证生效，`basis` 取 `process`（数到新子进程）才算 `confirmed`；超时才降级 `docker restart`。改 `env` 是唯一必须 `--force-recreate` 的情况。技能不受影响。
- **包之间没有依赖解析**，也没有版本约束。同名的包装新版会直接覆盖，不保留旧版。
- **私有包的"私有"只到市场层**：它仍然躺在宿主磁盘的 `deploy/market/` 里，有仓库读权限的人能直接看到。真要隔离得把市场拆成按团队的服务端存储。
- **分享不留撤销通道**：投递出去就是对方卷里的东西，源团队无法远程收回；要撤回只能让对方卸载。流水（`shares.json`）只记事实，不做状态机。
- **模型 API Key 走的是 dsh 自己的机制**，市场不管这一层。要按团队配不同 key，改 `$DSH_HOME/openai-gateway/api-key`（每团队一份）即可，不需要新概念。
- **新建团队默认不装包**（`defaults.json` 是空的）。要让新团队自带基础技能，往里面填名字即可，建团队时会自动装，失败只记日志不回滚团队。
