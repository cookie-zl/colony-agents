# 11 · 助理与消息机器人（@ 才处理版本）

> 一句话：一个助理 = 一个 IM 机器人 + 一个固定 dsh 会话；多个助理互不冲突；
> 群里 @ 机器人时消息转发到 dsh，结果由机器人发回。当前版本**只处理被 @ 的消息**。
> 对应 [总览](./README.md)、本文的「未完成」小节

## 一、需求

| 原始诉求 | 落地口径 |
|---|---|
| 门户里加助理菜单，能新增多个助理 | 团队级助理列表，owner 可增删改、启停、测试 |
| 一个助理对应一个会话，他俩不冲突 | 一个 `session_id` 只属一个助理；同一助理串行、不同助理并行 |
| 一个助理对应一个机器人 | `UNIQUE(platform, robot_key)`：一个机器人只能绑一个助理 |
| 支持钉钉和飞书，可自建应用 | 两个适配器归一化成同一种事件，调度器不认平台 |
| 先做只有 @ 才处理的版本 | 非 @ 消息一律 `ignored`，绝不进 dsh |

### 竞品对照：WorkBuddy 的「助理」

官方文档口径（[助理（远程任务）](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Assistant)）：
助理是**远程控制**功能，通过微信 / 企微 / QQ / 钉钉 / 飞书远程指挥电脑上的 WorkBuddy 执行任务。

| 对比项 | 普通任务 | WorkBuddy 助理 | **我们这版** |
|---|---|---|---|
| 会话 | 多个并行 | **仅一个会话**，所有远程指令集中处理 | **每个助理一个会话**，可有多个助理 |
| 工作目录 | 自由指定 | 固定助理专属文件夹 | 固定 `/workspace`，按 team 隔离 |
| 上下文 | 可清空 | 保留完整历史，不可清空 | 保留完整历史（固定 `--session-id`） |
| 机器人 | — | 多平台通道**汇到同一个助理** | **一个机器人绑一个助理** |
| 安全边界 | — | 绑定身份 + 来源校验 + 高风险任务确认 | 加签 / token 校验 + `msgId` 幂等（高风险确认未做） |

**关键差异**：WorkBuddy 是「一个遥控器」，多个 IM 通道都落到同一个会话；
这里要的是「N 个遥控器，各开各的窗口」。dsh 本身是多会话架构，所以多助理隔离
不需要改内核，靠两条唯一约束 + 队列就能做到。

## 二、技术方案

### 隔离语义（核心）

```
UNIQUE(platform, robot_key)   → 一个机器人只能绑一个助理
UNIQUE(session_id)            → 一个会话只属一个助理
每助理一条串行队列            → 不会两个 headless 抢同一个 session.lock
全局并发闸门（默认 2）        → 多助理可并行，但不把 2 GiB 容器打满
```

### 会话首建

`dsh --profile headless --session-id <id>` 遇到未知 id 会直接报错，所以**不能预先造 id**：

```
首条消息：不带 --session-id → headless 新建会话 → 从 JSONL 的 type:'session' 拿 id → 回写 assistants.session_id
后续消息：带 --session-id → 同一窗口续聊，上下文连续
```

### 链路

```
平台回调（免 console-token，各自验签）
  → normalizeEvent() 归一化：@ 判定 / 去占位符 / 幂等键
  → 同步完成「查助理 + INSERT OR IGNORE 流水 + 入队」→ 立刻回 200（平台要求几秒内响应）
  → 后台：docker exec dsh --profile headless --json ...
  → 只收 stdout 解析 text 事件（stderr 是插件日志，不能混）
  → 按 3000 字符分片 → POST 出站 webhook → 流水标 done
```

**为什么不能用 `runtime.mjs` 的 `run()`**：它把 stdout/stderr 合并并截断到 4 万字符，
首帧 `type:'session'` 可能丢；headless 的事件流在 stdout，所以单独用 `spawn` 分开收集。

### 平台差异（都被归一化掉）

| | 钉钉 | 飞书 |
|---|---|---|
| 入站通道 | **Stream 长连接**（默认）/ HTTP 回调（备用） | HTTP 回调 |
| 事件 | Stream `CALLBACK /v1.0/im/bot/messages/get` | `im.message.receive_v1` |
| @ 判定 | `isInAtList` / `atUsers` | `message.mentions[]` |
| 幂等键 | `msgId` | `message_id`（官方明确不要用 `event_id`） |
| 正文 | `text.content` | `content` 是**双重 JSON 字符串**，要先 parse |
| 路由键 | `robotCode`，匹配不到按 clientId 兜底 | `header.app_id` |
| 入站校验 | Stream 由 ticket 鉴权；HTTP 模式用加签 | Verification Token（含 URL `challenge`） |
| 回复地址 | 消息带 `sessionWebhook`（约 1.5 小时），缺失回落长期 webhook | 用助理配置的自定义机器人 webhook |
| 回复体 | `{msgtype:'text', text, at:{atUserIds}}` | `{msg_type:'text', content:{text:'<at ...> ...'}}` |

凭据全部走 `team_secrets` 信封加密，`scope = assistant:<id>`；列表接口只回「有没有配」，**不解密也不回显**。

### 传输层：钉钉走 Stream，飞书走 HTTP 回调

钉钉用**出站长连接**（Stream）：控制面拿 Client ID / Client Secret 调
`POST /v1.0/gateway/connections/open` 换 `{endpoint, ticket}`，再 `wss://<endpoint>?ticket=` 建连。
消息从这条连接推下来，**不需要公网 IP、不需要回调地址**。协议细节（协议原文见钉钉「Stream 模式协议接入说明」）：

```
注册连接   POST /v1.0/gateway/connections/open
           body: { clientId, clientSecret, subscriptions:[
                     {type:'EVENT', topic:'*'},
                     {type:'CALLBACK', topic:'/v1.0/im/bot/messages/get'} ] }
           → { endpoint, ticket }        # ticket 90 秒有效、只能用一次

建连       wss://<endpoint>?ticket=<ticket>

帧         { specVersion, type: SYSTEM|EVENT|CALLBACK, headers:{topic,messageId,contentType,time}, data }
回执       { code:200, headers:{ messageId, contentType:'application/json' }, message:'OK', data }
```

三个必须照做的细节：
- **探活** `topic=ping` 要把 `data` **原样**回传（改一个字节就判死）；
- **disconnect** 是服务端在做负载均衡，必须**换新 ticket** 立即重连，旧 ticket 不能复用；
- 每帧都要带**同一个 messageId** 回执，否则平台当未收到并重推。

回执**先发再跑业务**：dsh 一轮几十秒到几分钟，把回执挂在业务里会让平台超时重推。
归一化之后的事件和 HTTP 回调那条路完全一样（`normalizeEvent()` → `dispatcher.handle()`），
所以调度器、流水、出站逻辑一行没改。

钉钉仍保留 HTTP 回调入口（`POST /assistants/inbound/dingtalk`）用于对照排查；
飞书暂时只有 HTTP 回调，需要公网可达或内网穿透。

### 为什么一个应用只允许一条长连接

`createStreamManager` 按 **clientId** 去重，不按助理去重：同一应用开两条连接，
钉钉会把消息随机推到其中一条，群里表现就是「有时候回、有时候不回」。

同应用的多个助理靠 `conversation_id` 区分；`robotCode` 只作参考——
不同版本的应用里它有时是 AppKey、有时是 corpId 加后缀，匹配不到时用「本连接对应的助理」兜底。

### 界面层（两个入口，同一份数据）

```
dsh 侧栏「助理」面板 (plugins/client-ui-assistants)
  └→ GET  /__auth/api/assistants          ← 列表 + 平台元信息 + 回调地址，一次给全
  └→ POST /__auth/api/assistants/action   ← create / update / toggle / delete / test
  └→ GET  /__auth/api/assistants/messages ← 消息流水
门户 /__auth/assistants（服务端渲染，兜底 + 深链）
  └→ 表单 POST → 同一批控制面 /assistants
```

面板不直连控制面：控制面 token 不能进浏览器，平台凭据也只在服务端解密。
所以 auth 服务多了一层 JSON 代理，团队 id 固定取 `cfg.team`（不接受请求参数，
否则改一个 query 就能看别人团队的助理）。

**「回调地址」由服务端算，不由前端拼**：`ASSISTANT_INBOUND_BASE` 优先，
否则用「浏览器访问的主机名 + 控制面端口」。主机名是本机名时（`*.localhost` / `127.*`）
接口里带 `local: true`，面板直接把「平台服务器打不进来」标黄，避免配完在那儿干等。

**平台字段说明也由服务端下发**（`ASSISTANT_PLATFORMS`）。加平台只改这一张表和
`assistant-channels.mjs`，前端不用动；`credentials[].field` 必须与
`assistant-http.mjs` 的写入口（`CREDENTIAL_KEYS`）对齐，所以两边共用同一份常量。

**面板形态（2026-11-14 改过一版）**：早期是「先看两块平台大卡（各写一段接入说明）→ 再看助理列表」，
等于首屏被说明文字占满。实际用起来，人每天来这里是为了**看/改已有助理**，不是读接入文档，
于是改成**按平台分组的列表**：

- 每组一行标题：图标 + 平台名 + 数量 + `接入说明 ▸`（点开才展开，占满整行）+ `接入钉钉/飞书`；
- 标题下面直接是该平台的助理行（左信息、右操作），空平台只留一行虚线提示；
- 「按群隔离」「回调地址」这类说明都收进对应平台的接入说明里，钉钉那条只有一句
  「走 Stream 不需要回调地址」。

主流的做法也是这个顺序：Slack 的 Apps、GitHub 的 Integrations 都是**先列已装的**，
「添加」才进目录；把目录当首页只在平台很多（十几个）时才划算，只有两个平台时纯属浪费首屏。

**两个交互细节（踩过）**：
- 点「接入钉钉 / 接入飞书」直接带着平台进入新建表单，不用先在下拉里选——
  新建时平台也改成两个按钮，切换后凭据字段跟着变。
- 编辑表单很长（`Client ID` / `Secret` / `AgentId` / 出站 webhook / 加签），保存和取消
  **在标题栏和底部吸底栏各放一份**：只在表单末尾放按钮时，填到一半想退出得先滚到底，
  看起来就像「没有退出编辑的入口」。
- **面板必须自己当滚动容器**：dsh 的 `centerCol` 是 `display:flex; flex-direction:column;
  overflow:hidden`，子面板只写 `minHeight:100%` 时，内容超长会被父级直接裁掉且不能滚，
  表现是「拉到底就滚不动了」。所以 `S.page` 改成 `height:100% + overflowY:auto`。

### 填什么、从哪儿拿

| 字段 | 钉钉 | 飞书 |
|---|---|---|
| 机器人标识 | 应用凭证页的 **Client ID**（原 AppKey），企业自建应用的 RobotCode 与它一致 | 开放平台 → 开发者后台 → 凭证与基础信息 → **App ID** |
| 收消息（必填） | **Client ID + Client Secret**（Stream 建连用） | 事件订阅页的 **Verification Token** |
| AgentId（可选） | 应用凭证页的「原企业内部应用 AgentId」；实测主动发送用 `robotCode` 即可，暂未用到 | — |
| 出站 webhook（可选） | 群自定义机器人 Webhook；现在只是第三顺位兜底（主通道是 OpenAPI 主动发送） | 群自定义机器人 Webhook；**不填就发不出结果** |
| 回调地址 | 走 Stream 不需要；HTTP 模式才是 `…/assistants/inbound/dingtalk` | `…/assistants/inbound/feishu`（需公网） |

钉钉的必填项是「Client ID + Client Secret」，因为默认走 Stream；飞书的必填项是 Verification Token。
没配齐时卡片上是红点并写明「收不到消息」——这是真实行为，不是提示文案。

**钉钉后台还要做一步**：应用 → 机器人 → **消息接收模式选「Stream」**。选 HTTP 就只会往回调地址推。

**接口清单**

```
POST /assistants/inbound/dingtalk|feishu     平台回调（平台验签，免 console-token）
GET  /assistants?team=                       助理列表
POST /assistants                             新建（含凭据）
POST /assistants/:id                         改名 / 人设 / 绑定群 / 启停 / 换凭据
DELETE /assistants/:id                       删除助理 + 流水 + 凭据
GET  /assistants/:id/messages                消息流水
POST /assistants/:id/test                    模拟一条 @ 消息跑完整链路
```

### 消息去哪了：入站长连接 + 出站 OpenAPI

```
钉钉群里 @机器人
  → 钉钉经 Stream 长连接推一帧 CALLBACK（topic=/v1.0/im/bot/messages/get）
  → 控制面归一化 → assistant_messages 落一条流水（msg_id 用钉钉的加密 msgId）
  → docker exec dsh --profile headless --json（同一助理固定 session_id）
  → 出站：POST /v1.0/robot/groupMessages/send   ← 主动发送（主通道）
        ↳ 失败回落 POST <sessionWebhook>（消息自带，约 1.5 小时）
        ↳ 再回落助理配置的群机器人 OUTBOUND_WEBHOOK
```

**为什么 `sessionWebhook` 不能当主通道**：它是「回复这一条消息」的临时地址，约 1.5 小时过期。
dsh 一轮几十秒到几分钟，分片重试还会更久，长任务发结果时地址早就失效；它也不能主动发到别的会话。
WorkBuddy 这类助理之所以「随时 @ 随时回」，靠的是**入站长连接 + 出站 OpenAPI** 这一对：

| 方向 | 通道 | 关键点 |
|---|---|---|
| 入站 | Stream 长连接 | 免公网、断线自动重连、`ticket` 一次性 |
| 出站 | `/v1.0/oauth2/accessToken` → `robot/groupMessages/send`（群）/ `robot/oToMessages/batchSend`（单聊） | token 7200 秒、可缓存续期，随时能发 |

实现见 `deploy/orchestrator/dingtalk-openapi.mjs`：

- token 按 AppKey 缓存、提前 5 分钟续期，**401 才换 token 重试一次**（其它 4xx 重试没用）；
- `conversationType=2` 走群接口（`openConversationId`），`=1` 走单聊接口（`userIds`）；
- 自建应用机器人的 `robotCode` 实测就等于 Client ID（AppKey），所以直接用助理的 `robot_key`；
- 分片逐条发，任一通道成功即停，不会「OpenAPI 发一条、webhook 再发一条」造成重复。

`OUTBOUND_WEBHOOK` 退化成第三顺位兜底；**群里对话不需要配它**，配了也不会把回复改投到别的群。

**「测试发送」现在能真发到群**：`POST /assistants/:id/test` 支持 `conversationId`
（群里 @ 一次，从流水里抄 `conversation_id`，形如 `cid…==`），带上就走 OpenAPI。
不带 `conversationId` 时仍只跑 dsh、把回答留在流水 `outbound` 里——因为没有会话可发。

### 代理工作区：助理的会话不混进用户自己的工作区

助理的 `session_id` 就是普通 dsh 会话，但它的 cwd 被钉在 **`/workspace/agents`**：

```js
// assistants.mjs: headlessCommand
docker exec -w /workspace/agents dsh-team-a-dsh-1 dsh --profile headless --json "…"
```

dsh 用 cwd 决定会话归属，所以助理的会话在侧栏里是独立分组 **「代理工作区」**，
用户自己的会话还在「工作区」，两边互不干扰；产物仍落在 `/workspace` 之下（持久挂载，重建不丢）。

这个目录由 `plugins/workspace-guard` 负责建好并登记（`registry.create('/workspace/agents', '代理工作区')`），
**并且补登记会话**：headless 进程建会话时只写 `sessions/--workspace-agents--/`，
不会调 `workspaceRegistry`，不补的话侧栏根本看不到。

```
[workspace-guard] 代理工作区就位：/workspace/agents
[workspace-guard] 补登记 1 个未归组会话到 /workspace/agents（否则它们只在磁盘上，侧栏看不到）
```

> 切换前已有的助理会话 cwd 是 `/workspace`，它们会留在「工作区」里（历史仍可查）。
> 新会话一律进「代理工作区」。
>
> **旧会话不能迁过去**：实测 `entity.attachSession()` 会按会话 cwd 强校验，改文件 header、
> 改 `session_projcache` 的 `identity.cwd` / `workingDirectory`、甚至重启，dsh 仍然报
> `its cwd resolves to '/workspace'`——它还有更高层的会话索引，不认外部改文件。
> `migrate-agent-sessions.mjs` 因此标记为 `@deprecated`，只保留结论与备份逻辑。
> 想彻底分开，只能让助理从新会话开始（本仓库已经把 `session_id` 重置过一次）。

**人设只在首轮注入**：`prompt = 首轮 ? 人设 + 问题 : 问题`。dsh 会话是持久的，
首轮建立口径后模型会带着走；每条都拼会让会话记录变成「一大段人设 + 一句话」，
既不像正常对话，标题也会被首条消息里的那段人设占满。

### 沟通记录：连思考过程一起留档

headless 的 JSON 流里本来就有 `thinking`，之前只解析了 `text`，所以界面上只能看到问答。
现在 `parseHeadlessOutput` 把三类事件都收下来，落到 `assistant_messages`：

| headless 事件 | 落库字段 | 界面 |
|---|---|---|
| `{"type":"thinking","text":"…"}` | `thinking` | 折叠行「思考过程 · N 字」，点开看全文 |
| `{"type":"text","text":"…"}` | `outbound` | 助理气泡（多段用空行拼） |
| `{"type":"status","phase":"step_end","usage":{…}}` | `usage`（JSON 字符串） | 元信息里的 `N tokens` |

发送失败也照样落库：模型已经答出来的内容与思考都留在记录里，
配合失败气泡能分清「没答出来」和「答了但没发出去」。

> 思考是模型自己的语言，实测经常是英文（`The user is asking me…`），回复是中文——
> 这是模型行为，不是解析串台。

### 事故：侧栏「暂无会话」不等于数据丢了（2026-11-13 01:10）

现象：侧栏「工作区」下空白，只显示「暂无会话」，其余分组还在。

根因不在数据，而在 **`workspaceRegistry` 加载失败**：

```
workspace (@deepseek-ai/dsh-workspace): Error: EACCES: permission denied,
  open '.../sessions/--workspace--/session-09fe7866-…/session.v4.jsonl.zstd'
session-controller: pending (waiting for service: workspaceRegistry)
workspace-guard:   pending (waiting for service: workspaceRegistry)
```

`workspace.json` 里 18 条会话一条没少、文件也都在，但注册表初始化时读不到其中
一个会话头就整体失败，所有依赖它的插件变 `pending`，于是列表为空。

为什么读不到：上一轮迁移失败后回滚，我用 `docker cp` 把会话文件塞回容器，
**`docker cp` 保留宿主 uid（501），容器里的 dsh 是 1000，而会话文件是 `-rw-------`**。

修法的两个坑：

- 容器里 `-u 0` **没有特权**（OrbStack 的 btrfs 子卷 + 用户命名空间，root 连
  `700` 的 `/home/dsh/.dsh` 都进不去），所以 `chown` 必然失败；
- 只能「以 dsh 身份从 stdin 重写」：`docker cp` 取到宿主 → `rm`（目录可写即可 unlink）→
  `cat file | docker exec -i -u 1000 sh -c 'cat > …'`，属主自然变 1000。

已固化成工具：

```
make fix-perms                 # 只报告属主异常的路径
make fix-perms APPLY=1         # 修复（内容不变，属主改回 dsh）
make fix-perms TEAM=team-b     # 指定团队
```

脚本：`deploy/orchestrator/fix-session-perms.mjs`。修完要重启 dsh，
注册表才会重新加载（`restart` 即可，不用重建镜像）。

**判断口诀**：侧栏空白 / 暂无会话时，先看 `docker logs … | grep EACCES`，
再 `make fix-perms`；不要急着去恢复备份或重建数据卷。

### 自测抓到并修掉的 4 个问题
1. `db.transaction()` 在 `node:sqlite` 的 `DatabaseSync` 里不存在 → 改成显式 `BEGIN/COMMIT/ROLLBACK`
2. `cleanMention` 先抹名字会留下孤立 `@` → 最后再收一次
