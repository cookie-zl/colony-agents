# 10 · 定时任务能力实测（**未达标 · 待办**）

> 一句话：用户让 agent「建一个定时任务发消息」，agent 没有创建 dsh 的 schedule，而是自己写脚本 +
> 让用户去别处配 crontab/systemd timer。换一个不含「定时任务」字样的问法，仍然如此。
> 本篇是实测记录与根因分析，**这一项不算已完成功能**，对应待办 `docs/TODO.md` B1。

## 一、需求

用户原话（2026-11-08，会话 `<session-id>`）：

```
「配置成定时任务发吧 只需要最高的一个项目就行」
```

期望：创建一个到点自动发消息的自动化任务。实际：agent 写了 `github_daily_top_one.py`、
测通钉钉发送，然后想配 `crontab`，发现容器里没有，最后把 crontab 命令贴给用户
让「在实际服务器上执行」。用户观察到「好像是自己写了一个定时器」。

本轮追加验证：**换一个问法**（不出现「定时任务 / crontab」），看是否真的能走 dsh 原生能力：

```
「以后每天早上 9 点（北京时间）提醒我查看一下 Hologres 日报任务的运行状态，
 在我让你停之前一直保持。」
```

## 二、技术方案 · dsh 里到底有什么

先厘清「自动化任务」在这两个平台里是两种不同的东西：

| | WorkBuddy 的 automation | dsh 的 `schedule_create` |
|---|---|---|
| 归属 | **控制面**，独立于会话 | 会话内，被那个会话拥有 |
| 容器休眠 | 照样跑（调度在平台侧） | 不跑（进程内 `setTimeout`，靠 dsh 常驻） |
| 到点做什么 | 起一次新任务 | 往**原会话**投一条 prompt，agent 醒过来执行 |
| 持久化 | 平台库 | 会话日志 `schedule/changed` + `tasks` 表，重启能恢复 |
| 会话归档 | 不受影响 | `workspace/session-stop` 会 `stopSessionTasks()` |

`dsh-schedule` 本身能力是够的：`schedule_create` 支持 `after_seconds / at / every_seconds /
daily / weekly / cron` 六种定时参数，`daily: {time, time_zone}` 能直接表达「每天 9 点北京时间」；
`ScheduleRuntime` 用进程内 `setTimeout`（`timer.unref()`）+ `tasks` 表持久化，
错过的一次会在恢复后补投（`overdue`）。**dsh 里没有平台级 automation**。

## 三、实测与结果

### 原始会话（web profile，用户实际入口）

| 证据 | 结果 |
|---|---|
| 工具名单 | **51 个**，含 `schedule_create / list / update / delete` |
| 对这 4 个工具的调用 | **0 次** |
| 会话日志 `schedule/changed` 事件 | **0 条** |

| 证据 | 结果 |

### B 组 · 临时 patch 把 schedule 挂到 headless

写 `/tmp/sched-patch.yml` 插入 `- id: schedule` + `- id: tool-schedule`，
`--dump-config` 确认两项都在（第 407/409 行），但实际启动：

`schedule` 服务依赖 web 的 host runner / `sessionController` 体系，**headless 链路结构上挂不上**。
B 组因此无法完成对照实验，也说明这不是「模型会不会选」单方面的问题。

### 现状确认

`/home/dsh/.dsh/storages/` 下只有 `session_projcache`、`workspace.json`、`.bak`，
**没有任何 schedule 存储** —— 现在系统里没有任何定时任务在运行。
那次生成的脚本在 `/home/dsh/测试1/`（容器可写层），已在 21:30 重建中丢失，会话本身也已归档。

## 四、根因（两层）

1. **描述与意图错配（web 侧）**：`schedule_create` 的原文是
   「Create a **reminder** in the **current session** that delivers **prompt** when it becomes due」。
   三个词都指向「提醒我一下」，而「定时任务 / 每天早上」触发的是 OS 级 cron 的强先验。
   模型在读工具列表之前就已经在 thinking 里判定「做不到、得自己写脚本」。
2. **能力缺失（headless / SDK / ACP 侧）**：这条链路连 `tool-schedule` 都没挂，
   且 `dsh-schedule` 服务依赖 `sessionController`，简单 patch 补不齐。

## 五、待办（已记入 `docs/TODO.md` B1）

| 优先级 | 动作 |
|---|---|
| **P1** | 在 web profile 的 `agent-instructions` 加硬约束：遇到「定时 / 每天 / 每周 / 周期性 / 提醒我到点做 X」→ **必须**用 `schedule_create`（`daily`/`cron`），**禁止** crontab / `nohup` / `sleep` 循环 / systemd unit；脚本一律落 `/workspace` |
| **P1** | 验收：headless 或 web 跑同句，检查 `tool/call` 里出现 `schedule_create`、日志里出现 `schedule/changed`、重启后 `schedule_list` 仍在 |
| P2 | headless 链路补齐 schedule 服务（需连带 `sessionController`，或改造成独立 host runner） |
| P2 | 发布侧护栏：技能 / prompt 里出现 `crontab` 时告警，防回归（并入 D12） |

**不建议**把 `cron` 装进镜像：容器内 cron 需要自己当 PID 1 的子进程、重建即丢，
且与「会话内提醒」语义重复，属于用系统级机制去补平台级能力。
