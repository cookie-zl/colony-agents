# 09 · 代码规范审查

> 一句话：41 个 JS/MJS 文件过了一遍，21 处无争议的规范问题已直接修掉并跑全量自测；
> 剩下的按「是否掩盖根因」判定，不是简单按数量报问题。
> 审查时间：2026-11-10 · 范围：`deploy/orchestrator/`、`deploy/image/`、`plugins/` 下全部 `.mjs` / `.js`

## 一、需求

代码跨了 20 多篇设计文档、多次迭代和三个目录，容易出现三类漂移：

- **风格不一致**：同一文件里相邻的公开函数，有的有 JSDoc、有的没有
- **约定被遗忘**：插件日志必须走 stderr（因为 `dsh --json` 的 stdout 是 JSONL），后来新增插件容易写回 `console.log`
- **重构残留**：删掉功能后导入没跟着删

用户明确的规范口径：**public 方法必须带 JSDoc，private 可简略**；**修根因而非加锁/守卫**；
文档只写核心要点与一行示例。审查按这个口径，不套通用 lint 规则。

## 二、技术方案

两轮扫描，先粗后精：

1. **粗扫**（`/tmp/lint-scan.mjs`）：导出成员、函数长度、空 catch、TODO、`console.log`、硬编码线索。
   初报 167 处 —— 其中 137 处 `console.log` 绝大多数在控制面与 `verify-*` 里，是**正常日志**
   （`console.mjs` 是 HTTP 服务，不是 `--json` 事件流），不能一律判违规。
2. **精扫**（`/tmp/lint-precise.mjs`）：按文件位置区分语义，并逐条人工复核，
   排除函数长度的合并误判（例如 `buildMetrics()` 曾被测成 673 行，实际 33 行）。

**判定原则**：

| 现象 | 判定 |
|---|---|
| 控制面 / 自测脚本用 `console.log` | 合法，不改 |
| **插件**用 `console.log` | 违规，stdout 会打挂下游 JSON 解析 |
| 幂等清理路径的 `catch { /* 原因 */ }` | 若注释说明了「为什么可以吞」，可接受；不是「加守卫掩盖根因」 |
| 长函数 | 只在报告里列建议，不在审查轮里擅自重构 |

### 关于「修根因 vs 加守卫」

本轮专门核过：没有发现用加锁、重试、超时守卫去掩盖根因的写法。
反而有两处是**改算法而不是加兜底**的正面例子：

- `pruneSnapshots()`：改「10 分钟一次 + 单次 ≤20 + 失败聚合」，而不是给 `/health` 加缓存
- `normalizePatchText()`：把空 patch 写成合法的 `[]`，而不是在启动脚本里 catch fatal 后重启
