# 09 · 休眠与唤醒

一个团队闲置时把 dsh 进程停掉，有人回来访问时自动拉起。会话、工作区、登录态全部保留，用户最多等 5~8 秒。

## 一分钟版

```bash
export PATH=$HOME/.orbstack/bin:$PATH

make console              # 控制面（定时器在它里面，Ctrl-C 停）
make sleep TEAM=team-b    # 手动休眠：只停 dsh
make wake  TEAM=team-b    # 手动唤醒：起 dsh + 重新同步 token
make state                # 看每个团队的闲置时长与状态
```

自动休眠默认开启：**闲置 30 分钟 + CPU < 2% + 已运行超过 5 分钟**，每 5 分钟扫一次。

```bash
# 想当场看到效果，用短阈值起控制面
CONSOLE_IDLE_MS=15000 CONSOLE_SCAN_MS=5000 CONSOLE_MIN_UPTIME_MS=5000 make console
CONSOLE_AUTOSLEEP=0 make console    # 关掉自动休眠
```

## 休眠到底停什么

| 层 | 休眠时 | 为什么 |
| --- | --- | --- |
| Caddy 入口 | **常驻**（约 13MB） | 登录跳转、团队校验、唤醒拦截都在这里 |
| 账号服务 | **常驻**（约 12MB） | 唤醒请求得由它接住，否则用户拿到裸 502 |
| dsh 本体 | **停掉**（约 240MB） | 唯一值得省的部分 |
| 卷 dsh-home / workspace | **不动** | 会话、Cookie 签名密钥、代码都在这里 |

所以一个睡着的实例不是 0MB，而是约 25MB。换来的是：**用户不需要重新登录**（Cookie 签名密钥在卷里，重启后旧 Cookie 依然有效），只有入口 token 会变，而 token 由账号服务自动补。

## 触发链路（用户视角）

```
浏览器 → Caddy → forward_auth → /__auth/verify
                                    ├─ 醒着 → 200，放行 → dsh
                                    └─ 睡着 → 503 +「正在唤醒」页（meta refresh 2s）
                                                └─ 顺手 POST /wake → 控制面拉起容器
```

用户看到的是一个会自动刷新的页面，2~4 秒后自动进入 dsh。**不会看到 502**，也不会被要求重新登录。

埋点选在 `verify` 是有原因的：它是 Caddy 唯一的放行判据，每个页面、每个 API、每次 WebSocket 建连都会经过它，不存在漏计。但它是“请求级”的，所以不能只靠它判断活跃（见下）。

## 四条判据，缺一不可

控制面每 `CONSOLE_SCAN_MS` 扫一遍注册表里的所有团队：

| # | 判据 | 作用 | 不加会怎样 |
| --- | --- | --- | --- |
| ① | 距上次 HTTP 请求 > `CONSOLE_IDLE_MS` | 主判据 | 永远不会睡 |
| ② | 容器 CPU < `CONSOLE_CPU_MAX` | **防误杀** | agent 在后台连跑 10 分钟工具、一次请求都没有 → 会话被腰斩 |
| ③ | 容器已运行 > `CONSOLE_MIN_UPTIME_MS` | **防抖动** | 刚唤醒、用户看两眼关掉，5 分钟后又睡，来回摆 |
| ④ | 不在创建 / 唤醒过程中 | 防冲突 | 新建的团队刚起来就被睡掉 |

②最容易漏。`verify` 只看 HTTP，而 WebSocket 长连接建立之后几小时都不产生新请求，`lastSeen` 会“变旧”得很快；agent 跑工具时 CPU 不会低，这是唯一便宜且可靠的第二判据。

实测（本地 3 个实例，把阈值调到 15 秒）：

```
console: 休眠 team-a（idle 1min）
console: 休眠 team-b（idle 1min）
console: 休眠 team-c（idle 2min）
console: 唤醒 team-c（当前 exited）
console: team-c 的 HTTP 已静默但 CPU 为 100.54%，判断仍在干活，不睡
console: team-c 的 HTTP 已静默但 CPU 为 100.43%，判断仍在干活，不睡
```

第三、四行是同一个实例的两面：HTTP 已静默，但容器里有人在跑活，所以不睡。这就是判据 ② 存在的意义。

## 实测数据

| 项 | 数值 |
| --- | --- |
| 休眠释放的内存 | 234MB → 0（edge+auth 仍占 25MB） |
| 唤醒到健康 | **5.8 秒**（含 token 同步） |
| 用户看到「正在唤醒」到进入 | 2~4 秒（2 秒刷新一次） |
| 唤醒后是否需要重新登录 | **不需要**，旧 Cookie 继续有效 |
| 唤醒后 token | 变了（`yd8nAnzAV6` → `7crbGJ3Lbv`），由 `team-up.sh wake` 自动同步 |

## 三个必须知道的约束

**1. 只能停 dsh，不能整体 down。** 入口和账号服务是接住唤醒请求的那一层。整体停掉之后，访问者拿到的是 Caddy 的裸 502 空白页，没人能把他叫回来。

**2. 唤醒用 `start`，不能用 `up`。** `up` 会按 `compose.yaml` 的默认变量重建（`EDGE_PORT=8080`），端口和 `DSH_PUBLIC_URL` 就和实例登记的不一致，表现是“能登录但 /api 全 403”。`team-up.sh wake` 已经固定用 `start`。

**3. 控制面挂了会退化成旧行为。** 账号服务探测失败时 fail-open（当作醒着），此时睡着的实例会返回 502。这是有意的取舍：休眠只是优化，不该因为它把所有人挡在门外。

**4. 睡下的头 2 秒有一个小窗口。** 账号服务把「醒着」缓存了 2 秒（否则一次页面加载要问控制面几十次），所以实例刚睡下的 2 秒内进来的请求会穿过 verify，撞上 Caddy 的裸 502；刷新一次就进入唤醒页。自动休眠发生在闲置 30 分钟之后，那个时刻不会有人在用，所以这个窗口只在你手动 `make sleep` 时可能撞上。

## 云上（K8s）怎么落

本地这套是「edge/auth 常驻 + dsh 单容器 stop」。云上等价形态是：

| 本地 | K8s |
| --- | --- |
| `docker stop dsh-<team>-dsh-1` | `kubectl scale deploy/dsh-<team> --replicas=0` |
| `docker start` + 等 healthy | `scale --replicas=1` + 等 readiness |
| 账号服务常驻接住唤醒 | 账号服务必须常驻，**标准 Ingress 不会唤醒** |

注意最后一条：`replicas: 0` 之后 Service 没有 endpoint，Ingress 只会返回 503，**没有任何进程能接住唤醒请求**。所以要么保留账号服务常驻并由它调 scale，要么用 Knative 那类 activator。本地这套结构（入口常驻、只停本体）在上云后反而是对的形状。

## 归档包去哪了：对象层

归档是唯一会 `down -v` 的动作，所以它打出来的 tar **就是全库唯一副本**。这份副本以前落在控制面自己的磁盘
（`deploy/orchestrator/archives/`），机器坏掉就没了；现在统一走 `deploy/orchestrator/objects.mjs` 的对象层。

```
team-up.sh archive <team>            # 停 dsh → tar 卷 → down -v → 打印 tar 路径
  ↓  tar 落到 archives/.staging/（暂存，失败重试不与旧残包混淆）
storeArchive(file, team)             # runtime.mjs
  ↓  putFile → sha256 流式计算 → 移入 objects/archives/<team>/<dd>/<sha256>
accounts.json teams[<team>].archived = { at, key, digest, bytes, reason }
```

- **key 是内容寻址的**：`archives/<team>/<sha256>`，落盘时在 digest 前插两位分片。同一份内容重复归档幂等，
  不会出现第二份副本。
- **`putFile` 是「移入」不是「复制」**：成功后暂存目录里的 tar 就没了，省一次整包拷贝。
- **恢复两种来源都认**：新记录按 `key` 取（`materialize` 到 `archives/.restore-*` 临时文件，用完即删）；
  升级前的老记录只有 `file`，仍按本机路径恢复——不认老记录等于让已归档的团队永久回不来。
- **上传失败不丢数据**：`team-up.sh` 已经把卷删了，此时上传若失败，tar 会被搬到 `archives/` 并按旧格式记账，
  返回里带 `degraded` 原因。这条只允许「换位置」，不允许「删掉」。

实测（临时团队 `e2e`，跑完已清理）：归档 2 015 239 字节 → 对象键
`archives/e2e/934c19a0…c75f04` → 按 key 恢复 → 容器 healthy、门户 200、卷里预置的标记文件 `marker-e2e-2099` 原样回来。
对象层本身的 26 条断言见 `make verify-objects`（含 2 MB 真实归档包往返、以及 `CONSOLE_OBJECTS_DIR` 指向
不可写路径时的降级分支）。

还没做的三档（`docs/ROADMAP.md` L3–L6）：`stop` 与 `down` 分成两档回收、容器缺失时自动重建、
对象层换 OSS 后端（只改 `objects.mjs` 的四个函数）、归档纳入 `workspace/`。
