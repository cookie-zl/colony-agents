# 数据模型（技能 / 连接器 / 分享 / 操作日志）

现在的配置是「一堆 JSON 文件 + 卷里的目录」，两套事实（文件是事实、`packages.json` 是旁注）会漂移。
这份文档把技能与连接器的全部状态收敛到一张 SQLite 里，**卷降级为缓存**，容器里可以什么都没有。

选 SQLite 而不是 Postgres：单机零运维、单文件可快照、事务和唯一约束齐全，够用。
换 Postgres 只需去掉 `AUTOINCREMENT` 改 `GENERATED ALWAYS AS IDENTITY`，其余 DDL 不用动。

> `teams` / `users` 暂不迁入。`accounts.json` 是以**单文件 bind mount** 挂进每个容器的（`deploy/compose/compose.yaml`），
> 换 inode 会让已运行容器的挂载点当场悬空。等那处契约改掉再迁，这张表里用 `team_id` 字符串引用，暂时不加外键。

## 1. 表一览

12 张表按角色分四类：**人员/组织**（谁属于谁）、**基础表**（包是什么）、**关系表**（谁装了什么）、
**状态/流水表**（发生过什么）。两个关系中心：`teams.id` 和 `market_items.id`：

```
team_members.team_id ──→ teams.id ←── team_skills.team_id
team_members.user_id ──→ users.id      team_mcps.team_id
                                       team_secrets.team_id
                                       market_tokens.team_id

market_current.item_id ──┐
team_skills.item_id    ──┼──→ market_items.id ──→ market_item_files.item_id
team_mcps.item_id      ──┤
shares.item_id         ──┘
```

| 表（Table） | 角色（Role） | 一行是什么（Row） | 谁写 | 谁读 |
| --- | --- | --- | --- | --- |
| `users` | 人员：账号基础表 | 一个可登录账号 | `migrate-accounts.mjs`（暂未接 auth） | auth 登录校验、成员列表 |
| `teams` | 组织：团队基础表 | 一个团队（= 一套独立实例） | 同上 + 控制面建团队 | 门户团队卡片、控制面注册表 |
| `team_members` | 人员 × 团队关系表 | 某人在某团队里的角色 | 同上 | 权限判断（`canManage`）、成员管理页 |
| `market_items` | 基础表：skill / 连接器 | 一个包的一个版本 | `upsertItem()` | `marketCatalog()`、`visibleSkills()`、`canMount()` |
| `market_item_files` | 基础表：包内容（替身对象存储） | 包内一个文件 | 发布时遍历包目录 | `/bundle` 打包、正文现算 |
| `team_skills` | 关系表：团队 × skill | 某团队装了某技能（锁版本 + 启停） | `mountSkill()`、`setSkillEnabled()`、`unmountSkill()` | `visibleSkills()`、管理页台账 |
| `team_mcps` | 关系表：团队 × 连接器 | 某团队装了某 MCP（带渲染指纹） | `mountMcp()`、`unmountMcp()` | 门户连接器列表、漂移对账 |
| `team_secrets` | 关系表：团队 × scope × key | 一个密钥（AES-GCM 密文） | `/secrets`（模型密钥已接，docs/18）；连接器 env 待接 | 网关每次请求现解密 |
| `market_tokens` | 关系表：团队 × 机器身份 | 一枚只读市场 token | `ensureMarketToken()` | `teamOfMarketToken()` |
| `market_current` | 状态表：发布指针 | 某包当前对外是哪一版 | `setCurrent()` | `installSkill()`（不带版本号时装哪版） |
| `shares` | 流水表 + 授权凭证 | 一次点对点投递及其状态 | `insertShare()`、`patchShare()` | `canMount()` 鉴权、门户收件箱 |
| `ops` | 流水表：操作日志 | 一次变更（谁 / 何时 / 对谁 / 做了什么） | `appendOp()` | 门户操作日志、排障 |

| --- | --- |
| `users` + `teams` + `team_members` | `accounts.json`（`users` / `teams` 两段） |
| `market_items` + `market_current` | `deploy/market/index.json` + `packages/` 目录 |
| `market_item_files` | 包目录里的散文件 |
| `team_skills` + `team_mcps` | `packages.json` 的 `skills` / `mcp` 段 + 卷里 `cordis.patch.yml` 的块 |
| `team_secrets` | 模型密钥（AES-GCM 密文，KEK 在 `secret.key`）；容器里只有网关 token，见 docs/18 |
| `shares` | `shares.json` |
| `ops` | `oplog.json` |
| `market_tokens` | `market-tokens.json` |

## 2. 人员与团队

三张表：`users`（用户基础表）、`teams`（团队基础信息表）、`team_members`（团队成员表）。

现在这些数据都在 `deploy/auth/accounts.json` 里，而且**同一段关系存了两份**：

```
users.alice.teams = ["team-a","team-b","team-c"]        ← 账号侧：我在哪些团队
teams["team-a"].roles = {alice:"owner", bob:"member"}   ← 团队侧：谁是成员、什么角色
```

这两份必须一致，否则权限判断会静默出错。auth 的 `teamRole()` 正是两边各取一半：

```js
if (!user.teams.includes(team)) return null                    // 只看账号侧
return roles[user] ?? (owner === user ? 'owner' : 'member')    // 只看团队侧
```

所以「`team-a.roles.alice='owner'` 但 `alice.teams` 里没有 `team-a`」会返回 `null`——
写在团队侧的角色完全无效，而两份数据看起来都正常。三张表就是把这份双重记录收敛成一份。

### 2.1 三张表

```sql
-- users · 用户基础表：一行 = 一个可登录账号（登录名即主键，账号本身没有独立 id）
CREATE TABLE users (
  id               TEXT PRIMARY KEY,              -- 登录名 'alice'
  display_name     TEXT NOT NULL,                 -- 'Alice'
  password_salt    TEXT NOT NULL,
  password_hash    TEXT NOT NULL,
  password_version INTEGER NOT NULL DEFAULT 0,    -- 改密后旧会话立即失效（原 pv 字段）
  is_admin         INTEGER NOT NULL DEFAULT 0,    -- 全局管理员：能建团队、能管所有团队
  status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','disabled')),
  created_at       TEXT NOT NULL,
  updated_at       TEXT NOT NULL,
  last_login_at    TEXT
);

-- teams · 团队基础信息表：一行 = 一个团队（= 一套独立实例 + 独立数据卷 + 独立入口）
CREATE TABLE teams (
  id          TEXT PRIMARY KEY,                   -- 'team-a'
  name        TEXT NOT NULL,                      -- '研发组'
  description TEXT,
  host        TEXT,                               -- 入口 'team-a.localhost'
  port        INTEGER,                            -- 实例端口 8080
  node_id     TEXT,                               -- 落在哪个节点，对应 nodes.json 的 id
  status      TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','sleeping','archived')),
  created_by  TEXT REFERENCES users (id),
  created_at  TEXT NOT NULL,
  archived_at TEXT
);

-- team_members · 团队成员表：一行 = 某人在某团队里的角色；人员与团队的唯一关系源
CREATE TABLE team_members (
  team_id    TEXT NOT NULL REFERENCES teams (id),
  user_id    TEXT NOT NULL REFERENCES users (id),
  role       TEXT NOT NULL CHECK (role IN ('owner','member')),
  joined_at  TEXT NOT NULL,
  invited_by TEXT REFERENCES users (id),
  PRIMARY KEY (team_id, user_id)
);

CREATE INDEX idx_team_members_user ON team_members (user_id);
```

三个决定：

| 决定（Decision） | 原因（Why） |
|---|---|
| `teams` **不存 owner 列** | owner 就是 `team_members` 里 `role='owner'` 的行。存一列等于第三次记同一件事，且和 `roles{}` 一样会漂移。现在 `accounts.json` 的 `owner` 只是「roles 缺失时的兜底」，有了唯一关系源就不需要兜底 |
| `users.id` 就是登录名 | 现有注册表 `users` 是个以用户名为键的对象，账号本身没有独立 id；再造一个 uuid 会让所有 `installed_by` / `ops.by` 对不上 |
| 一个团队**允许多个 owner** | 现有 `roles{}` 本来就能写多个 owner，auth 的 `canManage()` 也是「角色是 owner 就能管」。不引入「唯一 owner」这个新约束 |

### 2.2 迁移规则：成员关系以 `user.teams[]` 为准

不是随便挑一个来源，而是照抄 `teamRole()` 的实际语义：

```
对每个 user：
  对 user.teams 里的每个 teamId：
     role = team.roles[user] ?? (team.owner === user ? 'owner' : 'member')
     写入 team_members

反向检查：team.roles 里有、但 user.teams[] 里没有的人
   → 按 auth 判定此人无权限，不写入，只报警
```

`migrate-accounts.mjs` 就是按这个跑的，真实数据结果：

```
用户 4 个：alice(admin, pv=2) / bob / carol / dave
团队 3 个：team-a 研发组(owner=alice, :8080) / team-b 产品组(owner=carol, :8081) / team-c 数据组(owner=alice, :8083)
成员关系 5 条：
  team-a alice owner    team-a bob member
  team-b alice member   team-b carol owner
  team-c alice owner
来源统计：roles 显式 5 条 · 由 owner 推导 0 条 · 缺省 member 0 条
对账：孤儿 0 · 无 owner 团队 0 · team_skills 悬空团队 0
```

两个字段是推导出来的，文档里标注清楚，不假装是原始值：

| 字段 | 来源 | 说明 |
|---|---|---|
| `users.created_at` / `teams.created_at` | `accounts.json` 的 mtime（team-c 例外，它有 `createdAt`） | 注册表里没记账号创建时间，只能这样兜底；输出里每条都带 `[由文件 mtime 推导]` 标记 |
| `teams.node_id` | 留 `NULL` | `nodes.json` 现在只有一个 `local`，但「唯一节点」不等于「这个团队用的就是它」，不猜 |

### 2.3 查「一个团队用了哪些 skill、开了哪些」

这是最常被问的一句，三张表串起来：

```sql
-- ① 某团队的技能清单 + 成员数（admin 视角一屏看完）
SELECT t.id            AS team_id,
       t.name          AS team_name,
       (SELECT COUNT(*) FROM team_members m WHERE m.team_id = t.id)                       AS members,
       (SELECT COUNT(*) FROM team_skills  s WHERE s.team_id = t.id)                       AS skills_total,
       (SELECT COUNT(*) FROM team_skills  s WHERE s.team_id = t.id AND s.enabled = 1)     AS skills_on
FROM teams t
WHERE t.id = 'team-a';

-- ② 某团队开了哪些技能，带描述（模型实际看到的那份）
SELECT s.name, s.version, s.source, s.source_team, i.description
FROM team_skills s
JOIN market_items i ON i.id = s.item_id
JOIN teams t       ON t.id = s.team_id
WHERE s.team_id = 'team-a' AND s.enabled = 1;

-- ③ 某人能管哪些团队（owner 或全局管理员）
SELECT t.id, t.name, m.role
FROM team_members m
JOIN teams t ON t.id = m.team_id
WHERE m.user_id = 'alice'
  AND (m.role = 'owner' OR (SELECT is_admin FROM users WHERE id = 'alice') = 1);

-- ④ 某团队有哪些人、各自什么角色
SELECT u.id, u.display_name, m.role, m.joined_at
FROM team_members m
JOIN users u ON u.id = m.user_id
WHERE m.team_id = 'team-a'
ORDER BY CASE m.role WHEN 'owner' THEN 0 ELSE 1 END, u.id;
```

真实数据跑出来的结果：

```
① team-a 研发组 | 成员 2 | 技能 装了2 开着2
   team-b 产品组 | 成员 2 | 技能 装了1 开着1
   team-c 数据组 | 成员 1 | 技能 装了2 开着2

② team-a 开着：ad-report-audit v1.1.0（market）· hologres-query v1.0.0（market）

③ alice 能管：team-a（owner）· team-b（member，但她是全局 admin）· team-c（owner）
   ↑ role 列是「她在该团队里的角色」，不是「能不能管」——admin 身份会覆盖 member

④ team-a：alice(owner) · bob(member)
```

### 2.4 为什么 `team_skills.team_id` 还没加外键

`teams` 表现在才有，而 `team_skills` / `team_mcps` / `team_secrets` / `market_tokens` 里的
`team_id` 一直是裸字符串。补外键在 SQLite 里要**整表重建**（`ALTER TABLE ADD CONSTRAINT` 不支持），
而且必须先保证历史 `team_id` 全部能在 `teams` 里找到——迁移脚本已经把这条对账跑通了（0 行悬空）。

顺序是：先让 `teams` 成为事实源、切换读取，再重建加外键。反过来的话，团队被归档那一刻
就会因为外键约束删不掉，生命周期回收直接卡住。

### 2.5 现在**不能**切换读取的原因

`accounts.json` 是以**单个文件** bind mount 挂进每个容器的（`deploy/compose/compose.yaml`）：

```yaml
- ./accounts.json:/data/accounts.json
```

`auth/server.mjs` 的写入方式是「写临时文件再 `copyFileSync` 覆盖目标」——single-file bind mount
换 inode 会让**已运行容器的挂载点当场悬空**，容器里读到的还是旧内容，直到重启。

所以切换必须是成套的三步，缺一步就掉线：

1. mount 改成目录（`./accounts:/data/`），或让 auth 改走控制面 API；
2. `auth/server.mjs` 的 `accounts()` 改成查表（现在是按 mtime 缓存读文件）；
3. 控制面的 `registry()` 也改成查 `teams` 表（它现在直接读 `accounts.json`）。

在这一步做完之前，三张表是**影子数据**：`migrate-accounts.mjs` 每次跑都把文件里的现状同步过来，
但业务读写仍然是文件。这样风险最低——文件是真源，表可随时重建，不会出现两边各写一半。

## 3. 市场

```sql
-- market_items · skill/连接器基础表（市场包元数据）：一行 = 一个包的一个版本，只存索引不存正文
CREATE TABLE market_items (
  id           TEXT PRIMARY KEY,              -- 'skill:hologres-query@1.0.0'
  kind         TEXT NOT NULL CHECK (kind IN ('skill','mcp')),
  name         TEXT NOT NULL,                 -- kebab-case，模型看到的名字
  version      TEXT NOT NULL,                 -- semver
  title        TEXT NOT NULL,                 -- 给人看的
  description  TEXT NOT NULL,                 -- 给模型看的路由摘要，进 <available_skills>
  when_to_use  TEXT,                          -- 技能专用：什么时候该用
  content      TEXT,                          -- 技能：SKILL.md 正文（frontmatter 已剥离）
                                              -- [P0 删除] 内容只留 market_item_files 一份，见 docs/13 §3.1
  config       TEXT,                          -- 连接器：JSON {command,args,env:[{key,required,desc}]}
  digest       TEXT NOT NULL,                 -- sha256(kind|name|version|content|config)；P0 起去掉 content
  rank         INTEGER NOT NULL DEFAULT 550,  -- 和团队本地同名技能撞车时谁赢：数字小的赢（市场内名字已唯一）
  visibility   TEXT NOT NULL CHECK (visibility IN ('public','private')),
  owner_team   TEXT NOT NULL DEFAULT '_system', -- 归属团队；内置包用保留值 '_system'
  status       TEXT NOT NULL CHECK (status IN ('draft','published','deprecated')),
  created_by   TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  published_at TEXT,
  UNIQUE (kind, name, version)
);

-- market_current · 市场发布指针表：一行 = 一个包当前对外发布的那一版
CREATE TABLE market_current (
  kind     TEXT NOT NULL,
  name     TEXT NOT NULL,
  item_id  TEXT NOT NULL REFERENCES market_items(id),
  updated_at TEXT NOT NULL,
  PRIMARY KEY (kind, name)
);

-- market_item_files · skill 包内容表（暂时扮演对象存储）：一行 = 包内一个文件，PK 即逻辑对象键
CREATE TABLE market_item_files (
  item_id    TEXT NOT NULL REFERENCES market_items(id),
  path       TEXT NOT NULL,                   -- 相对路径，如 'references/sql-style.md'
  size       INTEGER NOT NULL,
  sha256     TEXT NOT NULL,                   -- 单文件哈希，解包后逐条校验
  mime       TEXT NOT NULL DEFAULT 'application/octet-stream',
  executable INTEGER NOT NULL DEFAULT 0,      -- scripts/** 还原成 0755
  storage    TEXT NOT NULL CHECK (storage IN ('db','oss')),
  content    BLOB,                            -- storage=db 时的字节
  object_key TEXT,                            -- storage=oss 时才有值
  PRIMARY KEY (item_id, path)
);
```

`market_items` 另有三列与分发相关（`bundle_key` / `bundle_size` / `pending_oss`），
定义见 `docs/13` 第 3.1 节——它们描述「整包在对象存储里的位置」，不属于本文件讨论的
归属 / 版本 / 授权关系。

**历史版本必须留着。** 已安装的团队锁在 `item_id` 上，老会话按版本拉正文（见第 4 节例子 B）。
只存当前版本会让「1.0.0 的会话」在升级后 404。

## 4. 团队已装

```sql
-- team_skills · 团队×skill 安装关系表：一行 = 某团队装了某技能（锁版本 + 启停）
CREATE TABLE team_skills (
  team_id     TEXT NOT NULL,
  name        TEXT NOT NULL,
  item_id     TEXT NOT NULL REFERENCES market_items(id),  -- 锁死版本（真正的事实）
  version     TEXT NOT NULL,                  -- 冗余自 item_id，为的是不 JOIN 就能读
  enabled     INTEGER NOT NULL DEFAULT 0,     -- 装了 ≠ 启用；默认关闭
  source      TEXT NOT NULL CHECK (source IN ('market','share','manual')),
  source_team TEXT,                           -- source='share' 时记来源团队
  share_id    TEXT,                           -- 指向 shares.id
  installed_by TEXT NOT NULL,
  installed_at TEXT NOT NULL,
  enabled_by   TEXT,
  enabled_at   TEXT,
  PRIMARY KEY (team_id, name)
);

-- team_mcps · 团队×连接器安装关系表：一行 = 某团队装了某 MCP（带渲染指纹）
CREATE TABLE team_mcps (
  team_id     TEXT NOT NULL,
  name        TEXT NOT NULL,
  item_id     TEXT NOT NULL REFERENCES market_items(id),
  enabled     INTEGER NOT NULL DEFAULT 0,
  source      TEXT NOT NULL CHECK (source IN ('market','share','manual')),
  source_team TEXT,
  share_id    TEXT,
  config_override TEXT,                       -- JSON，覆盖市场默认 args/command
  rendered_digest TEXT,                       -- 已写进 cordis.patch.yml 的块指纹，用于查漂移
  installed_by TEXT NOT NULL,
  installed_at TEXT NOT NULL,
  enabled_by   TEXT,
  enabled_at   TEXT,
  PRIMARY KEY (team_id, name)
);

-- team_secrets · 连接器凭证明细表：一行 = 某团队某连接器的一个 env key（密文）
CREATE TABLE team_secrets (
  id         TEXT PRIMARY KEY,
  team_id    TEXT NOT NULL,
  scope      TEXT NOT NULL,                   -- 'mcp:github'
  key        TEXT NOT NULL,                   -- 'GITHUB_TOKEN'
  ciphertext BLOB NOT NULL,                   -- 信封加密：DEK 加密文，DEK 由主密钥包住
  updated_at TEXT NOT NULL,
  UNIQUE (team_id, scope, key)
);
```

### version 为什么存两份

`item_id` 里其实已经含版本（`skill:hologres-query@1.0.0`），再存一列 `version` 是故意的冗余：

- 排障时「team-a 现在挂的是 1.0.0 还是 1.1.0」不该逼人去拼字符串；
- `make packages` 这类输出不需要 JOIN；
- 账号服务、审计脚本读这张表时，不该为了一个版本号引入对市场表的依赖。

一致性由写入端保证：`item_id` 和 `version` **在同一事务里一起写**，永不单独改其中一个。
再加一条对账 SQL 兜底，必须返回 0 行：

```sql
SELECT t.team_id, t.name, t.version, t.item_id
FROM team_skills t JOIN market_items m ON m.id = t.item_id
WHERE m.version <> t.version;
```

### 历史挂载怎么回溯

`team_skills` 只保留**当前挂载**，升级是原地 `UPDATE`，历史被覆盖。要回答
「上个月那个报错是什么版本」靠两处：

1. `market_items` 里**所有版本的行都在**（`UNIQUE(kind,name,version)`，从来不删），内容可完整还原；
2. `ops` 里记一条 `upgrade`，`detail` 写明 `1.0.0 → 1.1.0`，`at` 是时间点。

两者合起来就能拼出「某团队在某段时间用的是哪个版本」。不单开一张「挂载历史表」——
那等于把 `ops` 再写一遍，而且历史表一旦被当成事实来源，就会有人去改它。

## 5. 可见性与冲突：使用者只看到自己团队的

这是整套设计里唯一需要写死的一条规则：

```
模型可见集合 = team_skills WHERE team_id = ? AND enabled = 1
                              JOIN market_items ON item_id
```

- **市场不进模型目录。** 它是「可安装的清单」，只出现在管理界面里。
- **团队身份由 token 推导**，不接受请求里的 `team` 参数——否则改一个 query 就能读别的团队的私有技能。
- **同名不可能冲突**：`PRIMARY KEY (team_id, name)` 保证一个团队一个名字只有一行。升级是 `UPDATE item_id`，不是插新行。
- **和手工放进卷里的技能撞名**：市场 `rank = 550`，本地来源（project 100 / custom 300 / user 400-500）都比它小，**本地赢**。控制面检测到这种撞名时在界面上标出来，但不阻止。

### 为什么要 JOIN 市场表

`team_skills` 只回答「谁装了什么、开没开」，**它没有 `description` 和 `content`**——那两个字段在 `market_items` 里。而模型目录恰恰需要 `description`（做路由）和正文（调起时用），所以必须回表取。

| 想回答的问题 | 需要的表 | 写法 |
| --- | --- | --- |
| team-a 装了哪些、开了几个 | 只要 `team_skills` | `SELECT name, enabled FROM team_skills WHERE team_id='team-a'` |
| 模型该看到哪些技能（带描述） | 两张都要 | `JOIN market_items ON m.id = t.item_id` |
| 某个技能的正文 | `team_skills` 取 `item_id` → `market_items.content` | 按 `id` 二次查，或同一个 JOIN |

不采用「把 description/content 冗余到 team_skills」的做法：那等于把市场的内容复制一份到团队侧，
市场改一版就得同步 N 个团队，漂移立刻回来——这正是现在 `packages.json` 和卷里目录对不上的原因。
`team_skills` 里唯一冗余的列是 `name`，因为主键需要「同名只一行」这个约束，
而 `item_id` 每个版本都不同，拿它做唯一键拦不住同名重复安装。

内连接还顺带兜住一类脏数据：`team_skills` 引用的 `item_id` 如果被删（理论上不该发生），
这行会自动从模型目录里消失，而不是让 dsh 拿到一个空内容。排查时用 `LEFT JOIN` 找孤儿行：

```sql
SELECT t.team_id, t.name, t.item_id FROM team_skills t
LEFT JOIN market_items m ON m.id = t.item_id WHERE m.id IS NULL;
```

注意**不要**在查询里加 `m.status = 'published'`：技能下架（`deprecated`）不该让已装的团队当场失去它，
只影响「新团队能不能装」。这个判断由安装路径做，不由读路径做。

### 例子 A：装一个技能（安装 ≠ 启用）

```sql
-- 插入时就要把版本写死：item_id 和 version 必须来自同一行 market_items
INSERT INTO team_skills (team_id, name, item_id, version, enabled, source, installed_by, installed_at)
VALUES ('team-c', 'hologres-query', 'skill:hologres-query@1.0.0', '1.0.0', 0, 'market', 'alice', '2026-11-04T00:10:00Z');
```

`enabled = 0` → 模型目录里看不到它，但团队管理员能看到「已安装，未启用」。
和分享的语义一致：分享过来默认关闭，接收方点启用才生效。

### 例子 B：市场升级到 1.1.0，老会话不受影响

```sql
-- 市场侧：当前发布指向新版本（一行 UPDATE）。1.0.0 的 market_items 行原样留着
UPDATE market_current SET item_id = 'skill:hologres-query@1.1.0', updated_at = ...
WHERE kind='skill' AND name='hologres-query';

-- 团队侧：不动。team_skills.item_id 还锁在 skill:hologres-query@1.0.0
```

老会话继续用 1.0.0，新会话拉到 1.1.0。**不会出现「同一个会话中途换版」**。
要升级团队，是显式的两步（同一事务）：

```sql
UPDATE team_skills
   SET item_id = 'skill:hologres-query@1.1.0', version = '1.1.0'
 WHERE team_id='team-a' AND name='hologres-query';
INSERT INTO ops (at, team, action, kind, name, by, detail)
VALUES ('2026-11-04T00:30:00Z','team-a','upgrade','skill','hologres-query','alice','1.0.0 → 1.1.0');
```

### 归属：每个包都有主人

`owner_team` 是 **NOT NULL**，没有「无主的包」。内置的 `hologres-query` 归 `_system` 这个保留值，
团队发布的一律归发布它的团队。**即使后来公开了，归属也不变**——公开只是「谁能看见」变了，
「谁负责维护这个包」没变。所以：

```sql
-- 发布到市场：只改可见性，不动归属
UPDATE market_items SET visibility='public', status='published', published_at=...
WHERE id='skill:ad-report-audit@1.1.0' AND owner_team='team-a';
```

团队被回收时，归属的处理分两种：

| 包的可见性 | 处理 | 原因 |
| --- | --- | --- |
| `private` | 随团队一起 `deprecated`，内容保留 | 只有它自己用得到，别人看不见 |
| `public` | **保留可用**，只在 `ops` 里记「owner 已回收」 | 别的团队可能已经装了，删掉会让人当场失去技能 |

### 关联只用 id，名字只做业务唯一

库内所有跨表引用都是 `item_id`，指向 `market_items.id`（= `kind:name@version`）。名字**不是**关联键：

| 表 | 关联键 | `name` / `version` 是什么 |
| --- | --- | --- |
| `team_skills` / `team_mcps` | `item_id`（外键） | 冗余快照：不 JOIN 就能读、能按名字查 |
| `shares` | `item_id`（外键） | 快照：投递那一刻的版本，包改名/下架后流水仍可读 |
| `market_current` | `item_id`（外键） | `(kind,name)` 只是解析入口 |
| `ops` | 无 | 纯快照，**故意不加外键**：包删了，日志也得留着 |

`name` 唯一是**业务规则**，不是关联规则：`(kind, name)` 先到先得，被某个团队认领后别人不能再发这个名字。
执行点只有一个——`db.mjs` 的 `assertNameAvailable()`，由 `upsertItem()` 调用，违反返回 409：

```
team-b 发布 skill:alpha（team-a 已占用） → 409「市场里已经有 team-a 发布的 skill「alpha」…」
team-a 发布 skill:alpha@1.1.0            → 允许（自己的名字，发新版本）
skill:alpha 与 mcp:alpha 同名            → 允许（kind 不同，是两个名字空间）
```

为什么要有这条业务规则：dsh 侧一个名字只对应一个技能（`ctx.skills.get(name)`），同名并存没法向模型解释。
反过来，有了这条规则，`market_current` 就不需要 `owner` 列——名字的唯一归属就是 owner，`current` 指针不可能被别的团队抢走。

为什么关联**必须**是 id：授权判断靠 `shares`，如果按 `kind+name+version` 匹配，那么「改名后复用」
或「同名同版本的另一个包」都能靠一条旧分享白拿授权。三元组是快照，认它等于认字符串。

代价是改名成本：两个团队都想叫 `report` 时，后者只能叫 `report-b`，或者让对方分享。这一条是产品选择，
不是实现限制——要放开就把 `assertNameAvailable` 从 `upsertItem` 里摘掉即可，其余逻辑不用动。

### 发布到市场 ≠ 点对点分享

两件事都会让「别的团队拿到这个包」，但走的是不同表、不同语义：

| | 发布（publish） | 分享（share） |
| --- | --- | --- |
| 作用于 | `market_items.visibility` | 新建一行 `shares` |
| 谁能看到 | 所有团队（在「可安装」列表里） | **只有指定团队**（在「待接收」里） |
| 对方是否直接生效 | 否，要自己装 | 否，要自己点启用（默认关闭） |
| 版本 | 始终跟 `market_current` 走 | **锁定投递时的版本**（`shares.version`） |
| 撤销 | 改回 `private` / `deprecated` | 接收方 `reject`，或从团队卸载 |

分享锁版本这点很重要：team-a 在 1.0.0 时分享给 team-b，team-a 后来升到 1.1.0，
team-b 收到的仍是 1.0.0。要拿新版就重新分享一次。这避免了「我分享时是这个版本，
对方启用时变成另一个版本」——那会让 `shares.version` 这个字段彻底失去意义。

锁的具体形式是 `shares.item_id`（`skill:xxx@1.0.0`），不是版本字符串。授权判断、启用时挂载
都认它；`name` / `version` 只是给人看和给审计用的快照。市场外的连接器（手写块分享）没有
对应的 `market_items` 行，`item_id` 为空，启用时按块内容渲染而不走 `mountMcp`。

## 6. 分享与操作日志

```sql
-- shares · 分享流水表（同时是授权凭证）：一行 = 一次点对点投递及其状态
CREATE TABLE shares (
  id           TEXT PRIMARY KEY,
  from_team    TEXT NOT NULL,
  to_team      TEXT NOT NULL,
  kind         TEXT NOT NULL CHECK (kind IN ('skill','mcp')),
  item_id      TEXT REFERENCES market_items(id),  -- 关联键：授权按它判
  name         TEXT NOT NULL,                    -- 快照，仅展示/审计
  version      TEXT NOT NULL,                    -- 快照：投递时锁定的版本
  status       TEXT NOT NULL CHECK (status IN ('pending','enabled','rejected')),
  note         TEXT,                          -- 发起人写的备注，接收方能看到
  env_keys     TEXT,                          -- JSON array：凭证键名（值不传）
  by           TEXT NOT NULL,
  at           TEXT NOT NULL,
  enabled_at   TEXT, enabled_by TEXT,
  rejected_at  TEXT, rejected_by TEXT
);

-- ops · 操作日志表：一行 = 一次变更（谁 / 何时 / 对谁 / 做了什么）
CREATE TABLE ops (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  at     TEXT NOT NULL,
  team   TEXT NOT NULL,
  action TEXT NOT NULL,                       -- install/uninstall/enable/disable/publish/share/reject
  kind   TEXT,
  name   TEXT,
  by     TEXT,
  note   TEXT,
  detail TEXT
);
CREATE INDEX ops_team_at ON ops(team, at DESC);

-- market_tokens · 机器身份表：一行 = 一个团队的只读市场 token
CREATE TABLE market_tokens (
  team_id    TEXT PRIMARY KEY,
  token      TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL,
  revoked_at TEXT
);
```

> `market_tokens` 不属于「分享」也不属于「操作日志」，单独放在这里是因为它和登录态无关：
> 它是**机器身份**——容器起来时拿它证明「我是 team-a」，用完就扔在 env 里，不参与任何用户会话。

## 7. 一个技能进表需要哪些字段

以 `hologres-query` 的 `SKILL.md` frontmatter 为例：

```yaml
---
name: hologres-query
description: 在 Hologres 上写查询的规范：先 EXPLAIN 再跑数…
whenToUse: 需要查 Hologres、排查慢查询、或从 jsonb 字段里取广告报表指标时使用。
---
# Hologres 查询规范
…
```

| 类别 | 字段 | 来源 |
| --- | --- | --- |
| **标识** | `id`、`kind`、`name`、`version` | `name` 取自 frontmatter；`version` 取自发布动作；`id` 自动拼 |
| **路由**（模型看得见） | `description`、`when_to_use`、`rank` | frontmatter 的 `description` / `whenToUse`；`rank` 默认 550 |
| **内容** | `content`（正文）、`digest` | 文件正文（frontmatter 去掉）；`digest` 自动算 |
| **附件** | `market_item_files` 若干行 | 包里的 `references/` 等 |
| **权限** | `visibility`、`owner_team` | private 时必须有 `owner_team`；public 为空 |
| **生命周期** | `status`、`created_by`、`created_at`、`published_at` | 发布动作写入 |
| **兼容性** | （预留）`min_dsh_version` | 现在恒为空，等真需要再加列 |

必填 8 项：`kind / name / version / title / description / content(技能)或 config(连接器) / visibility / status`。
`digest`、`id`、`created_at` 全部由写入逻辑自动生成，**不接受调用方传**。

## 9. 切换步骤（一次性，不做双写）

保留两套写入是自找麻烦：两份事实必然漂移，而且双写期一长就没人敢删旧路径。
所以直接切，用「快照 + 停写窗口」控制风险，而不是用「双写」换时间。

1. **停控制面**：`make console` 是唯一写入方，停掉它就没有并发写入。
2. **建库灌数据**：`make db-init` 建表并导入现有 JSON（见第 7 节映射）。原文件**不改动**，作为回退基线。
3. **校验**：跑几条对账 SQL，和现有 `make packages` / `make shares` 的人工认知比对：
   ```sql
   -- 每个团队装了什么、启用了几个
   SELECT team_id, COUNT(*) AS total, SUM(enabled) AS enabled FROM team_skills GROUP BY team_id;
   -- 引用的 item 是否都存在（应为 0 行）
   SELECT t.team_id, t.name FROM team_skills t
   LEFT JOIN market_items m ON m.id = t.item_id WHERE m.id IS NULL;
   ```
4. **切写路径**：`market.mjs` 的 install / uninstall / publish / share 全部改读写库；
   技能不再 `docker exec` 写卷，连接器仍渲染 `cordis.patch.yml`（那是进程，绕不开）。
5. **删旧路径**：删掉 `packages.json` / `shares.json` / `oplog.json` 的读写代码，文件留在原地下线，
   `.gitignore` 保留条目以免误提交。确认一周无异常后删除文件本体。

回退方式：把第 2 步之前的 `deploy/orchestrator/backups/` 快照 + 原始 JSON 放回去，
代码切回上一个镜像即可。**不做运行时双写，也不做在线灰度**——单机平台，停 2 分钟切换比长期双源便宜。

唯一保留的兼容点：卷里的 `skills/` 目录仍然存在，供团队手工放私有技能。
市场来源的技能不再写进去，两者在 dsh 里靠 `rank` 共存（见第 4 节）。

## 11. 设计复核（对照 WorkBuddy 的实现）

### 10.1 参考实现长什么样

从本机 `~/.workbuddy/` 实测出来的结构，不是推测：

| 维度（Aspect） | WorkBuddy 的做法 | 证据文件 |
|---|---|---|
| 包身份 | `name@marketplace`，**市场是主键的一部分** | `plugins/installed_plugins.json` 的键 |
| 安装记录 | 一个名字对应**数组**，按 `scope`（`user` / `project`）各一条：`{scope, installPath, version, installedAt, lastUpdated}` | 同上 |
| 版本共存 | 版本落在路径上：`plugins/cache/<marketplace>/<name>/<version>/`，多版本并存 | `plugins/cache/*/*/*` |
| 启停 | **不在安装记录里**，单独一张映射：`settings.json.enabledPlugins = { "name@marketplace": true\|false }`，缺省即默认 | `settings.json` |
| 市场 | `known_marketplaces.json`：`source` / `installLocation` / `autoUpdate` / `lastUpdated` / `isBuiltIn`；包内 `plugin.json` 带 `version` / `author` / `license` | 同上 + `marketplaces/*/plugins/*/.codebuddy-plugin/plugin.json` |
| 连接器凭据 | 单独文件，带**加密参数与校验值**：`{scheme:'aes-256-gcm', kdf:'hkdf-sha256', salt, userIdCheck, keyCheck}` + `envOverrides` | `connectors/*/connector-states.json`（`version: 4`） |
| 审计 | 按天 append-only JSONL，字段 `decision` / `category` / `eventType`，**从不裁剪** | `audit-log/2026-11-04.jsonl` |
| 表结构演进 | 编号迁移 + journal：`0000_...` → `0017_...` + `meta/_journal.json` | `.workbuddy-sqlite-migrations/` |

对到我们这版，差的不是「有没有表」，而是**四条结构性的东西**：包的命名空间、启停与安装分离后的落点、凭据的完整性校验、schema 演进机制。

### 10.2 问题清单

#### P0（越权 / 跨租户，必须修）

**P0-1 私有包可被任意团队 `install` 并读到正文。** 读侧 `visibleSkills` 是对的，但写侧 `mountSkill` 只校验「包存在」，不校验「你能不能装」。实测：

```
team-b 装 team-a 的私有 ad-report-audit@1.1.0 → 成功
skillBodyForTeam(team-b, ad-report-audit, 1.1.0) → 返回 717 字节正文
```

更严重的是可以接一条链：装进来 → `publishSkill` 把它发成自己的公开版 → 私有内容被洗成公开内容。**本轮已修**（见 10.5）。

**P0-2 `market_current` 没有 owner，发布同名包会抢走全局指针。** 主键是 `(kind, name)`，`publishSkill` 又没有归属校验，于是 team-b 发布自己的 `hologres-query@2.0.0` 之后：

```
team-a 目录里 hologres-query → 消失（当前版本指向 team-b 的私有包）
team-b 目录里 hologres-query → 2.0.0
```

一个团队可以凭一次发布，让全平台都看不到别人的包。**未修**。

**P0-3 分享会静默覆盖同名市场安装。** `team_skills` 主键 `(team_id, name)`，`enableShare` 走 `mountSkill` 的 UPSERT，于是「已从市场装了 X」被「收到分享 X」直接顶掉：原 `source` 被改写、版本被换、没有任何冲突记录，卸载后也不会恢复原来的市场安装。WorkBuddy 用 `name@marketplace` 规避了这一整类问题——同名不同源是两条独立记录。**未修**。

#### P1（语义错误 / 会慢慢劣化）

| # | 问题 | 实测/依据 | 后果 |
|---|---|---|---|
| P1-1 | `visibility` / `owner_team` / `rank` 挂在**版本行**上，不是包上 | 把当前版本的 `visibility` 改成 `private`，team-b 目录里整个包消失 | 发一个私有版本 = 让别的团队丢掉这个包；可见性是包属性，不该随版本变 |
| P1-2 | `marketRev` 只哈希 `name@version`，不含 `digest` | 同版本改正文后 `digest` 变了、`rev` 没变（`1705a2b45211` → `1705a2b45211`） | 在线会话永远看不到内容更新，要等进程重启 |
| P1-3 | `market_tokens` 存**明文**，主键 `team_id` | `token` 列直接是 `mt_team-a_...`；`ON CONFLICT DO UPDATE` 会连旧行一起覆盖 | 与注释「token 也需要轮换记录」自相矛盾；库泄露等于全平台 token 泄露 |
| P1-4 | 只有团队级一套权限，没有 scope 维度 | `team_skills` 主键 `(team_id, name)` | 将来要支持「只对我自己启用」，主键得改，等于重建表 |
| P1-5 | 连接器的 `enabled` 与「渲染进 patch」是两套状态 | `rendered_digest` 全库**从未被写入**（只有注释和建表语句提到） | 表说启用了、卷里没有，只能靠人肉发现 |

#### P2（约束缺失 / 运维债）

用真实写入探过一遍，这些「应该被拦」的写入目前全部被允许：

| 试写（Attempt） | 结果 |
|---|---|
| `team_skills.version='9.9.9'` 而 `item_id='skill:hologres-query@1.0.0'` | 允许（两份版本信息可以互相矛盾） |
| `kind='skill'` 但 `content` 为 NULL | 允许（技能没有正文） |
| `kind='mcp'` 但 `config` 为 NULL | 允许（连接器没有命令） |
| `share_id` 指向不存在的分享 | 允许（无外键，能留悬空引用） |
| `shares.status` 从 `rejected` 直接改 `enabled` | 允许（状态机只在代码里，DB 不设防） |
| `team_secrets` 缺 `created_by` / `key_check` | 允许（加密表建了但无法判断主密钥是否正确） |

另外三条：

- **没有 schema 演进机制**：`init-db.sql` 全是 `IF NOT EXISTS`，第二次改列时没有落脚点（对比 WorkBuddy 的 17 个编号迁移）。下一步任何字段调整都会卡在这里。
- **`ops` 不是审计**：全局只留 500 条、且用 `DELETE` 裁掉，一个活跃团队能把别人的历史挤掉；也没有 `(team, kind, name)` 索引，查「这个技能被谁动过」要全表扫。
- **整个库没有一处事务**：`grep BEGIN|COMMIT` 在 `deploy/orchestrator/*.mjs` 里 0 命中。`enableShare` 是「改分享状态 + 挂载 + 记日志」三步，任一步失败就留下半截状态。

### 10.3 目标结构

核心动作是**把「包」从「版本」里拆出来**，让 `market_current` 消失：

```sql
-- 新增：包本身。可见性、归属、rank、当前版本都在这一层
CREATE TABLE market_packages (
  kind            TEXT NOT NULL CHECK (kind IN ('skill','mcp')),
  name            TEXT NOT NULL,
  owner_team      TEXT NOT NULL,                 -- 首个发布者认领，别人不能抢
  visibility      TEXT NOT NULL CHECK (visibility IN ('public','private')),
  rank            INTEGER NOT NULL DEFAULT 550,
  status          TEXT NOT NULL CHECK (status IN ('draft','published','deprecated')),
  current_version TEXT NOT NULL,                 -- 取代整张 market_current
  created_by      TEXT NOT NULL,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  PRIMARY KEY (kind, name),
  FOREIGN KEY (kind, name, current_version) REFERENCES market_items (kind, name, version)
);

-- market_items 只留版本内容，删掉 owner_team / visibility / rank / status
-- market_current 整张删除
```

配套约束（SQLite **不支持** `ALTER TABLE ... ADD CONSTRAINT`，只能整表重建：建新表 → `INSERT ... SELECT` → 改名。所以要么趁现在数据只有几十行做掉，要么以后越拖越贵）：

```sql
-- 两份版本信息不许互相矛盾（team_skills / team_mcps 各一条）
CONSTRAINT v_match CHECK (item_id = 'skill:' || name || '@' || version)

-- kind 与内容互斥：技能必须有正文，连接器必须有命令
CHECK ((kind = 'skill' AND content IS NOT NULL AND config IS NULL)
    OR (kind = 'mcp'   AND config  IS NOT NULL))

-- 分享状态机 + 过期时间
CHECK (status IN ('pending','enabled','rejected','revoked'))
CHECK ((status = 'enabled') = (enabled_at IS NOT NULL))
expires_at TEXT

-- 凭据能验主密钥，token 不存明文
team_secrets: PRIMARY KEY (team_id, mcp_name, key), 加 key_check / cipher / kdf / created_by
market_tokens: id INTEGER PRIMARY KEY, token_hash TEXT UNIQUE, 加 last_used_at / expires_at / created_by
```

跨团队发布**已定**（方案 A 的简化版，不做 `market_packages` 拆表）：

| 方案（Option） | 规则 | 代价 | 状态 |
|---|---|---|---|
| **A：名字全局唯一** | `(kind,name)` 唯一，`owner_team` 认领后别人发布直接拒（409），提示「已被 team-a 占用，请改名或让对方分享」 | 同名分支要靠改名 | **已实现**：`assertNameAvailable()` |
| B：按所有者分命名空间 | 主键 `(owner_team, kind, name)`，模型侧靠 `rank` 竞争 | 模型会看到两个同名技能，`rank` 决定谁生效，容易解释不清 | 不采用 |

选 A 而不是 B 的直接理由：dsh 的 `ctx.skills.get(name)` 是按名字取技能的，B 方案在 dsh 侧根本无法表达。
既然名字在运行时就唯一，把它提前到市场层唯一是一次显式化，不是新增限制。

`market_packages` 拆表**暂不做**：拆表的收益是「可见性/归属从版本行挪到包行」，而名称唯一之后
`market_current` 里的每个 `(kind,name)` 天然只有一个 owner，多出来的那张表和 JOIN 换不到新能力。
等出现「一个包要按团队分别配 rank」这类需求时再拆，届时按 10.4 的顺序整表重建。

### 10.4 建议顺序

| 阶段 | 内容 | 为什么先做 | 状态 |
|---|---|---|---|
| S1 | P0-2 名称归属 + 关联统一到 `item_id` | 跨租户影响最大，且越晚改、历史数据越难迁 | ✅ 已完成 |
| S2 | 约束补齐 + 事务边界 | 纯 DDL + 包一层 `BEGIN IMMEDIATE`，不改业务逻辑 | 待做 |
| S3 | token 存 hash、`team_secrets` 加密与校验 | 上库前的安全底线 | 待做 |
| S4 | 迁移机制（`PRAGMA user_version` + `migrations/`） | 后面每一步都要用它 | 待做 |
| S5 | P0-3 冲突语义（同名分享 vs 市场安装） | 要产品决定：拒绝 / 并存 / 覆盖需显式确认 | 待做 |

### 10.5 本轮已修

**P0-1（授权）**：`db.mjs` 新增 `canMount()`，作为**写入侧唯一授权点**，`mountSkill` / `mountMcp` 都过它。三条放行路径：`public`、自己是 `owner`、有指向这个包的分享记录（只认记录，不认调用方传的 `source` 字段）。授权失败抛 `status: 403`，`console.mjs` 的兜底 catch 改为尊重 `error.status`——这类拒绝不是服务器故障，混进 500 会让错误率误报。

验证结果（真库，回滚后数据未变）：

```
team-b 装 team-a 私有包          → 403「是 team-a 的私有包，需要先由对方分享给你」
team-a 装自己的私有包            → 允许
team-b 装公开包                  → 允许
带有效 shareId 的启用            → 允许
伪造 shareId 硬闯                → 403
HTTP POST /market/install 越权   → 403（修复前 200 + 正文可读）
分享 → 启用 → 读正文 全链路      → 200
```

**P0-2（名称霸占 + 关联靠字符串）**：

- `shares` 加 `item_id` 外键，`canMount()` 从 `kind+name+version` 改成按 `item_id` 判授权。三元组从此只是快照。
  历史 13 条分享在 `ensureColumns()` 里一次性回填（幂等），市场外的连接器留空——**留空不伪造**。
- `db.mjs` 新增 `assertNameAvailable()`，由 `upsertItem()` 调用：`(kind,name)` 已被别的团队占用就抛 409。
  发布入口（`publishSkill` / `publishMcp`）不再各自校验，避免两处规则漂移。迁移脚本用 `force: true` 跳过
  （历史归属以原台账为准，冲突交给对账暴露）。
- `upsertItem()` 的 `ON CONFLICT` 不再写 `owner_team`：重发同一版本只改内容与可见性，主人一旦定下不变。
  这是 P0-2 的原始成因——原来 team-b 发同名包会把 `owner_team` 覆盖成自己，`market_current` 于是被抢走。
- `setCurrent()` 加存在性校验：指向不存在的版本抛 409，不再让市场首页挂一个 join 不出内容的位置。
- 连接器这条线同步切表：`publishMcp` 写 `market_items`（`config` 存 `{spec, env}`）+ `setCurrent`，
  `installMcp` 优先从表取包描述并 `mountMcp` 记账（顺带获得授权校验），`uninstallMcp` 走 `unmountMcp`。
  此前市场页读表、安装读目录，两套事实。

验证（`node deploy/orchestrator/verify-ownership.mjs`，临时库，15 条断言全过）：

```
team-b 发同名包 / 同名新版本     → 409（名字先到先得）
team-a 自己发新版本              → 允许，新版本 owner 仍是 team-a，旧版本正文仍在
setCurrent 指向未发布版本        → 409，指针未被改坏
team-b 装私有包                  → 403
分享按 item_id 授权              → 允许；shareId 指向别的包 → 403
skill:alpha 与 mcp:alpha 同名    → 互不干扰
```

真库迁移对账：

```
db: 回填 13 条分享的 item_id
市场 4 个包（技能 2 / 连接器 2）· 挂载 技能 5 行 / 连接器 1 行
孤儿引用 0 · 版本不一致 0 · 名称跨团队冲突 0
⚠️ 2 条挂载无法迁移：team-a / team-c 的 mcp:filesystem@1.0.0（市场里只有 1.2.0，跳过而非伪造）
```

最后那条是历史漂移：`packages.json` 里记的是 1.0.0，市场早就是 1.2.0。迁移不猜，让它显形——
需要人确认后重新安装一次即可。

HTTP 层：

```
GET  /market/skills（Bearer 市场 token）   → 200，team-b 的 rev=3d6f4541906a，1 条技能
GET  /market?team=team-a                  → 200，4 条，技能与连接器都在（含 owner/installedVersion）
POST /market/publish 同名包                → 409（不是 500）
```

**操作日志分裂成两处（不在上面清单里，是跑数据时发现的）**：

`market.mjs` 还从 `oplog.mjs` 引 `appendOp` 写 **`oplog.json`**，而 `db.mjs` 的挂载/卸载/启停写的是 **`ops` 表**；门户的 `opsView()` 只读前者。结果页面上只有「分享/启用/拒收」，**「安装/卸载/停用/升级」一条都没有**，而且 16 条 vs 21 条，看的人不知道少了一半。

改法：`market.mjs` 的 `appendOp` 收到本地包装里、统一落库；`ops` 加 `from_team` / `to_team` 两列（原来调用方传了 `from`/`to`，`db.appendOp` 的签名里没有，被静默丢弃，只能塞进 `detail` 文本）；`console.mjs` 改读 `opsForTeam()`；旧的 16 条按 `(at, action, name, by)` 去重补进库。门户的动作名映射补上 `disable` / `upgrade`（之前会露出英文原文），可见条数 12 → 20。

验证：

```
oplog.json 做一次分享后 md5 不变（已无写入）
/packages?team=team-c 的 ops 覆盖 install / uninstall / upgrade / enable / disable / share / reject
最新一条带 from=team-a to=team-c + 备注
```

### 10.6 本地技能遮蔽（本轮新增）

**问题**：dsh 的技能目录是**按 name 唯一**的一张表，同名只留一条，谁赢看 rank。本地来源全部排在市场前面：

```
<workspace>/.dsh/skills     100
<workspace>/.agents/skills  200
custom dirs                 300
$DSH_HOME/skills            400
~/.agents/skills            500
市场（market-skill）         550
bundled                     600
```

实测（临时容器里直接跑内核 `SkillRegistry`，两个 fake provider 给同名技能）：

```
local100 vs market550            → 生效 local
local400 vs market550            → 生效 local
local500 vs market550            → 生效 local
market550 先注册、local550 后     → 生效 market（同 rank 看注册顺序）
market50  vs local100            → 生效 market（rank 被写小就能反压本地）
```

两个关键事实：输掉的那条**从列表里彻底消失**，只在内核日志留一行 `warn`；而且 `complete` 仍是 `true`，
内核不认为这是异常。也就是说：**表里写着「已安装、已启用」，模型拿到的却是另一份，控制面完全感知不到。**

**修法**：把「工作区里有没有同名技能」做成挂载前的第 2 道检查，和 `canMount()` 并列放在 `mountSkill`
这个唯一写入点上（`setSkillEnabled` 启用时同样过一遍）。

- `deploy/orchestrator/workspace.mjs`：`resolveWorkspace(team)` 以容器挂载为准（`docker inspect` 的
  `/workspace` 来源），兜底 `workspace-<team>` 命名；`findShadow()` 扫**工作区根 + 一层子目录**的
  `.dsh/skills` 与 `.agents/skills`，两种形态都认——`<name>/SKILL.md` 和 `<name>.md`。
- 命中且没有 `force` → `409 SHADOWED`，错误体带 `code` 与 `detail.shadow`（具体路径、rank、形态），
  文案直接给出三条出路：改名 / 删掉 / 加 `force` 保留记录但明说不生效。
- `force` 强装时在 `ops.note` 里记一笔「被 … 遮蔽，实际不生效」，事后可查。
- 发布路径用 `force: true`：发布这个动作不该被本地文件名拦住，但返回值带回 `shadow`，让门户能提示
  「你发的这个版本，自己这边其实没在用」。
- `console.mjs` 的兜底 catch 追加 `code` / `detail` 透传——前端要靠 `SHADOWED` 区分「装不上」和
  「装了也不生效」。

**为什么不做成自动改名或加前缀**：技能名是模型调用和 `/命令` 的契约，改名等于改所有引用。
宁可挡在门口让人做决定。

验证（`node deploy/orchestrator/verify-shadow.mjs`，临时库 + 临时工作区，19 条断言全过）：

```
无同名技能                           → 装得进去
.dsh/skills/<name>/SKILL.md          → 409 SHADOWED，路径与 rank 100 都带得出来
.agents/skills/<name>.md             → 检出，rank 200，shape=file
proj/.dsh/skills/<name>（子目录）     → 检出，路径正确
被挡住时不写 team_skills             → 行数为 0
force 强装                           → 写入成功，返回 shadow，ops.note 留痕
停用                                 → 不检测
启用时被遮蔽                         → 409，且标志位没被改
```

真机 HTTP（team-a，在工作区里放了个同名 `hologres-query`）：

```
POST /market/install            → 409 SHADOWED + 具体路径
```
