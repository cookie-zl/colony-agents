# 13 · 技能包分发与对象存储

> 结论先说：技能包**必须落盘到容器**（脚本和二进制要真实文件），但落盘目录不是 `skills/`，
> 而是 `$DSH_HOME/market-skills/`。存储分三层：**表存元数据与授权，对象存储存整包，容器存物化副本**。
> 对象存储没接上时降级为「内容存库」，功能完整、只是体积受限。

## 1. 现状：单文件，且是「明说不支持」

| 环节 | 现在的行为 | 代码位置 |
|---|---|---|
| 发布 | 只取 `market_items.content`，也就是 SKILL.md 正文；目录里的其他文件不进库 | `market.mjs` `publishSkill` |
| 存储 | `market_item_files` 表建好了、字段不全，**从未写入过一行** | `init-db.sql` |
| 下发 | `GET /market/skills/:name/:version` 返回纯文本正文 | `console.mjs` |
| 解析 | provider 返回 `resourceBase: {kind:'opaque'}` | `plugins/market-skill/index.js` |

实测基线（生产库）：两个技能各 682 / 717 字节，`market_item_files` 0 行。

**这个「明说不支持」是刻意的**：比起给模型一个假的目录基址、让它去读不存在的
`scripts/run.py`，不如直接告诉它没有。代价是带脚本的技能根本装不进来。

### 发布时的静默丢弃

`publishSkill` 只读 `src.content`。技能目录里还有 `references/style.md`，发布后这些文件
既不在表里、也没有任何提示。别人装到手里只有正文，正文里提到的相对路径全部失效。
这一条比「不支持」更糟，因为**发布者以为发出去了**。

## 2. 一个真实的技能包长什么样

```
sql-review/
├── SKILL.md              # frontmatter + 正文：模型唯一必读的东西
├── references/
│   ├── sql-style.md      # 按需读，几十 KB 的规范
│   └── dialect-notes.md
├── scripts/
│   ├── explain.py        # 真要执行，需要解释器
│   └── lint.sh
└── assets/
    └── template.xlsx     # 二进制，模型只当附件
```

按「能不能只靠 API」分三类：

| 类型 | 例子 | 能不能不下发到本地 |
|---|---|---|
| 正文 | `SKILL.md` | 能，一行字符串 |
| 纯文本附件 | `references/*.md` | 能，但要模型主动去取（多一次往返），体验差 |
| 可执行 | `scripts/*.py` | **不能**。bash 要真实文件 |
| 二进制 | `assets/*.xlsx` | **不能**。要真实文件才能被程序读 |

dsh 侧对此有三态（`SkillResourceBase`）：

| 形态 | 渲染出的提示 | 适用 |
|---|---|---|
| `{kind:'directory', path}` | 「Base directory for this skill: …」 | 已物化到本地 |
| `{kind:'url', url}` | 「Base URL for this skill: …」 | 资源在对象存储、模型自己会取 |
| `{kind:'opaque'}` | 「资源由 provider 管理」 | 只有正文 |

`url` 看着能省掉落盘，但模型取每个文件都要自己发请求，也没法执行。
**脚本和二进制只能走 `directory`。**

## 3. 三层职责

```
控制面                          内容仓库                      容器（运行时缓存）
market_items（只有元数据）       market_item_files            $DSH_HOME/market-skills/
  ├ 版本 / 可见性 / 归属          （现在扮演对象存储）           <name>@<version>-<digest8>/
  ├ description  ← 索引            ├ path + sha256              ├ SKILL.md
  ├ digest       ← 内容指纹        ├ content BLOB               ├ references/
  └ rank                           └ storage / object_key       ├ scripts/
team_skills  ← 谁装了什么、启没启                                └ .dsh-market.json

                    ↓ P1 接 OSS 后，大文件从表搬到
                    market/items/<kind>/<name>/<version>/<digest>.tar.gz
```

一句话分工：

| 问题 | 谁回答 |
|---|---|
| 谁能装、装哪一版、启没启 | 表 |
| 这一版的内容是什么 | OSS |
| 现在要用，文件在哪 | 容器（没有就现拉） |

**不能反过来。** 任何「OSS 里有对象就等于有技能」的判断都是错的——可见性只由表决定，
所以签名 URL 必须**先过 `canMount()` 再签**。

### 3.1 两张表：元数据 + 内容

`market_items` 一行对应 `market_item_files` 多行，**只靠 `item_id` 关联**：

| 表（Table） | 一行是什么（Row） | 回答什么问题（Question） |
|---|---|---|
| `market_items` | 一个「包 × 版本」 | 这是什么、谁能用、哪一版是当前发布 |
| `market_item_files` | 这一版里的一个文件 | 内容是什么、多大、哈希对不对 |

名字和版本**不是**关联键：同名同版本的另一个包（比如重发覆盖前的旧内容）靠 id 才能区分。
表里冗余的 `name` / `version` 只为「不 JOIN 就能读」。

```sql
-- market_items · skill/连接器基础表（市场包元数据）：一行 = 一个包的一个版本，只存索引不存正文
CREATE TABLE market_items (
  id           TEXT PRIMARY KEY,               -- 'skill:hologres-query@1.0.0'
  kind         TEXT NOT NULL,
  name         TEXT NOT NULL,
  version      TEXT NOT NULL,
  title        TEXT NOT NULL,
  description  TEXT NOT NULL,                  -- 唯一保留的「内容」：给模型看的路由摘要
  when_to_use  TEXT,                           -- 同上，也是索引
  digest       TEXT NOT NULL,                  -- sha256(kind|name|version|文件清单|config)
  rank         INTEGER NOT NULL DEFAULT 550,
  visibility   TEXT NOT NULL CHECK (visibility IN ('public','private')),
  owner_team   TEXT NOT NULL DEFAULT '_system',
  status       TEXT NOT NULL CHECK (status IN ('draft','published','deprecated')),
  created_by   TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  published_at TEXT,
  -- bundle_key / bundle_size / pending_oss 三列**现在还没有**：接 OSS 时和第 8 节的补传逻辑一起加。
  -- 提前建列会让人以为「已经有整包对象了」，而实际上 /bundle 是每次现打的。
  UNIQUE (kind, name, version)
);

-- market_item_files · skill 包内容表（暂时扮演对象存储）：一行 = 包内一个文件，PK 即逻辑对象键
CREATE TABLE market_item_files (
  item_id    TEXT NOT NULL REFERENCES market_items (id),
  path       TEXT NOT NULL,                    -- 包内相对路径 'references/sql-style.md'
  size       INTEGER NOT NULL,
  sha256     TEXT NOT NULL,                    -- 单文件内容哈希，解包后逐条校验
  mime       TEXT NOT NULL DEFAULT 'application/octet-stream',
  executable INTEGER NOT NULL DEFAULT 0,       -- scripts/** 才为 1，解包时还原 0755
  storage    TEXT NOT NULL CHECK (storage IN ('db','oss')),
  content    BLOB,                             -- storage=db 时的字节
  object_key TEXT,                             -- storage=oss 时才有值
  PRIMARY KEY (item_id, path)
);
```

**`market_items.content` 这一列删掉。** 它原来是 SKILL.md 的第二份拷贝，和 `market_item_files`
里的 `SKILL.md` 天然会漂移，而两份看起来都正常，出了问题极难排查。删掉之后内容只有一处。

留下的 `description` / `when_to_use` 不是「内容」，是**索引**：列表页要展示、内核要拿它做
技能路由，每次请求都去解 frontmatter 算一遍没有意义。这个区分决定了什么该进元数据表。

内核需要的 `content` 字符串（已剥 frontmatter）在**读的时候算一次**：

```js
content = stripFrontmatter(await readFile(itemId, 'SKILL.md'))
```

一条 SELECT 加一次字符串切分，相对一次 HTTP 往返可以忽略。

分流规则（写入时决定，读时不用判断）：

| 条件 | storage | 理由 |
|---|---|---|
| UTF-8 文本且 ≤ 256 KB | `db` | 一次查询拿到，能 grep、能 diff、能审计 |
| 其他（二进制、超过 256 KB） | `oss` | 库里存二进制会让快照膨胀 |
| OSS 不可用且整包总量 ≤ 8 MB | 全部 `db` + `pending_oss=1` | 降级可用，见第 8 节 |
| OSS 不可用且整包总量 > 8 MB | **拒绝发布** | 防止把库撑爆 |

这里的 **8 MB 指包里所有文件字节数之和**（解压后的总量），不是上传的压缩包体积。
压缩比因包而异（`references/*.md` 大约 3:1，已压缩的二进制接近 1:1），
按解压后算才是真正压到库上的量。

256 KB 不是拍脑袋：技能里的文本附件是「给模型读的」，超过这个量级模型也不会整篇读，
不如让它自己按需取。

### 3.1.1 表暂时扮演对象存储

现在的 `market_item_files` 就是对象存储的替身：`(item_id, path)` 是逻辑对象键，
`content` 是对象体，`size/sha256/mime` 是对象元数据。`storage` 列现在全是 `'db'`。

接 OSS 时发生的事只有一件——把满足条件的行搬走，改两个字段：

```sql
UPDATE market_item_files SET storage='oss', object_key='market/items/...', content=NULL
 WHERE item_id=? AND path=?;
```

读写路径完全不变：写时按规则选后端，读时看 `storage` 决定是直接拿 `content`
还是签 URL。**这就是为什么现在不用等 OSS**——表已经是那个抽象了。

存散装文件而不是存 zip / tar.gz：

| 位置 | 存什么 | 形态 |
|---|---|---|
| `market_item_files.content` | 每个文件的原始字节 | BLOB，一行一个文件 |
| `/bundle` 响应 | 现场把上面的行打成 tar.gz | 不落库 |
| OSS（P1） | 打好的 tar.gz | 一个对象 |

为什么不直接存整包：

| 能力 | 逐文件 BLOB | 存整包 |
|---|---|---|
| 单独取 `references/sql-style.md` | 一条 SELECT | 解整个包 |
| 查「哪些包引用了这个文件」 | SQL 能查 | 做不到 |
| 人工排查包内容 | 打开行就能看 | 下载解包 |
| 同内容跨版本去重 | 按 sha256 能 | 不能 |
| `/bundle` 响应 | 现场打包（有 CPU 开销） | 直接吐，更快 |

代价是 `/bundle` 要现场打包，但那是一次性成本：打完缓存到
`.cache/bundles/<digest>.tar.gz`，同一 digest 第二次请求直接发文件。

### 3.2 对象键：id 定位，digest 定版

逻辑标识用 `item_id`（`skill:hologres-query@1.0.0`），它本身就是「某个技能的具体版本」，
唯一且能和版本信息对上。但它含 `:` 和 `@`，直接当键名在 URL 里要转义两次，容易出错，
所以物理键按路径展开：

```
market/items/<kind>/<name>/<version>/<digest>.tar.gz
market/items/skill/hologres-query/1.0.0/9f2c4a1b8e3d5f6079a2b4c6d8e0f1a3.tar.gz
```

三段路径 = `item_id` 的等价展开，唯一性完全一致；末尾 `digest` 这一层是**必须留的**：

| 只写 `<version>.tar.gz` | 加上 `<digest>.tar.gz` |
|---|---|
| 同版本重发会覆盖，旧内容永久丢失 | 新内容 = 新对象，旧的还在，可回溯 |
| 写表成功、上传失败时，表里 digest 和对象内容对不上，且查不出来 | 表指哪个 digest 就下哪个，永远一致 |
| 上传重试是「覆盖」语义，不敢重放 | 重传同一个 digest 是幂等的，可以放心重试 |

`digest` 是 32 位十六进制（`sha256(...).slice(0, 32)`），128 位足够防碰撞。

对象键里**不出现团队名**。私有包和公开包共用同一份对象，可见性完全由表决定，
对象存储不需要跟着改 ACL，团队归档时也不用手动清它的对象。

### 3.3 digest 只剩两个来源：文件清单 + config

`content` 删掉之后，指纹不再单独算正文——`SKILL.md` 的 sha256 已经在清单里了：

```js
digest = sha256(kind, name, version, config || '',
                ...files.sort(byPath).map(f => `${f.path}\0${f.sha256}`)).slice(0, 32)
```

- 技能：`config` 为空，指纹完全由文件清单决定
- 连接器：`files` 为空，指纹由 `config`（JSON）决定
- 两者都变 = 都参与哈希，不需要特殊分支

否则「只改 `references/` 不改 `SKILL.md`」检测不出来——`rev` 不变、缓存不失效、
团队永远拿旧包。

### 3.4 存量迁移：4 条记录要重建 frontmatter

现有 4 条 `market_items` 的 `content` 是**剥掉 frontmatter 的正文**，原始 frontmatter 已经丢了。
迁进 `market_item_files` 时只能拼一个最小的回来：

```markdown
---
name: hologres-query
description: <market_items.description>
---
<原 content>
```

`title` / `when_to_use` 在表里也有，一并写入。**其他 frontmatter 字段（`allowed-tools`、
`license` 之类）找不回来**，只能由包作者重新发布一次。现在总共 4 条、都是几百字节的手写技能，
这个代价可以接受；再晚做，迁移成本会随包数量线性涨。

迁移后必须核对：

```sql
-- 每条技能记录都必须有 SKILL.md，否则物化出来是个空目录
SELECT i.id FROM market_items i
  LEFT JOIN market_item_files f ON f.item_id = i.id AND f.path = 'SKILL.md'
 WHERE i.kind = 'skill' AND f.path IS NULL;   -- 应为 0 行
```

## 4. 两个上传入口，一种存储形态

| 入口 | 触发方式 | 内容来源 | 额外校验 |
|---|---|---|---|
| **A 目录发布** | 团队在 workspace 里做好技能后 `publish` | `docker cp` 出容器目录 | 目录里必须有 `SKILL.md` |
| **B 浏览器上传** | 门户拖入 `.tar.gz` / `.zip` | HTTP body（`multipart`） | 格式、大小、条目数、路径安全 |

两条路最后都归一到同一件事：**一个 tar.gz → sha256 → 表 + 对象存储**。
所以存储层只有一套代码，入口差异全在「怎么拿到原始字节」这一步。

B 入口的限制：

| 项 | 阈值 | 理由 |
|---|---|---|
| 上传体积 | ≤ 32 MB | 超过就是资源包不是技能包了 |
| 解压后总量 | ≤ 128 MB | 防 zip bomb |
| 条目数 | ≤ 500 | 同上 |
| 格式 | 只认 tar.gz / zip | 不猜，也不接受裸目录 |
| 根目录 | 必须能解析出 `SKILL.md` | 允许包一层顶层目录，不允许两层以上 |

## 5. 分发：内容只从一个入口出

| 接口 | 返回 | 用途 |
|---|---|---|
| `GET /market/skills` | 每项加 `bundle: {size, digest, hasBundle}`，**不带内容** | 市场列表、算体积、判断要不要下 |
| `GET /market/skills/:name/:version` | 纯文本正文（从 `SKILL.md` 现算） | 单文件技能，现状不变 |
| `GET /market/skills/:name/:version/bundle` | `application/gzip`，tar 流 | 多文件技能，物化时一次拉全 |

`hasBundle` 的判定：**包里除 `SKILL.md` 外还有文件，就是 true**。只有单个 `SKILL.md` 的
技能走纯文本接口，不走物化——一个 700 字节的字符串打成 tar.gz 只会更慢。

`/bundle` 除了字节还回三个头，缺一个客户端就没法自证拿到的是原包：

| 头 | 值 | 用途 |
|---|---|---|
| `X-Dsh-Digest` | `market_items.digest` | 版本指纹，客户端拿它做缓存目录名与「要不要重下」 |
| `X-Dsh-Manifest` | `filesDigest(files)` | 文件清单指纹，客户端解包后自己算一遍，对不上直接丢弃 |
| `X-Dsh-Files` | 文件数 | 日志与排障用 |

打出来的 tar 是**确定的**：`mtime` 置 0、`uid/gid` 置 0、条目按路径排序，只保留可执行位。
否则同一份内容在 macOS 上打一次、在 Linux 上再打一次，字节不同——缓存和「内容没变」的判断全都会失真
（`make verify-bundle` 里钉了「同样输入打两次字节完全一致」）。

**为什么内容入口必须收在一个地方**：provider 只认这两个接口，不关心后端是库还是 OSS。

```
provider → /bundle → 控制面 → { storage='db'  → 从 market_item_files 现场打包
                              { storage='oss' → 302 到签名 URL（或服务端代理流）
```

这条边界让第 8 节的「OSS 没接上也能用」成为自然结果，而不是特例分支——
P1 接 OSS 时，provider 的下载/解包/校验代码**一行都不用改**。

为什么是 tar.gz 而不是逐文件下载：200 个文件逐个拉就是 200 次鉴权和往返，
而且整包才有统一的 `ETag = digest`，本地目录只要 digest 一致就不用重下。

## 6. 运行时物化：懒加载 + 预热

`plugins/market-skill` 的 `get()`：

```
有 bundle?
  ├─ 否 → GET /market/skills/:name/:version 拿纯文本 → 返回 opaque（单文件技能，现状不变）
  └─ 是 → 本地目录 <name>@<version>-<digest:8>/ 存在 且 标记文件 digest 匹配?
           ├─ 是 → 直接用（零网络）
           └─ 否 → 下载 → 解包到临时目录 → 逐文件校验 sha256 → 原子 rename
                  → 返回 resourceBase: {kind:'directory', path}
                  → content = stripFrontmatter(读本地 SKILL.md)
```

两条分支的 `content` 来源不同，但都对内核呈现同一个字段：

| 分支 | `content` 从哪来 |
|---|---|
| 单文件 | 接口直接返回正文 |
| 多文件 | 物化后读本地 `SKILL.md`，剥掉 frontmatter |

多文件分支不再额外发一次纯文本请求——文件已经在本地了。

标记文件 `.dsh-market.json`：

```json
{ "itemId": "skill:hologres-query@1.0.0", "digest": "9f2c4a1b…", "files": [{ "path": "SKILL.md", "sha256": "…", "size": 682 }] }
```

**判断要不要下载只比 digest**，不比 mtime、不比 version。version 可能被同版本重发覆盖，
digest 是内容指纹，不变就不用动。

### 6.1 目录位置

**必须放 `$DSH_HOME/market-skills/`，不能放 `$DSH_HOME/skills/`。**

后者是 `dsh-skill-filesystem` 的 `user-dsh` 根（rank 400）。放那儿会造成同一个技能
同时被两个 provider 提供：filesystem 那份 rank 400 赢，市场 provider 的 550 输。
于是「在门户里停用了这个技能，容器里那份还在生效」——又回到两套事实。

放在 `market-skills/` 下，filesystem provider 根本不扫这个目录，物化产物只作为
`resourceBase` 的落点存在，技能**是否可见完全由表决定**。这条是整个方案的支点。

### 6.2 预热

**不在 entrypoint 里同步下载全部。** 团队装 20 个技能、共 100 MB，每次冷启动都要等，
而绝大多数会话一个技能都用不到。

改成：容器起来后异步预拉（不阻塞 dsh 启动），`get()` 时若还没就绪就同步等这一次。

```
apply(ctx) → 立即注册 provider
           → setTimeout(0) 起一个后台循环：
               拉 /market/skills → 对每条 hasBundle 的项，串行物化
               失败记日志不重试（下次 get() 会自己拉）
```

串行而不是并发：SQLite 单写、控制面还要现场打包，并发只会互相拖慢。
一次最多预热 5 个，剩下的按 LRU 留给 `get()` 现拉。

### 6.3 生命周期

| 时机 | 动作 |
|---|---|
| 技能被停用/卸载 | 不动磁盘。下次 `get()` 不会再被调用，目录自然不再被引用 |
| digest 变化 | 新目录，旧的不动；进程启动时清理同名旧版本，只留最近 2 个 |
| 进程退出 | 不清。保持在卷里，重启后 digest 一致就免下载 |
| 团队归档 | 打 tar 时**排除** `market-skills/`，见第 7 节 |

不做过期删除是有意的：这是缓存，判断「还在不在用」要靠表，不是靠 mtime。

## 7. 重建矩阵：什么时候真的要重下

`dsh-home` 是 named volume（`dsh-team-a_dsh-home`），所以大部分「销毁重建」都不需要重下：

| 操作 | 卷 | 物化目录 | 要不要重下 |
|---|---|---|---|
| `sleep` → `wake` | 保留 | 保留 | **不用**，校验 digest |
| `down` → `up` | 保留 | 保留 | **不用** |
| `archive` → `restore` | tar 里有 | tar 里带着 | **不用**（除非归档时排除了，见下） |
| **`destroy` → `up`** | 删了 | 没了 | **要**，全量按 `team_skills` 重建 |
| 卷迁到新节点 | 一起搬 | 一起搬 | **不用** |
| 发布者升版本 | 保留 | 旧版本 | 只下新 digest |

「按团队 id 查技能 → 逐条下载 → 装回容器」这个流程只在 `destroy` 之后才真正跑一遍。
实现上不需要单独的 bootstrap：`GET /market/skills` 本来就是按 token（即团队）查的，
provider 起来后预热一遍就等于重建，逻辑只有一份。

### 归档体积

`archive` 是 tar 整个 `dsh-home` 卷，物化目录在卷里会被一起打进去。
一个大包 8 MB × 20 个技能 = 160 MB 归档，而这些都是**能从对象存储重建的**。

改法：`archive` 时排除 `market-skills/`，`restore` 后由预热重新拉。
和「卷里 7.4 MB 有 98% 是前端产物」是同一类问题——可重建的东西不该进归档。

## 8. 上传不强阻塞

发布接口不等对象存储写完就返回。内容先落在库里（`storage='db'`），后台再传：

```
publish → 算 digest → 写 market_items + market_item_files → 返回成功（pending_oss=1）
                    ↓ 后台（不阻塞响应）
                 传 tar.gz 到 OSS
                    ├─ 成功 → 回写 bundle_key/bundle_size，pending_oss=0
                    └─ 失败 → 保持原样，功能不受影响，等补传
```

为什么这个顺序是安全的：`/bundle` 是唯一入口（第 5 节），后端是库还是 OSS 对 provider
没有区别。所以「还没传上去」和「已经传上去」是**性能差异，不是功能差异**。

前提是**内容先落库**。如果反过来——内容只存 OSS、表先写、上传后补——上传失败时
表里就留下一条拿不到内容的记录，用户看得见、装不下来。两害相权，选「内容先落库」。

补传时机：

| 触发 | 说明 |
|---|---|
| 控制面启动 | 扫 `WHERE pending_oss = 1 ORDER BY published_at` 补一轮 |
| 下一次发布 | 顺手把积压的带上，一次最多 3 个 |
| 手动 | `make oss-sync` 或 `POST /market/sync-oss` |

幂等：同一个 `(item_id, digest)` 重传就是覆盖同一个对象，删了重下也无所谓。

前端展示：`bundle: { storage: 'db', pendingOss: true }` 时可以标「云端复制中」，
但不该阻止使用。

## 9. 安全边界

解包是这套方案里唯一「拿外部内容写磁盘」的地方，必须逐条挡住：

| 风险 | 处理 |
|---|---|
| `../` 穿越、绝对路径 | 解包前对每个 entry 做 `resolve(dest, path)` 前缀校验，不在 dest 下就整包拒绝 |
| 符号链接指向包外 | 拒绝任何非普通文件/目录的 entry（symlink、hardlink、device） |
| zip bomb | 单文件 ≤ 32 MB、解压总量 ≤ 128 MB、条目数 ≤ 500，读 tar header 就能判，不用先解 |
| 权限位 | 只把 `scripts/**` 还原成 0755，其他一律 0644；不还原 setuid |
| 内容被调包 | 逐文件校验 sha256，对不上整包删掉重下，连续失败就 `complete:false` |
| 私有包的链接外泄 | 私有 bucket，控制面签发 60 秒 TTL 的签名 URL；先过 `canMount()` 再签 |
| 容器拿到长期凭据 | **绝不给容器 AK**，只给单个对象的短 TTL 只读 URL |

## 10. 执行环境：这一步最容易漏

多文件技能里最值钱的是 `scripts/`，但**当前镜像里没有 python3**：

```
$ docker run --rm --entrypoint sh colony:0.2.1-rc.5 -c "python3 -V"
sh: 1: python3: not found
```

就算把包完整物化下来，`scripts/explain.py` 照样跑不了。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 镜像内置 | Dockerfile 装 `python3` + `uv`，不预装业务包 | 镜像 +300 MB，每个团队实例都吃这份 |
| B 按需装 | 物化时读 `SKILL.md` 声明的 `runtime: python3`，缺就装 | 首次调用慢、要联网、失败面大 |
| C 只允许 bash/node | 发布时校验脚本解释器白名单 | 挡住大部分真实技能 |

推荐 **A + C**：镜像内置 python3 与 uv（不做预装，让技能自己 `uv run` 声明依赖），
发布时校验解释器白名单。B 看着灵活，但「装依赖」放在请求路径上会变成不可控的延迟源。

**在 A 落地之前，多文件包只支持 `scripts/*.sh` 和纯文本附件。**

## 11. OSS 技术链路

### 11.1 对象键规划

```
oss://<bucket>/market/items/<kind>/<name>/<version>/<digest>.tar.gz     整包（主）
oss://<bucket>/market/bundles/<digest>.tar.gz                            打包缓存（可再生）
```

第二行只在「后端是库、需要现场打包」时用，作为打包结果缓存，丢了无妨。

### 11.2 写路径

| 步骤 | 做法 |
|---|---|
| 打包 | 控制面遍历 `market_item_files`（或源目录）→ tar（不压缩或 gzip -1） |
| 上传 | `putObject(key, buf, { ContentType: 'application/gzip', Metadata: { digest, itemId } })` |
| 回写 | `UPDATE market_items SET bundle_key=?, bundle_size=?, pending_oss=0 WHERE id=?` |
| 失败 | 记 `ops` 一条，`pending_oss` 保持 1，不重试循环（避免放大故障） |

上传**不做分片**：单包上限 32 MB，一次 PUT 足够。

### 11.3 读路径

```
GET /market/skills/:name/:version/bundle
  → 校验 Bearer token → 得到 team
  → 查 team_skills（确保 enabled=1）→ 查 market_items → canMount()
  → storage='oss' ? 302 Location=<60s 签名 GET URL>
                  : 200 现场打包库里的内容
```

302 而不是服务端代理流：控制面不用扛带宽，容器直接对 OSS 拉，同 region 走内网还不收流量费。

签名 URL 的范围要收窄：**单个对象、只读、60 秒**。不要签前缀（`prefix=market/`），
那等于把 bucket 交出去。

### 11.4 权限模型

| 动作 | 谁做 | 凭据 |
|---|---|---|
| 写（发布、打包） | 控制面 | 容器内 RAM Role（ACK 用 RRSA）或 STS 临时凭证 |
| 读（物化） | dsh 容器直连 | 控制面签发的 60 秒 URL |
| 删（GC） | 控制面 | 同写 |

**绝不要把 AK 配进团队容器。** 容器里跑的是用户代码，任何长期凭据等于把 bucket 交出去。

### 11.5 依赖与配置

控制面目前零依赖（只用 `node:sqlite`）。接 OSS 会引入 `ali-oss`：

```js
// 唯一的写入口，其余代码只碰这两个函数
await putBundle(key, buf)
const url = signGetUrl(key, 60)
```

配置走环境变量，不进库：

```
OSS_BUCKET=...
OSS_REGION=oss-cn-hangzhou
OSS_ENDPOINT=oss-cn-hangzhou-internal.aliyuncs.com   # 同 region 走内网，不收流量费
OSS_ROLE_ARN=...                                      # 或 OSS_ACCESS_KEY_ID/SECRET（仅本地调试）
```

`OSS_BUCKET` 为空 = 未启用，自动走降级路径（第 8 节），不需要额外的开关。

### 11.6 什么时候必须上

| 指标 | 阈值 | 原因 |
|---|---|---|
| 单个库文件 | > 200 MB | 每次快照 `VACUUM INTO` 整库拷贝，库越大越快照越慢、磁盘翻倍 |
| 单个包 | > 8 MB | 超过就不该进库 |
| 二进制文件总量 | > 50 MB | BLOB 在库里没法压，快照会直接翻倍 |

按现在体量（两个技能不到 2 KB）离阈值很远。**P0 全部存库即可**，
表结构把 `storage`/`bundle_key` 留好，接 OSS 是加分支不是改设计。

## 12. 分阶段

| 阶段 | 内容 | 依赖 | 产出 |
|---|---|---|---|
| **P0** ✅ | `market_item_files` 写入（A/B 两个入口）+ digest 含文件 + `/bundle` + 物化 + 预热 + 解包安全校验 + 归档排除 | 无 | 多文件包（references + sh 脚本）可用 |
| **P1** | OSS 后端：写路径、签名 URL、`pending_oss` 补传、GC | 阿里云账号 | 二进制附件、大包 |
| **P2** | 发布时校验解释器白名单 | 无（python3 已在镜像里，`docs/19`） | 带脚本的包能跑起来前就知道缺什么 |

P0 落地情况（`make verify-bundle` 55 条 + 真机验证）：

| 步骤 | 落在哪 | 状态 |
|---|---|---|
| 迁移：`content` → `market_item_files['SKILL.md']`，补最小 frontmatter，`DROP COLUMN content`，重算 digest | `db.mjs` `migrateItemContent()` | ✅ 真库跑过：2 个包迁完，正文长度逐字节不变（682 / 717） |
| 目录发布取整目录（先找 `skills/<name>`，再找 `market-skills/<name>@*`，都没有则从库里 fork） | `market.mjs` `skillFilesFromTeam()` | ✅ |
| `POST /market/upload`（body 直接是 tar.gz） | `console.mjs` | ✅ 3 文件包上传 → 发布 → 安装 → 物化 → 跑通 `scripts/check.py` |
| 目录发布取整目录，编辑后再发布走卷 | `market.mjs` `skillFilesFromTeam()` | ✅ 在物化目录里加一行 → publish → 返回 `from: 'volume'`，1.3.0 里带上了那行 |
| `/bundle` + `/market/skills` 补 `bundle` 字段 | `console.mjs` | ✅ |
| 物化 + 解包校验 + 预热 + 旧版本清理 | `plugins/market-skill` | ✅ 启动即物化；升级换目录；restart 后 mtime 不变（没重下）；1.0.0 被清、留 2 个 |
| `team-up.sh archive` 排除 `market-skills/` | `deploy/compose/team-up.sh` | ✅ 归档里 0 条 `market-skills` |

三处和设计稿不一样，都是有意的：

- **上传只收 tar.gz，不收 zip。** 控制面手写 multipart + zip 解析是几百行最易出越界问题的代码，
  而客户端 `fetch(url, {body: file})` 一行就够。要收 zip 等真有需求时再补。
- **`storage` 列没有 CHECK 约束**，只是 `TEXT DEFAULT 'db'`：现在唯一合法值就是 `db`，
  等 `oss` 真接上再加约束，避免「改了约束但老库不认」。
- **`bundle_key` / `bundle_size` / `pending_oss` 三列没建。** 提前建空列会让人以为「整包已经对象化了」，
  而实际上 `/bundle` 是每次现场打的。

第 1 步必须一次做完：`content` 列一旦删掉，所有读正文的路径（`skillBodyForTeam`、
`publishSkill`、`migrate-db.mjs`）就都断了，不能分两次上。

### 12.1 还缺的两件（记在 `docs/ROADMAP.md`）

| 缺什么 | 后果 | 怎么补 |
|---|---|---|
| 单包体积上限仍是估值 | 32 MB / 8 MB 都是猜的 | 统计一批真实技能包的分布再定 |
| 上传不收 zip | 只能用 `tar czf` 打包 | 真有需求再补 zip 解析（同一条路径安全规则） |

另外两处**设计上就没做**，不是漏了：

- 发布不校验 `scripts/` 的解释器是否存在。`python3` 已在镜像里（`docs/19`），
  但团队写 `#!/usr/bin/env node18` 这种，发布时不会拦——等 P2 加白名单。
- 物化目录不设过期清理。这是缓存，判断「还在不在用」要靠库，不靠 mtime；只在进程启动时
  按「同名留最近 2 个」裁一次。
