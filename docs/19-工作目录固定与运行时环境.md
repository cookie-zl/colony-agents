# 19 · 工作目录固定与运行时环境

docs/16 说过「产物落点取决于 cwd」，docs/17 把历史 cwd 补建回来了，但三件事都没解决：

1. **用户新建的工作区落在哪，由界面上选的目录决定**。容器里查不到 Documents 目录，用户
   随手建在 `/home/dsh/测试1`——那是**容器可写层**，`docker rm` 那一刻蒸发。
2. **镜像里没有 Python**。实测「通过 py 脚本帮我查一下」这条任务，agent 写得出脚本，
   执行时 `python: command not found`（退出码 127），最后只能交付脚本让用户自己装。
3. **已经登记过的工作区指向可写层**，而且 dsh 的自动发现只在第一次启动跑一遍，
   之后再没有机制把新目录变成工作区——界面上的工作区选择和会话的实际落点因此会对不上。

这篇记这三件事怎么做、验证到什么程度，以及顺手把「卷 / 沙箱 / 绑定目录」这几个词掰清楚。

## 一、四个「地方」，别混着叫

同一个文件写在不同位置，发版后的命运完全不同：

| 位置 | 容器里长什么样 | 谁在写 | `docker rm` 后 | `docker build` 后 | 备份 |
|---|---|---|---|---|---|
| **镜像层** | `/usr/local/bin/dsh`、`/opt/dsh-seed` | 构建期 | 还在（镜像没变） | 换新的 | 不用备份，能重建 |
| **可写层**（口语里的「沙箱内」） | `/home/dsh/xxx`（除挂载点）、`/tmp`、`/root` | 运行期 | **没了** | 没了 | 无从备份，日志里的内容也救不回来 |
| **命名卷** | `/home/dsh/.dsh` → `dsh-team-a_dsh-home` | dsh 自己 | 还在 | 还在 | 控制面快照 + 归档 tar |
| **绑定目录** | `/workspace` → 宿主 `deploy/compose/workspace-team-a/` | agent 与用户 | 还在 | 还在 | 跟宿主目录一起备份 |

所以「沙箱」在我们这套里有两层意思，说到时必须分开：

- **容器沙箱**：可写层 + `/tmp`。一次性，发版即清空。
- **权限沙箱**（`DSH_PERMISSION_MODE=workspace-write`）：限制 agent 能写哪些路径，
  它管的是「能不能写」，不是「写了还在不在」。两个概念互不替代：权限开着、写在可写层，
  照样丢；权限关着、写在 `/workspace`，照样活着。

`/workspace` 是唯一既有权限沙箱容得下、又有宿主真身的目录，所以工作区应该只往那里落。

## 二、workspace-guard：把工作区钉在 `/workspace/<name>`

不改 dsh 源码。dsh 的界面「新建项目」走的是 `ctx.workspaceController.createWorkspace(path)`
→ `ctx.workspaceRegistry.create(path)`，这是「把某目录登记成工作区」的**唯一入口**，
包住它就覆盖了所有上游调用方。

插件 `plugins/workspace-guard/` 只做三件事：

| 方法 | 原来 | 现在 |
|---|---|---|
| `create(path, title)` | 用传进来的目录 | 取最后一段当名字，改写为 `<root>/<name>`，**先 mkdir**（create 内部要 `realpath` + `stat`，目录不存在直接抛错） |
| `resolveByPath(path)` | 按原路径反查 | 先按映射后的路径查，查不到再按原路径查 |
| `initializeDefault(fn)` | 首次使用落在 `<Documents>/deepseek-harness/default-workspace`，容器里查不到就放弃 | 映射到 `<root>/default-workspace`；解析失败也退回这里，不再放弃 |

行为实测（`make verify-workspace-guard`，17 条）：

| 请求 | 落点 |
|---|---|
| `/home/dsh/测试1` | `/workspace/测试1` |
| `/workspace/already` | `/workspace/already`（幂等，不套两层） |
| `/tmp/elsewhere/proj2` | `/workspace/proj2` |
| `/`、`` | `/workspace`（不会拼成 `/workspace/workspace`） |
| `/etc/../../../tmp/x` | `/workspace/x`（`..` 先被解析掉） |

另外两点是刻意的：

- **不做旧数据迁移**。已经在 `/workspace` 外面的工作区只打一行告警
  （team-a 实测：`1 个旧工作区不在 /workspace 里（不迁移，产物仍在可写层）：/home/dsh/测试1`），
  不搬、不删。
- **注册表缺方法就降级**，只打日志不抛错——dsh 升级换了 API 时容器仍然起得来。

配套的那条配置在 `profile/cordis.patch.yml`：`working-directory.defaultDirectory = /workspace`。
它管的是「连目录都没有」的会话，别让兜底值依赖 `WORKDIR` 恰好是什么。

## 三、Python 预装进镜像

改一个 `apt-get install` 就行，**每个团队用同一个镜像**，所以「起来就自带」不需要任何运行期动作：

```dockerfile
apt-get install -y --no-install-recommends \
  ca-certificates curl git tini python3 python3-pip python3-venv
&& ln -snf /usr/bin/python3 /usr/local/bin/python   # agent 习惯写 python，不是 python3
&& ln -snf /usr/bin/pip3 /usr/local/bin/pip
```

三个容易踩的点：

| 坑 | 处理 |
|---|---|
| Debian 12 的 PEP 668：`pip install` 直接被拒 | `PIP_BREAK_SYSTEM_PACKAGES=1`（单用户容器，没有被 pip 破坏的系统包） |
| 非 root 装包落到 user site（默认 `~/.local`），在可写层，发版即丢 | `PYTHONUSERBASE=/home/dsh/.dsh/py`，指进数据卷；`PATH` 补上 `$PYTHONUSERBASE/bin` |
| 默认连 PyPI 慢 | `PIP_INDEX_URL` 默认清华镜像，`--build-arg` 可改回 `https://pypi.org/simple` |

实测（同一数据卷、先装一次再换一个容器）：

```
容器 1：which python → /usr/local/bin/python，Python 3.11.2
        pip install cowpy → 落到 /home/dsh/.dsh/py/lib/python3.11/site-packages
        which cowpy     → /home/dsh/.dsh/py/bin/cowpy
容器 2（新容器、同卷）：python -c "import cowpy" → ok；cowpy "重建后还在" → 正常输出
```

## 五、把工作区收敛成 `/workspace` 一个根

第二节解决了「新建的工作区落在哪」，但没解决「**已经登记过的工作区指向哪**」。实测 team-a 的现场是：

```
workspace.json   1 个工作组：测试1 → /home/dsh/测试1   （4 个会话）
sessions/        另有 8 个会话 cwd = /workspace，不属于任何工作组
界面上           侧栏：测试1 ── 每日星标最多项目脚本 / 查询助手版本
                       未分组 ── 8 个会话
/home/dsh/测试1  find … -mindepth 1 | wc -l → 0（重建后已是空目录）
```

### 5.1 根因：`bootstrap()` 只跑一次

`dsh-workspace` 的 `Service.init` 里：

```js
if (!this.state.initialized) { await this.bootstrap(headers) }   // 按 cwd 分组，自动建工作区
else if (this.table.size > 0) await this.replaceHeaderIndex(await this.listStoredHeaders())
```

`bootstrap()` 才是「按会话 cwd 自动发现工作区」的那段代码。团队 11-04 在 `/home/dsh/测试1`
建了第一个工作区，`initialized` 从此永久为 `true`；之后落在 `/workspace` 的会话再也没人
给它们建归属，只能堆进「未分组」。

而「未分组」不是一个工作区类型，是 `groupByWorkspace()` 的兜底桶（`workspaceId === undefined`），
凡是拿工作区身份的能力全在上面短路：

| 能力 | 未分组 | 依据 |
|---|---|---|
| 在里面新建会话 | ❌ 点「+」没反应 | `onCreate: if (group.workspaceId !== undefined) startSession(...)` |
| 重命名 / 删除 | ❌ 没有菜单 | `actions: group.workspaceId === void 0 ? void 0 : {...}` |
| 拖动排序 | ❌ 不能拖 | `workspaceDragProps = workspaceId === void 0 ? void 0 : {...}` |
| 悬停看路径 | ❌ 没有卡片 | 源码注释 `the ungrouped bucket has none` |

最隐蔽的一条是**新建会话的落点**：

```js
const target = workspaceId ?? currentWorkspaceId ?? recent
```

从一个未分组的会话里点「新会话」，`currentWorkspaceId` 是 `undefined`，于是回落到 `recent`
——最近用过的那个真实工作区，也就是「测试1」。**用户从安全位置（`/workspace`）被拉回可写层**。

### 5.2 做法：不兼容旧登记，一次性收敛

按「一切以当前版本为准」的口径，**不搬文件、不做兼容**，直接把登记重置成「只有 `/workspace`」。
三个改动，顺序不能换：

| 顺序 | 改哪 | 做什么 |
|---|---|---|
| 1 | 新 `deploy/image/migrate-workspaces.mjs`（entrypoint 里、`prepare-workspaces` 之前） | 把 `path` 不在 `/workspace` 下的工作区摘掉（`workspaceIds` 同步删），它们的 `sessionIds` 塞进 `archivedSessionIds`（日志一个字节不动，只是侧栏默认不显示），`initialized` 置 `false` 交给 `bootstrap()` 重建 |
| 2 | `deploy/image/prepare-workspaces.mjs` | 不用改逻辑，只是**必须排在 1 之后**：它补的是「登记里写了什么」，先摘后补才不会把刚删的目录又建回来 |
| 3 | `plugins/workspace-guard` 的 `ensureRoot` | `registry.create(root, '工作区')` 幂等兜底（表被清空、用户手删都能救回）；`create` 对已存在的 path **不改 title**，所以 bootstrap 生成的目录名 `workspace` 要显式 `setTitle` 成中文，只改「自动生成的那个名字」，用户自己改过的不碰 |

三条硬约束：

- **不搬文件**。旧目录只在**确认为空**时 `rmdir` —— 它对非空目录会抛 `ENOTEMPTY`，
  等于天然的保险，比任何 `rm -rf` 都稳。
- **不删会话日志**。只加进 `archivedSessionIds`，`sessions/` 里什么都不动，随时能取消归档。
- **可关、可重复**。`DSH_MIGRATE_WORKSPACES=0` 整个跳过；跑过之后没有违规记录，第二次启动
  直接输出「无需迁移」。原登记只在首次改动时备份成 `workspace.json.bak`，不覆盖。

### 5.3 用户看到的变化

| 场景 | 之前 | 之后 |
|---|---|---|
| 侧栏 | 「测试1」+「未分组」(8 个) | 只有一个「工作区」，8 个会话都在它下面 |
| 在某个会话里点「新会话」 | 回落到「测试1」（`/home/dsh/测试1`，可写层） | 落在 `/workspace` |
| 未分组里点「+」 | 没反应 | 「工作区」行有「+」，能建 |
| 发版 / 重建容器 | 老会话能开，里面的文件没了 | 都还在 |
| 那 4 个旧会话 | 挂在指向空目录的「测试1」下 | 进「已归档」，要看看得到，不再占位 |

### 5.4 实测（team-a，`colony:0.2.1-rc.5`）

```
迁移前  workspace.json : 测试1(/home/dsh/测试1) + 4 会话，initialized=true
        /home/dsh/测试1 条目数 = 0

跑脚本  已删除空的旧工作目录 /home/dsh/测试1
        移除 1 个旧工作区：测试1(/home/dsh/测试1)
        归档 4 个会话（日志保留，侧栏默认隐藏）
        会把 initialized 置 false，下次启动由 dsh 重建 /workspace 工作区

重建后  migrate-workspaces: 工作区登记已全部在 /workspace 下，无需迁移    ← 幂等
        prepare-workspaces: 1 个工作目录都在，无需补建
        [workspace-guard] 根工作区就位：/workspace
        工作区: [ '工作区 /workspace 会话数=8' ]，归档 4，initialized=true
```

`make verify-workspace-migrate` 31 条（旧登记摘除 / 归档去重 / `initialized` 判定 /
`/workspace-evil` 前缀陷阱 / 幂等 / 坏数据退化 / 空目录才删 / 根本身不动），
`make verify-workspace-guard` 20 条（新增：根工作区复用、英文名改中文、只登记一次）。

## 六、边界（还没做的）

- **会话产物本身仍要 S6**。工作区钉住了位置，但「agent 这一轮写了哪些文件」还没有归因和
  对象层备份。cwd 对了只保证「文件在宿主上」，不保证「跟着会话走」。
- **旧会话不改 cwd**。dsh 没有「把会话搬到另一个目录」的 API（`allowMigration` 是日志格式
  迁移 v0→v4，不是 cwd 迁移），所以那 4 个 `cwd=/home/dsh/测试1` 的会话只能归档。取消归档
  它们仍然打不开（cwd 不可解析），历史消息能看。
- **`prepare-workspaces.mjs` 保留且顺序敏感**。它补的是「登记里写了什么」，所以必须跑在
  `migrate-workspaces.mjs` 之后——反了就会把刚摘掉的旧目录又建回来。它现在只服务
  「宿主目录被清空」这一种场景，补回来的目录是空的，产物回不来。
- **`uv` 没装**。TODO 里和 python3 写在同一条（D8），本次只做了 python3。
- **pip 装包不进镜像**。写进卷意味着跟着团队走、换硬件也在；但要进**镜像**（所有团队共用）
  仍得改 Dockerfile，这是刻意的：不能让某个团队的临时装包影响别人。
