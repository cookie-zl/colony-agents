# 10 · 平台运维

前面九篇讲的是「怎么让它跑起来」。这一篇讲**跑起来之后怎么不出事**：团队一多、机器一挤，最先炸的是这五处——没配额、没对账、卷不回收、看不到状态、出了事查不到人。

一句话记住各自的分工：

| 层 | 谁负责 | 回答什么问题 |
| --- | --- | --- |
| `accounts.json` | 账号服务 + 控制面共同写 | 谁属于哪个团队、入口在哪、这个团队什么策略 |
| `state.json` | 控制面独占 | 谁最后活跃、谁睡着 |
| `nodes.json` | 控制面独占 | 有几台机器、每台还剩多少配额 |
| 真实容器 | docker / K8s | **最终事实**，前三份对不上时以它为准 |

## 一分钟版

```bash
export PATH=$HOME/.orbstack/bin:$PATH
make console            # 控制面：定时休眠、对账、归档都跑在它里面

make nodes              # 每台机器的配额余量
make state              # 每个团队的活跃度、配额、休眠/归档状态
make reconcile-check    # 对账：只看不动（漂移、缺失容器、孤儿卷）
make reconcile          # 对账：修复（缺失的重建，孤儿卷只报告）
make metrics            # Prometheus 指标
make archive TEAM=team-b  # 归档：卷打包 → 删容器删卷
make restore TEAM=team-b  # 从归档恢复
make snapshot           # 立刻拍快照（每小时也会自动拍）
```

## 一、资源配额：一个团队不能拖死整机

**不加会怎样。** 同机并排跑多个实例时，没有上限的容器谁都能吃满 CPU/内存。一个团队里 agent 跑全量编译，宿主内存被吃穿，Docker 的 VM 直接 OOM——**同机所有团队一起断**，而且日志上看不出是谁干的。

**怎么设。** 三处，从粗到细：

| 位置 | 作用 | 默认值 |
| --- | --- | --- |
| `compose.yaml` 的 `cpus` / `mem_limit` | 每个 dsh 容器的硬上限 | `1.5` 核 / `2g` |
| `nodes.json` 的 `cpuBudget` / `memBudgetGB` | 一台机器**可分配**的总量 | 8 核 / 8GB |
| `teams[].quota` | 单个团队的配额，建团队时按节点余量分配 | 取控制面默认值 |

预算是「可分配」而不是「物理」的地方：物理 8GB 的机器只写 7，留 1GB 给系统和其他进程。写满等于不设。

**建团队时的校验。** 控制面先算「这个节点已分配多少」，放不下就直接 400，不会先建再翻车：

```
所有节点都放不下（需要 1.5 核 / 2 GB）。当前占用：local 6/7 核、6.0/7 GB。
可以归档闲置团队，或调大 nodes.json 的预算
```

**实测生效。** 同一个宿主机上的两个实例：

```
dsh-team-a-dsh-1  NanoCpus=0           Memory=3221225472   # 改动前建的老容器
dsh-team-c-dsh-1  NanoCpus=1500000000  Memory=2147483648   # 按 1.5 核 / 2g 重建
```

注意：**已经建好的容器不会自动获得新限制**，要重建（`team-up.sh up <team> <port>`）才生效。

## 二、对账：三份状态一定会漂移

**漂移从哪来。** 手工 `docker rm`、机器重启、建团队时中途失败、有人 `compose down` 了但没改注册表。任何一种都会让「账号里有的东西」和「容器里有的东西」对不上，症状是**点进去永远 502，而且自己不会好**。

**对账做四件事**：

| 检查 | dry-run 结果 | fix 时怎么做 |
| --- | --- | --- |
| 注册表有、容器没了 | `missing: ["team-c"]` | 按登记端口重建；端口被占就换一个并写回注册表 |
| 容器在跑、注册表没有 | `orphans: [{team, project}]` | **只报告**，不自动删（里面可能有人正在用的会话） |
| 卷还在、项目没了 | `orphanVolumes: [{volume, team}]` | 只报告；带 `cleanupVolumes` 才删 |
| state 说睡着、容器在跑 | `stateFixed: ["team-b"]` | 以容器为准，删掉错误的 asleep 记录 |

**为什么不自动删孤儿。** 删错了不可恢复，而误报的代价只是一条日志。清理命令由人来下：

```bash
curl -s -H "X-Console-Token: $(cat deploy/orchestrator/console-token)" \
  -H 'Content-Type: application/json' -d '{"cleanupVolumes":true}' \
  http://127.0.0.1:9700/reconcile
```

**`desired` 字段决定要不要拉起。** 有人主动 `team-down` 的团队 `desired: down`，对账不会把它拉回来——那是人的决定，不是故障。只有 `desired: running` 的缺失容器才重建。

**节奏。** 每 10 分钟自动跑一次（`CONSOLE_RECONCILE_MS`），重建走同一个串行队列，不会和「新建团队」抢端口。

## 三、归档与备份：磁盘是慢慢满的

### 归档

休眠只是 `docker stop`，卷一直在盘上。团队开得越多、停用得越久，磁盘涨得越快。

**判据**：超过 `CONSOLE_ARCHIVE_AFTER_MS`（默认 30 天）没有任何访问，**且**容器当前没在跑。还在跑的不动。

**动作顺序不能反**：停 dsh → `tar czf` 打包卷 → `compose down -v` 删容器删卷 → 注册表留一条 `archived` 记录。先删卷再打包就永久丢数据了。打包失败时脚本因 `set -e` 退出，此时容器与卷都还在，可以直接重试。

**实测（team-c）**：

| 阶段 | 结果 |
| --- | --- |
| 归档前 | 卷内 328 个文件 |
| 归档包 | `archives/team-c-20261103-003210.tar.gz`，1.9MB |
| 归档后 | 容器 0 个、卷 0 个、注册表 `archived.file` 指向包 |
| 恢复后 | 卷内 329 个文件（dsh 启动时新写了一个），三容器全起、dsh healthy |

门户上归档过的团队显示「已归档」，按钮变成「恢复」。恢复走的是和新建完全相同的 `provision()`，配额、端口、入口都按注册表来。

**云上换法**：`docker run -v 卷` 打包换成 `kubectl exec` + `tar`，或直接把 PVC 快照到对象存储。归档记录里存的是「快照 ID」而不是本地路径。

### 备份

`accounts.json` 曾被一次误写搞坏过，那次就是全站登录故障——而且**没有备份可回滚**。现在：

- 启动、建团队、对账修复、进程收到 SIGTERM、每小时定时，各拍一次
- 落在 `deploy/orchestrator/backups/`，按 `accounts-<时间戳>.json` 命名，每类保留 48 份
- `state.json` / `nodes.json` 一起拍；`state.json` 其实可以随时重建，顺手存着是为了对比
- 市场台账 `packages.json` 与分享流水 `shares.json` 也拍——它们记着「谁装了什么、谁把什么给了谁」，丢了只能翻容器卷重建
- **`dsh.db` 单独用 `VACUUM INTO` 拍一份 `db-<时间戳>.db`**：技能/连接器/分享/操作日志/市场 token 的事实已经迁到这张 SQLite 里（见 `docs/12`）。WAL 模式下不能 `copyFileSync`，直接拷会拿到写了一半的状态
- 包操作日志已并入 `dsh.db` 的 `ops` 表，不再单独拍 `oplog.json`
- `inbox/`（别人投递过来、还没启用的包）**不拍**：它是可重新投递的运行态数据，体积也不可控
- **不包含** `secret.key`（模型密钥的主密钥 KEK）与 `audit/`（日志不是配置）。但注意：**`dsh.db` 的备份必须和 `secret.key` 一起存**——库里是 AES-GCM 密文，没有 KEK 解不开，所有团队密钥都要重配（见 `docs/18`）

恢复走 `store.mjs` 的 `restoreSnapshot()`，会**先给当前文件再拍一份**，避免「恢复」本身变成不可逆操作。

### 孤儿卷回收

一个团队是一个 compose 项目，不止一个卷：`dsh-home` 装会话、`caddy-data` 装入口状态、`dsh-node-modules` 装依赖缓存。团队归档或删掉之后三种卷都会留下，所以对账把三者都算进来：

```bash
make reconcile-check   # 只看：列出注册表里没有的团队的卷
make reclaim           # 真删；被任何容器挂着的会跳过，不会删出「起不来的容器」
```

## 四、门户：不用再开终端

`/__auth/home` 现在是一张运维面板，每个团队一行：

| 元素 | 说明 |
| --- | --- |
| 状态点 | 绿=运行中、灰=休眠中、黄=唤醒中/状态未知、归档态单独标 |
| 入口 | `team-c.localhost:8082` 或云上的 ingress 域名 |
| 配额 + 成员数 | 从控制面实时读，旧注册表没有 quota 字段时也能显示真实值 |
| 按钮 | 进入 / 休眠·唤醒·恢复 / 成员 / 审计 |

**成员管理**（`/__auth/members?team=`）：加人、移出、看角色。只有该团队 owner 或全局 owner 能操作。owner 不能被移出——先转 owner 再移。

**休眠策略**也在这个页面：长期在用的团队关掉自动休眠，临时团队把闲置阈值调到 10 分钟。策略写在 `accounts.json` 的 `teams[].policy` 里，控制面每轮扫描按团队取值，没配就退回全局默认。

## 五、审计：能查「谁在用」，查不了「谁说的」

这是本次唯一一处**没有完全满足需求**的地方，说清楚边界。

**能做到**：`forward_auth` 的 `verify` 是所有页面的必经之路，在那里记一条

```json
{"ts":"2026-11-02T16:30:50.119Z","user":"alice","team":"team-a",
 "method":"GET","path":"/","ip":"192.168.97.1","ua":"..."}
```

落在 `deploy/auth/audit/YYYY-MM-DD.jsonl`，按天切分，`grep` 就能查。门户 `/__auth/audit?team=` 直接看最近记录。

**做不到**：把每条消息标上作者。dsh 的事件流只有 `role: user/assistant`，`meta` 只在建会话时写一次，消息走 WebSocket 由 dsh 自己落盘——插件层拿不到上下文，也改不了事件结构。所有团队共用一份会话历史时，「这条是 Alice 还是 Bob 说的」在技术上无从区分。要突破只有 fork dsh 一条路。

**取舍**：把「消息级归属」降级成「访问级审计」，覆盖了运维真正会问的问题（谁什么时候在用哪个团队），且不引入 fork。这个边界写在这里，避免下一个人以为漏做了。

**去重规则**：只记 `/`、`/api/*`、`/__auth/*`；同一个人同一团队同一路径 5 秒内只记一条。静态资源不进日志，否则一个页面就几十条。安全事件（`login-failed` / `login-locked` / `password-changed`）走 1 秒窗口——5 秒去重会把"试了 5 次"压成一条，事后算不出攻击强度。

**保留期**：`AUDIT_KEEP_DAYS`（默认 30 天），auth 服务每 6 小时清一次过期文件。按天切文件只是让单个文件不至于打不开，**不等于自动轮转**；没人删的话一年就是 365 个文件，而审计里含用户名与 IP，留无限久既占盘又多一份泄露面。

## 六、登录加固

| 项 | 之前 | 现在 |
| --- | --- | --- |
| 会话过期 | 固定 12 小时，到点就踢 | **滑动续期**：过了一半时长才重发 Cookie，长期在用不会被踢 |
| 改密后旧会话 | 仍然有效 | 密码版本号 `pv` 加一，**所有旧 Cookie 立刻失效** |
| 忘记下线 | 只能改 secret 让所有人重登 | owner 可对单个账号 `POST /__auth/revoke`，只踢那一个人 |
| 首登改密 | 无 | 账号上 `mustChangePassword: true` 时，`verify` 直接拦住并跳改密页 |
| 密码规则 | 无 | 至少 8 位、两次一致、不能与旧密码相同 |
| 暴力破解 | 无限制，可无限猜 | 同一账户或同一 IP 15 分钟内错 5 次 → 锁 5 分钟，锁定期内**即使密码正确也拒绝**，返回 `429` + `Retry-After` |

`pv` 机制的好处是不用维护会话表：JWT 里带 `pv`，校验时比一下账号上的值，改密/踢人只是加一。

**实测**：

```
改密 → 302 /__auth/home
旧 Cookie 访问 home → 302 /__auth/login?rd=%2F__auth%2Fhome   # 立即失效
新 Cookie 访问 home → 200
用旧密码登录 → 401
```

## 七、观测

`GET /metrics`，Prometheus 文本格式。抓取配置见 `deploy/orchestrator/prometheus.yml`，认证用 `Authorization: Bearer <console-token>`（控制面同时认 `X-Console-Token`，curl 用后者方便）。

| 指标 | 类型 | 看什么 |
| --- | --- | --- |
| `dsh_team_up{team}` | gauge | 实例在不在跑 |
| `dsh_team_healthy{team}` | gauge | 起来了但是不是坏的 |
| `dsh_team_archived{team}` | gauge | 已归档（和「异常停掉」区分开） |
| `dsh_team_cpu_percent{team}` | gauge | 谁在吃 CPU |
| `dsh_team_mem_bytes{team}` | gauge | 谁在吃内存 |
| `dsh_team_idle_seconds{team}` | gauge | 多久没人用（该睡没睡） |
| `dsh_team_quota_cpus{team}` | gauge | 这个团队被分了多少 |
| `dsh_platform_quota_cpu_used/budget` | gauge | 整机水位，>90% 新建团队就会失败 |
| `dsh_platform_events_total{event}` | counter | `rebuild` 涨得快 = 有实例在反复挂掉 |

三条建议告警写在 `prometheus.yml` 的注释里，可以直接抄到 Grafana。

`docker stats` 有 1~2 秒开销，指标缓存 5 秒（`CONSOLE_METRICS_CACHE_MS`），抓取间隔 30 秒足够。

## 八、多机与 K8s

**`nodes.json` 就是调度表。** 加一台机器就是加一条：

```json
{
  "id": "ack-1",
  "label": "ACK 节点池",
  "provider": "helm",
  "domain": "dsh.example.com",
  "cpuBudget": 32,
  "memBudgetGB": 128
}
```

`provider: compose` 的节点用端口区分入口（本地），`helm` 的节点用 ingress 域名（云上，`port` 为 null）。

**调度按「剩余比例」而不是绝对余量。** 8 核剩 4 核（50%）会优先于 32 核剩 8 核（25%），避免大机器被小机器先填满后还继续往上堆。

**换成 helm 之后，上层代码一行没改。** `provision()` 里分叉：

| compose | helm |
| --- | --- |
| `team-up.sh up <team> <port>` | `helm upgrade --install dsh-<team> -f values-team.yaml -f <生成的覆盖>` |
| 等 `/__auth/health` | `kubectl rollout status` |
| `stop` / `start` 容器 | `kubectl scale --replicas=0/1` |

每团队的 values 覆盖文件由控制面生成（`deploy/orchestrator/helm-values/<team>.yaml`），只写差异项：ingress host、publicUrl、配额。基础规格留在 `values-team.yaml`，改一次对所有团队生效。

本地没有集群时用 `CONSOLE_HELM_DRYRUN=1`：走 `helm template` 校验能渲染出正确清单，不真的部署。实测产物：

```
kind: Deployment   replicas: 1
  limits:    cpu: "1.5"  memory: "2Gi"
  requests:  cpu: "0.38" memory: "1Gi"
kind: Ingress      host: "team-d.dsh.example.com"
kind: PersistentVolumeClaim ×2
```

**云上必须补的一件事**：账号服务要常驻，且它能调 `scale`。`replicas: 0` 之后 Service 没有 endpoint，Ingress 只会返回 503，**没有任何进程能接住唤醒请求**。本地这套「入口常驻、只停本体」的形状在上云后反而正好。

## 九、没做的

| 项 | 现状 | 说明 |
| --- | --- | --- |
| 按人限流 | 未做 | 现在只有节点级预算，没有「每个人最多建几个团队」 |
| 审批流 | 未做 | 建团队只要 owner 点一下，大团队应该走审批 |
| 真实 IdP | 未做 | 仍是自研密码；换 oauth2-proxy 时替换 `server.mjs`，Caddy 侧契约不变 |
| 消息级归属 | **做不到** | 见第五节，需要 fork dsh |
| 归档到对象存储 | 未做 | 现在落在本地 `archives/`，云上应传 OSS/S3 后删本地 |
| **删除团队** | 未做 | 只有归档。归档后 `accounts.json` 里还留着团队记录与成员关系，想彻底消失得手改注册表 |
| **workspace 进归档** | 未做 | 归档只打 `dsh-home` 卷；宿主的 `deploy/compose/workspace-<team>/` 不在包里（用户在里面放的文件换机器就没了） |
| 用量计量 | 未做 | 只有 CPU/内存瞬时值，没有「谁这个月消耗了多少 token / 多少机时」 |
| 告警通知 | 未做 | 休眠、归档、重建失败都只写日志，没人主动知道 |
| 程序化访问 | 未做 | 没有个人 API Token，CI / 脚本只能用控制面 token 或账号密码 |
