# 07 · 多团队与账号

方案 1：**必须登录、必须属于某个团队，才能看到该团队的对话。** 一个团队 = 一个实例。

这篇写三件事：怎么落地（本地 + K8s）、SSO 与 dsh token 的接缝怎么补、以及"会话里为什么区分不出是谁说的"。

## 为什么是「一团队一实例」

dsh 的会话存储里**没有 user / tenant 维度**，会话列表是内核 UI。所以"团队内共享、团队间隔离"只能靠物理隔离：

| 概念 | 本地 | K8s |
| --- | --- | --- |
| 一个团队 | 一个 compose 项目 `dsh-team-a` | 一个 Helm release `dsh-team-a` |
| 实例进程 | 容器 `dsh-team-a-dsh-1` | 1 个 Pod（`replicas: 1`） |
| 会话与凭据 | 卷 `dsh-team-a_dsh-home` | PVC（`ReadWriteOnce`） |
| 工作区 | `deploy/compose/workspace-team-a/` | 另一个 PVC |
| 入口 | `team-a.localhost:8080` | 1 个 Ingress host |

三者（项目名 / 数据卷 / 工作区）任意共享，就不再是两个团队。`replicas: 1`、`RWO`、`Recreate` 仍然是硬约束。

## 一、账号与团队：现在跑的是什么

`deploy/auth/` 是一个零依赖的账号服务（只用 node 内置模块，没有 npm install，镜像 60MB 左右）。它不碰 dsh，只回答一个问题：**这个请求以谁的身份放行**。

| 端点 | 作用 |
| --- | --- |
| `/__auth/verify` | Caddy `forward_auth` 的子请求：200 + `X-Auth-User` / `X-Auth-Teams`，或 401 / 403 |
| `/__auth/login` | 登录页 + 下发本 host 的会话 Cookie（12h） |
| `/__auth/home` | 门户：我加入的团队（管理员额外看到其他团队和「新建团队」入口） |
| `/__auth/members` | 成员花名册。团队成员可读，owner 才有增删按钮 |
| `/__auth/members/add`、`/remove`、`/role` | 加人、移人、改角色。只接受团队 owner（或管理员） |
| `/__auth/join` | **已关闭自助加入**，固定返回 403 并提示联系该团队 owner |
| `/__auth/teams` | 新建团队，只有管理员可通过（门户里普通成员看不到入口） |
| `/__auth/sso`、`/__auth/sso-callback` | 跨 host 的一次性票据，换团队时不用重新输密码 |
| `/__auth/bootstrap` | 用当前实例的 token 换 dsh 自己的 Cookie |

三个设计取舍，都知道原因：

- **Cookie 按 host 隔离**。浏览器不会把 `Domain=localhost` 的 Cookie 共享给子域，所以每个团队 host 各有一份会话；换团队靠票据（60 秒、一次性、绑定目标团队）。
- **会话签名密钥全实例共享**（`deploy/auth/secret`）。这是票据能在 team-a 签发、team-b 验签的原因；换掉它等于让所有人重新登录。
- **成员关系存在 `accounts.json`**，两个实例读同一份文件，所以"在哪个团队里加人都算数"。

已经初始化两个团队：

| 团队 | 名称 | 入口 | 成员（角色） |
| --- | --- | --- | --- |
| `team-a` | 研发组 | `http://team-a.localhost:8080/` | alice（owner）、bob（成员） |
| `team-b` | 产品组 | `http://team-b.localhost:8081/` | alice（成员）、carol（owner） |
| `team-c` | 数据组 | `http://team-c.localhost:8083/` | alice（owner） |

演示账号（密码统一 `dsh-demo-1234`）：`alice`（管理员）、`bob`、`carol`、`dave`。**dave 刻意没有任何团队**，用来验证"必须 owner 添加才能进"。

实测过的完整链路：

| 场景 | 结果 |
| --- | --- |
| 未登录访问 `team-a:8080/` | 302 → `/__auth/login?rd=/` |
| 密码错误 | 401 + 表单提示 |
| alice 登录 | 302 → `/`，下发 `dsh-sso`；再 2 跳换成 dsh Cookie，最终 200 |
| dave 登录 team-a | 403 + 「不是研发组的成员」，门户里没有任何「加入」按钮 |
| dave 强行 `POST /__auth/join` | 403，提示找 owner |
| dave 打开 team-a 成员页 | 403（不是成员，看不到花名册） |
| bob 打开 team-a 成员页 | 200，只有花名册，没有「添加成员」表单 |
| bob 强行 `POST /members/add` | 403 |
| bob 强行 `POST /__auth/teams` | 403（只有管理员能建团队） |
| alice 把 dave 加进 team-c | 302；dave 随后登录 team-c 成功，200 |
| alice 降级自己、dave 成为唯一 owner 后再降级 | 400「团队至少要有一个人是 owner」 |
| dave（唯一 owner）移出自己 | 400「不能移出最后一位 owner」 |
| alice（只属于 team-a）访问 team-b | 302 → team-b 登录页，不放行 |
| carol 打开 team-a 成员页 | 403（不是该团队成员） |
| bob 强行 `POST /__auth/packages/share` | 302 带 err「只有这个团队的 owner 可以安装或发布」 |
| carol（team-b owner，不在 team-a）把包分享给 team-a | 302 带 err「你不在「研发组」里，不能直接投递」——跨租户投递只能由管理员发起 |
| alice（team-a owner）把 `ad-report-audit` 投递给 team-c | 302；team-c 出现「待接收」，卷里**没有**这个技能；owner 启用后才落卷，已装列表标「来自 team-a 分享」，分享记录 `team-a → team-c` |
| bob 启用一条属于 team-c 的分享 | 302 带 err「只有这个团队的 owner 可以安装或发布」 |
| alice 把表单里的 team 改成 team-a、id 指向 team-c 的待接收项 | 302 带 err「这条分享不属于当前团队」——授权按记录里的 `to` 判，不认表单 |
| 退出登录 | 清 Cookie，`/` 重新 302 到登录页 |

## 角色与权限

两层角色，互不干扰：

| 层 | 取值 | 存在哪 | 能做什么 |
| --- | --- | --- | --- |
| 全局 | `admin` / `member` | `users[].role` | 管理员才能**新建团队**、强制下线、看全部团队的审计 |
| 团队内 | `owner` / `member` | `teams[].roles` | owner 才能**加人、移人、改角色、调休眠策略、装/卸/发布/分享技能与连接器、启用或拒收别人投递过来的包**；成员只能进门和看花名册（待接收项也可见，只是没有按钮） |

角色挂在团队上而不是账号上，所以同一个人可以是 A 组的 owner、B 组的普通成员（alice 现在是 team-a/team-c 的 owner、team-b 的成员）。

三条不变量：

1. **不能自助加入**。门户不再列"可加入的团队"，`/__auth/join` 直接 403，只有 owner 能把人加进来。
2. **至少保留一位 owner**。把最后一位 owner 降级或移出都会被 400 挡住，避免团队变成没人能管。
3. **`teams[].owner` 跟着 `roles` 走**。它是历史字段，控制面还在读，改角色时会一并同步，不留两套真相。

生产请把这一层换成公司 IdP。这个服务的三个出口（`X-Auth-User` 头、组判断、登录跳转）与 oauth2-proxy 的 `--allowed-groups` 一一对应，Caddy / Ingress 那一侧不用改。

### 登录防护

密码登录与改密都按「账户 + 来源 IP」双维度计数：

| 项 | 默认值 | 环境变量 |
| --- | --- | --- |
| 触发阈值的失败次数 | 5 | `LOGIN_MAX_FAILURES` |
| 锁定时长 | 300 秒 | `LOGIN_LOCK_SECONDS` |
| 计数窗口 | 900 秒 | `LOGIN_WINDOW_SECONDS` |

超过阈值返回 `429` 并带 `Retry-After`。**锁定期内即使密码正确也拒绝**——否则攻击者对每个候选密码只需验一次，"锁定"就没有意义了。之所以两个维度都数：只按 IP 挡不住换 IP 打同一个账号，只按账号挡不住撞库打一片账号。

状态在内存里，进程重启即清空；每个团队是独立的 auth 容器，所以 A 团队被锁不影响 B 团队（这是隔离的副作用，不是漏）。审计里 `login-failed` / `login-locked` 秒级去重（普通访问是 5 秒），能数得出攻击强度。

> 已知边界：没有验证码、没有 MFA、密码只校验长度（默认 8）。要防更认真的对手，把这一层换成公司 IdP 或在 Caddy 上加 `rate_limit`。

## 二、本地：两个团队已经起来

```bash
export PATH=$HOME/.orbstack/bin:$PATH          # 这台机器的 docker 在 OrbStack 里

make up                                        # 起 team-a（默认团队）
./deploy/compose/team-up.sh up    team-b 8081  # 起 team-b
./deploy/compose/team-up.sh sync  team-a       # dsh 重启后补一次 token
./deploy/compose/team-up.sh ps
./deploy/compose/team-up.sh down  team-b       # 停，保留卷
./deploy/compose/team-up.sh destroy team-b     # 停并删卷

# 绕过登录的原始 token（排障用）
make token
```

`*.localhost` 在 macOS / Linux 都解析到 127.0.0.1，不需要改 hosts。

不同实例的**数据卷完全独立**（`dsh-team-a_dsh-home` / `dsh-team-b_dsh-home`），dsh Cookie 的签名密钥各在各的卷里，串不过去——这是"团队间隔离"的物理基础，也是账号层之外的第二道墙。

三个坑（都已修，写进代码里以免重复踩）：

1. **容器内监听端口必须等于 `EDGE_PORT`**。Caddy 的站点地址是 `http://{$DSH_SITE_HOST}:{$EDGE_PORT}`，所以 compose 映射要写 `${EDGE_PORT}:${EDGE_PORT}`；写成 `8081:8080` 会得到"端口通但没响应"（curl exit 52）。
2. **补 token 的 redirect 必须放行带 `?token=` 的请求**，否则会把"换 Cookie 的那一下"也拦掉，形成 302 死循环。`@noDsh` 用的是表达式，同时排除了 `token=`。
3. **Caddyfile 是挂载进去的，但 `admin off` 不会热加载**，改完必须重建 edge 容器；`team-up.sh up` 已经每次都重建。

## 三、K8s：teams.txt 一行一个团队

```bash
# 一次性前置
kubectl create namespace ai-tools
kubectl -n ai-tools create secret generic dsh-deepseek-key --from-literal=DEEPSEEK_API_KEY='sk-xxx'
kubectl -n ai-tools create secret docker-registry harbor-pull --docker-server=... --docker-username=... --docker-password=...

# 每个团队一条 oauth2-proxy，组放行靠它
#   --allowed-groups=dsh-team-a
#   --provider / --client-id / --client-secret 指向公司 IdP（OIDC）
# 然后用清单发布：
NAMESPACE=ai-tools IMAGE_REPOSITORY=harbor.example.com/dsh/colony-agents \
  ./deploy/helm/deploy-teams.sh --dry-run      # 先看渲染结果
./deploy/helm/deploy-teams.sh
```

`deploy/helm/teams.txt` 三列：团队名、浏览器 host、该团队 SSO 网关 host。团队名同时决定 release 名、IdP 组名（`dsh-<团队名>`）、卷名前缀——**改名等于换实例**。

模板在 `deploy/helm/values-team.yaml`，与默认 values 的差别只有四处：`marketplace=off`、`permissionMode=workspace-write`、卷更大、`forwardAuth` 打开。

验收（Pod Running ≠ 可用）：

```bash
kubectl -n ai-tools exec deploy/dsh-team-a -- dsh --profile web --dump-config | grep '^# =='
curl -s -o /dev/null -w '%{http_code}\n' https://dsh-team-a.example.com/   # 期望 401
```

## 四、token 与 SSO 的接缝（一定会踩）

SSO 通过之后，浏览器访问首页**仍然是 401**：dsh 不认 IdP 的会话，它只认自己发的 `dsh-auth-*` Cookie。这个接缝必须在网关补，两种补法：

| 做法 | 成本 | 代价 |
| --- | --- | --- |
| **一次性链接**：把带 token 的 URL 一对一发给成员，换 30 天 Cookie | 0 | 每次重启后，**新设备/新人**需要重新发一次（老人 Cookie 还有效，因为签名密钥在卷里） |
| **发布后同步 token**：把当前 token 写进 ingress 的 redirect 规则，无 Cookie 自动 302 | 0.5 人日 + 每条发布跑一条命令 | 依赖集群允许 `configuration-snippet` |

```bash
# 发布后取当前 token，并让「没有 dsh Cookie 的请求」自动带上它
TOKEN=$(kubectl -n ai-tools logs deploy/dsh-team-a | grep -o 'token=[A-Za-z0-9_-]*' | tail -1)
kubectl -n ai-tools annotate ingress dsh-team-a --overwrite \
  nginx.ingress.kubernetes.io/configuration-snippet="if (\$http_cookie !~* \"dsh-auth-\") { return 302 https://dsh-team-a.example.com/?$TOKEN; }"
```

本地这一层已经自动化了：`team-up.sh up` 在 dsh 健康后把 token 写进 `deploy/auth/tokens/<team>`，账号服务在「有登录态但没有 dsh Cookie」时读它并 302。所以本地不需要手工发链接；dsh 重启后跑一次 `./team-up.sh sync <team>`（`make restart` / `make reload` 已内置）。

**不要做的事**：自己按 `.credentials.yaml` 里的 secret 去 mint Cookie。那等于实现一个 dsh 内部格式的副本，dsh 一旦改签名结构就全线登录失败——而它没有任何兼容承诺。

## 五、为什么「谁说的」区分不了

你的直觉是对的：**如果身份能写进对话日志，就能归属。** 问题是 dsh 现在没有这个字段，也没有留给你的注入点。三条证据（都在容器里查过）：

| 事实 | 证据 |
| --- | --- |
| 会话事件只有角色，没有作者 | `dsh-session` 类型里是 `role: user / assistant / tool`，无 `author` / `userId` |
| 会话 header 有 `meta`，但只能由**创建方**在创建时写入 | `createSession({ meta })`，`meta.cwd` 必填；事后没有"补写作者"的 API |
| 连"哪个浏览器"都不分 | `.anonymous-user-id` 是**每个 `$DSH_HOME` 一个** UUID（给遥测/回执关联用），不是一人一个 |
| 消息走 WebSocket | 网关只能看到"某用户在某时刻连上了某个实例"，看不到每条 prompt 的内容与归属 |

所以"记录谁说的"有两条路，都很贵：改 dsh 内核（不可持续），或写一个前端插件在每条消息上打标 + 后端配合存（跨版本脆弱，且 UI 本来就没有作者位）。

**能拿到的三档，按成本排：**

| 档 | 能回答 | 成本 |
| --- | --- | --- |
| 连接级审计：网关 access log 记 `用户 / 时间 / host` | "昨天下午谁在用团队 A" | 0 代码 |
| 会话命名约定：`alice-排查线上慢查询` | 粗粒度归属（靠自觉） | 0 |
| 一人一实例（方案 2） | 真正的"这是我的对话" | 见方案 2 的成本 |

对"团队共享上下文"这个目标来说，第二档通常就够：**共享的意义是可见，不是追责**。真要追责（比如生产改配置），该走的是命令级审计——dsh 的工具调用是可拦截的，那才是插件该补的地方，不是会话 UI。

## 六、加入 / 退出团队的生效时间

| 动作 | 操作 | 生效 |
| --- | --- | --- |
| 加入 | IdP 组 `dsh-team-a` 加人 | 下次访问即通过（网关每次请求都验） |
| 退出 | 从 IdP 组移除 | 取决于 oauth2-proxy 的会话 Cookie 有效期（默认 2h，可缩短到 15min） |
| 立即失效 | 缩短 cookie 有效期 + 删除该用户的 dsh Cookie？做不到按人删 | 只能靠网关，别让 Pod 可直连 |
| 离职 | 移出所有组 | 同上；**他在共享卷里留下的内容不会消失** |

本地对应关系更直接：**加入 = `accounts.json` 里 `users.<id>.teams` 加一项，退出 = 删一项**，因为 `verify` 每次请求都重新读文件，改完立刻生效（不需要重新登录）。这也说明 `accounts.json` **只是个演示实现**：没有审批、没有并发保护、账号跟随仓库走。生产上它应该被 IdP 完全替代。

必须补的一条：**NetworkPolicy 禁止绕过网关直连 Pod**，Service 保持 `ClusterIP`。否则任何拿到 Pod IP 的人都能跳过 SSO。

## 七、上线前 checklist

- [ ] 每个团队的 `ingress.host` 与 `dsh.publicUrl` 完全一致
- [ ] 每个团队一条 oauth2-proxy，`--allowed-groups` 与 IdP 组名一致
- [ ] `marketplace=off`（共享实例里"能开页面"等于"能往主进程装代码"）
- [ ] `permissionMode` 不是 `danger-full-access`
- [ ] 团队实例里没有任何个人凭据（模型 Key、git token）
- [ ] NetworkPolicy 已禁止直连 Pod
- [ ] token 分发/同步有唯一渠道（不进群公告、不进文档）
- [ ] 成员知道：**会话共享 ≠ 同时编辑**，一个话题开一个 session，别挤在一起
