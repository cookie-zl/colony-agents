# 对象层：大块二进制统一从这里进出

归档包、会话日志、技能包（docs/13）、以后的产物快照，都是「大块、只追加、按内容校验」的二进制。
它们不该落在控制面自己的磁盘上，也不该进事务库。本文记的是**已经做完的 L2**（归档包进对象层）
以及它为什么这样做、怎么验证的。

## 一、为什么要这一层

在 L2 之前，归档是这么走的：

```
team-up.sh archive → tar 落到 deploy/orchestrator/archives/ → down -v 删容器删卷
```

`down -v` 之后，那个 tar 就是**唯一副本**。它落在控制面所在的磁盘上，机器坏掉就没了。
更要紧的是：**「容器可丢」这个前提要求数据必须存在容器之外**，而这个 tar 恰恰是我们第一个
真正需要外置的负载。不先把它挪出去，「沙箱可以销毁」在架构上就不成立。

所以这一层的定位是：**存储实现细节的收口点**。调用方只说「把这个文件放进去」「把这个键取回来」，
不知道也不关心背后是本地目录还是 OSS。`docs/ROADMAP.md` L5（换 OSS）只改本文后面列出的四个函数。

## 二、对象键设计

```
archives/<team>/<sha256>           归档包
```

- **内容寻址**：键的末段就是内容的 sha256。同一份内容重复 `putFile` 幂等，不会产生第二份副本。
- **落盘插分片**：`objects/archives/team-a/93/934c19a0…`。digest 前两位当子目录，避免单目录堆几万文件。
  分片位置和 OSS 的 `<prefix>/<xx>/<digest>` 习惯一致，将来迁移对象键不用重写。
- **前缀带 team**：`archives/team-a/…` 让「按团队清理/统计」变成一个目录操作，不用扫全库。

## 三、接口（就这五个）

`deploy/orchestrator/objects.mjs`：

| 函数 | 作用 | 备注 |
|---|---|---|
| `putFile(src, {prefix})` | 移入对象层，返回 `{key, digest, bytes, storage}` | **是「移入」不是「复制」**，成功后源文件不存在 |
| `materialize(key, dest)` | 把对象取回本地真实路径 | tar 只认路径，所以恢复前必须落一份临时副本 |
| `statObject(key)` | `{bytes, digest}` 或 `null` | 不存在返回 null，不抛 |
| `objectExists(key)` | 布尔 | 键残缺时按不存在处理，让调用方走降级而不是崩 |
| `deleteObject(key)` | 布尔 | |

两个实现细节值得记住：

- **sha256 一律流式算**。归档包可能几百 MB，`readFileSync` 会把控制面直接撑爆。
- **`renameSync` 失败（EXDEV）退化成流式拷贝再删源**。暂存目录和对象目录可能不在一个分区，
  跨设备 rename 必然失败，这是必踩的一脚。

## 四、归档流程改造

```
team-up.sh archive <team>          # 停 dsh → tar 卷 → down -v → 打印 tar 路径（没变）
  ↓  tar 落到 archives/.staging/（暂存：失败重试不与上一次残包混淆，也不会被误认为正式归档）
storeArchive(file, team)           # runtime.mjs（新增）
  ↓  putFile → 流式 sha256 → 移入 objects/archives/<team>/<dd>/<digest>
accounts.json: teams[<team>].archived = { at, key, digest, bytes, reason }
```

三个必须保持的性质：

1. **上传失败不丢数据**。走到这一步卷已经被 `down -v` 删了，tar 就是唯一副本。
   所以 `putFile` 抛错时只允许「换位置」——搬到 `archives/` 并按旧格式记账，返回里带 `degraded` 原因——
   **绝不允许删掉**。
2. **老记录兼容**。恢复时优先按 `key` 取，没有 `key` 就退回原来的本机 `file` 路径。
   不认老记录等于让升级前已归档的团队永久回不来。
3. **恢复用的临时文件用完即删**。`materialize` 到 `archives/.restore-*`，`team-up.sh restore` 读完就删，
   否则每次恢复都在磁盘上留一份整包。

## 五、验证方式

`make verify-objects`（`verify-objects.mjs`，26 条断言），覆盖：

| 断言组 | 验什么 |
|---|---|
| 键与分片 | `archives/team-x/<sha>` 落盘位置正确，digest 前两位成了子目录 |
| 往返一致 | 用**真实归档包**（`team-c-20261103-003210.tar.gz`，2 MB）put → materialize → 逐字节比对 |
| 幂等去重 | 同内容 put 两次，库里只有一份，第二次源文件被丢弃 |
| 大小上限 | 大文件走流式，不把内容读进内存 |
| 降级分支 | `CONSOLE_OBJECTS_DIR=/dev/null/objects` 复现上传失败，断言 tar 仍在、字节不变、返回带 `degraded` |
| 残缺键 | `objectExists('只有文件名')` 返回 false 而不是抛 |

端到端（临时团队 `e2e`，跑完已清理）：

```
卷里写 marker-e2e-2099 → archive 2 015 239 字节 → 键 archives/e2e/934c19a0…c75f04
  → restore 按 key 恢复 → 容器 healthy、门户 200、marker-e2e-2099 原样回来
```

## 附：一个环境坑

macOS 自带 BSD `grep` 不支持 `\|`，`grep "archive\|restore"` 会**静默返回空**（不是报错），
排查「代码里明明有却搜不到」多半是这个原因。脚本里一律用 `grep -E`。
