# 16 · 数据存放与重启存活

回答三个问题：**每类数据落在哪、什么时候写、哪种重启会丢**；**agent 参数为什么重启就回默认**；
**团队能不能不休眠**。结论来自容器内实测（删容器重建后 `ls` 对比）与 dsh 源码。

## 一句话结论

会话正文已经是「卷 + 对象层」双份，容器怎么重启都在；**但 agent 参数和会话的 cwd 目录不在持久层**，
前者每次启动被镜像覆盖，后者在容器可写层里随重建蒸发。产物安不安全取决于写在哪——`/workspace` 安全，
`/home/dsh/**` 不安全。

## 一、存放位置总表

「容器重建」= 发版 `compose up -d --build`、删容器后唤醒（实测 43 s），可写层重置、卷不动。
「宿主重启」= 宿主机 / OrbStack VM 重启，卷与 bind mount 都在，但容器不会自己回来（休眠是 `docker stop`）。
「归档」= 闲置 30 天且容器已停 → `tar` 进对象层 → `down -v` 删卷。

| 数据 | 落地位置 | 写入时机 | 容器重建 | 宿主重启 | 归档后 |
|---|---|---|---|---|---|
| 会话事件流 | 卷 `sessions/--<cwd>--/<sid>/session.vN.jsonl.zstd` | 每 checkpoint，append+fsync | ✅ 在 | ✅ 在 | ✅ 从对象层 restore（docs/15） |
| 会话分片副本 | 对象层 `objects/sessions/<team>/<sid>/` | 5 分钟扫描，增量 ≥256 KiB 或闲置 10 分钟或睡前强制 | ✅ 在（≤5 min 前的可能缺） | ✅ 在 | ✅ 恢复源 |
| 附件 / 图片 | 卷 `attachments/v1/objects/<sha256>` | 发送时立即 fsync | ✅ 在 | ✅ 在 | ❌ 无对象层副本 |
| agent 产物（写到 `/workspace`） | **宿主** `deploy/compose/workspace-team-X/` | 工具执行时立即 | ✅ 在（bind mount） | ✅ 在 | ✅ 在（**但不在归档包里**，C6） |
| agent 产物（写到 `/home/dsh/**`） | 容器可写层 | 工具执行时立即 | ❌ **丢** | ❌ 丢 | ❌ 丢 |
| 工具输出 > 64 KB | `/tmp/dsh-spill-XXXX/` | 工具执行时溢出 | ❌ 丢 | ❌ 丢 | ❌ 丢（C3） |
| **agent 参数**（模型 / preset / 工具 / shell / web-search / subagent） | 卷 `profiles/web/cordis.patch.yml` | UI 改设置即时写盘 | ❌ **被镜像覆盖** | ❌ 同左 | ❌ 同左 |
| 市场装的 MCP | 卷根 `cordis.patch.yml` | 安装时写标记块 | ✅ 在 | ✅ 在 | ✅ 在（卷里 → 进归档包） |
| 技能包 | 卷 `skills/` | 安装时物化 | ✅ 在 | ✅ 在 | ✅ 在（市场表可重新物化） |
| 凭据 `.credentials.yaml` | 卷根 | 首次配置 | ✅ 在 | ✅ 在 | ✅ 在 |
| 会话索引 / 同步进度 | SQLite `deploy/orchestrator/dsh.db`（宿主） | 跟随同步 | ✅ 在 | ✅ 在 | ✅ 在 |
| 归档包 | 对象层 `objects/archives/<team>/<sha256>` | 归档时 tar → 校验 → 入层 | ✅ 在 | ✅ 在 | ✅ 恢复源 |
| 团队 / 成员 / 策略 | 宿主 `deploy/auth/accounts.json` | 建团队、加成员 | ✅ 在 | ✅ 在 | ✅ 在 |
| 审计 | 宿主 `deploy/auth/audit/*.jsonl` | 每请求，节流 20 s | ✅ 在 | ✅ 在 | ✅ 在 |
| 控制面自身状态 | 宿主 `deploy/orchestrator/state.json` | lastSeen / asleep 变更 | ✅ 在 | ✅ 在 | ✅ 只是缓存 |

一句话记法：**卷（`dsh-home`）+ 宿主 bind（`workspace-team-X`）+ 宿主 SQLite/Object 是持久层；
容器可写层和 `/tmp` 是草稿纸。** 归档只打 `dsh-home` 一个卷，所以 bind 目录反而不在包里。

## 二、agent 参数为什么每次重启归零

dsh 的写入目标只有一个：**active profile patch**。`dsh-config-editor` 的原话是

> Edits target the active profile patch. Home patches and command-line overlays are read
> for precedence but are **not write targets**.

对应到我们的目录：

```
$DSH_HOME/cordis.patch.yml          ← Home patch：优先级高、只读、不被 seed 覆盖（市场 MCP 写这里）
$DSH_HOME/profiles/web/cordis.patch.yml  ← active profile patch：UI 的所有设置写这里
```

而 `deploy/image/entrypoint.sh` 的 seed 是 `refresh`：

```sh
rm -rf "${DSH_HOME}/profiles/web"      # ← UI 改的一切在这里被删掉
cp -a "${DSH_SEED_SRC}/web" "${DSH_HOME}/profiles/web"
```

所以链是：**UI 改模型/温度/preset/工具开关 → 写 `profiles/web/cordis.patch.yml` → 下次启动被镜像覆盖 →
回到镜像默认**。`profiles/web/cordis.patch.yml` 里那段注释（"UI 里切模型写回的 cordis.patch.yml 会在下次
重启时被冲掉"）就是这件事的自白。

会话内部不受影响：每个会话的 header 记着自己的 cwd 与选型，翻历史记录还能看到「当时用的是哪个模型」。
**丢的是「团队默认值」和「我这台机器上的偏好」**，表现是发版后用户发现模型换回去了、权限模式变了、
自己开的工具开关没了。

### 三条改法，按推荐顺序

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 控制面存 + 生成 Home patch**（推荐） | `team_agent_config` 表存团队级 agent 参数；唤醒前渲染成 `$DSH_HOME/cordis.patch.yml` 的标记块（与市场 MCP 同一套写法）；UI 改动通过 `/agent-config` 接口回写库 | 要定「哪些字段允许用户改」，且与市场块共用同一文件需分段管理 |
| B. `DSH_PROFILE_SEED=once` | 只在首次铺 profile，之后不覆盖 | 镜像升级带的新插件永远进不来，线上与仓库脱钩（entrypoint 注释里明确不推荐） |
| C. seed 前备份用户行、seed 后按 id 合并回去 | 保住 UI 改的那几行 | patch 是整块覆盖，按 id 合并要自己实现 diff，dsh 升级容易失配 |

## 三、会话 cwd 不在持久层（本轮实测）

容器 `pwd` 是 `/workspace`、`HOME` 是 `/home/dsh`。默认新建会话落在 `/workspace`，安全；
但 UI 的目录选择器允许选任意路径——team-a 里就有一个 `path: /home/dsh/测试1` 的 workspace。

实测：备份卷 → `docker rm -f dsh-team-a-dsh-1` → `POST /wake`（43 s 起来）→

```
ls /home/dsh        # 没有「测试1」
ls .dsh/sessions/   # --home-dsh-~6D4B~8BD51-- 还在，两个会话文件都在
```

dsh 对这种情况的处理（`dsh-workspace/lib/index.js:887`）：

```js
const path = await realpathNormalize(header.cwd)
if (!(await stat(path)).isDirectory()) → invalidSessionPaths.set(id, `cwd '${cwd}' is not a directory`)
// ENOENT 分支：同时进 missingSessionPaths 与 invalidSessionPaths（"does not resolve"）
```

`missingSessionPaths` 在 `candidateMatches` 里放行，所以会话**仍会出现在侧栏**、只是目录缺失；
真进去跑命令时 bash 的 cwd 不存在，产物也回不来。等于「记录在，现场没了」。

改法：新会话默认钉在 `/workspace`（或 `/workspace/<project>`），并在 provision / 唤醒时
`mkdir -p` 一遍历史会话里出现的 cwd，避免出现半可用状态。

## 四、能不能不休眠

能。休眠是**每团队策略**，不是全局硬编码（`console.mjs:1320`）：

```js
Object.entries(data.teams).filter(([, t]) => !t.archived && t.policy?.autoSleep !== false)
```

在 `deploy/auth/accounts.json` 对应团队下加一行即可（`registry()` 每次读文件，下一轮扫描生效）：

```json
"team-a": { "policy": { "autoSleep": false } }
```

或者不关、只放宽：`"policy": { "idleMs": 43200000 }`（12 小时）。

成本（本机实测）：空载 **349 MiB / 2 GiB**、CPU 0.3%。VM 共 8.4 GB / 8 核，预算 7 GB，
两个团队常驻约 0.7 GB，完全放得下；四个才开始吃紧。

**但不建议现在就全关**，因为休眠判据只有「闲置 30 分钟 + CPU < 2% + 已跑满 5 分钟」。
等模型响应、等审批、等用户回话时 CPU 本来就在 1% 上下，一个跑 30 分钟以上的长任务
会在你离开后被判成闲置杀掉。正确顺序是先把判据补上「有活跃 turn 不睡」，再考虑关休眠。
