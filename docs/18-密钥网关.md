# 18 · 密钥网关

模型 API Key 不放容器里，容器只拿一枚可吊销的 token，请求从容器发出来、由控制面代发。
这篇记为什么必须这样、改了什么、验证到什么程度。

## 一、为什么不能靠「加密存起来」

起因是 `team-secrets.json`（明文 JSON）通过 env 注入容器。原以为「加密 + 换个存放位置」就能解决，
读了 `dsh-credentials-local` 的官方文档才发现这条路走不通，原文两句：

> Only your OS user can read the file, but **agent tool processes run as that same user, so this store cannot isolate secrets from the agent**.

> Choose a different store when a deployment must provide keys away from its own agent — **file permissions cannot do that**, because the agent's tool processes run as your OS user.

实测把这条坐实了。dsh 自己有一层 env scrub（`dsh-subprocess/lib/index.js:32`）：

```js
const SENSITIVE_ENV_PATTERN = /KEY|PASSWORD|SECRET|TOKEN/i;  // 子进程 env 里抹掉凭据形状的名字 + 全部 DSH_*
```

所以 agent 跑 `env` 看不到 key——这一层是有效的。但同 uid 能直接读主进程：

```
$ docker exec <容器> sh -c 'tr "\0" "\n" < /proc/1/environ | grep -E "TOKEN|KEY"'
MARKET_API_TOKEN 34 字符
DEEPSEEK_API_KEY <改造前是真 key>
```

**结论：只要密钥进了容器，agent 一定能拿到。** 加密只解决「平台侧怎么放」，
不解决「agent 读不读得到」——后者只有一条路：密钥不进去。

## 二、架构

```
dsh 容器 ──(网关 token: gl_<team>_xxx)──▶ 控制面 /llm/<team>/v1/messages
                                              │
                                              ├─ 校验 token 属于该团队
                                              ├─ 从 team_secrets 解密真 key
                                              └─▶ api.deepseek.com/anthropic （SSE 原样回传）
```

容器里只有两样东西：

| 变量 | 值 | 泄漏后果 |
|---|---|---|
| `DEEPSEEK_BASE_URL` | `http://host.docker.internal:9700/llm/<team>` | 无 |
| `DEEPSEEK_API_KEY` | `gl_<team>_<24 位随机>` | 只能调我们自己的网关，可限速、可吊销、可审计 |

真 key 只在控制面进程内存里，来源是 `team_secrets` 表（AES-256-GCM 密文）。

### 为什么是纯反向代理

`dsh-llm-deepseek` 的 baseURL 根是 **Anthropic Messages 协议**（`https://api.deepseek.com/anthropic`），
只走两个端点：`/v1/messages` 和 `/v1/files`。所以网关不需要任何格式转换，只是
「换掉 `x-api-key` 再转发」，约 200 行。

三个容易写错的点，代码里都显式处理了：

1. **请求体必须流式**：图片走 base64 内联时单请求几十 MB，先读进内存会 OOM；
2. **响应体不能缓冲**：SSE 一攒包就没有逐字输出，必须 `x-accel-buffering: no` + 不设 `content-length`；
3. **hop-by-hop 头必须剥掉**：`connection` / `transfer-encoding` / `content-length` 描述的是「这一跳」。

## 四、验证到什么程度

### 自动化：`make verify-gateway`（38 条）

| 组 | 断言要点 |
|---|---|
| 信封加密 | 往返一致、密文里搜不到明文、AAD 换团队解不开、改一个字节解不开、截断解不开 |
| 主密钥 | 0600、32 字节 |
| 库存放的 | 直接读 `dsh.db` 二进制，搜不到明文 key；列表接口只回名字 |
| 网关 token | 前缀、幂等、反查、伪造为空、轮换后旧的立即失效 |
| 路径解析 | 只放 `/v1/*`，拒绝路径穿越、双斜杠、非法团队名 |
| 转发 | 无 token 401、跨团队 401 且上游一次没被调、无密钥 401 `missing_credential`、**上游收到的是真 key**、400 兜底 |
| SSE | 上游分两段发、中间停 200ms，第一段必须在 180ms 内到达（证明没攒包） |

### 真机（team-c）

```
$ docker inspect ... | ...                      # 容器内
DEEPSEEK_BASE_URL = http://host.docker.internal:9700/llm/team-c
DEEPSEEK_API_KEY  = gl_team-c_meXH… (34 字符)

$ tr "\0" "\n" < /proc/1/environ | grep DEEPSEEK_API_KEY   # 改造前这里是真 key
DEEPSEEK_API_KEY 34 字符                        # 现在只有 token，且不含 sk- 前缀

$ # 容器内带 token 调网关（库里配了一把假 key 做验证）
带 token  → 401 {"message":"Authentication Fails, Your api key: ****7890 is invalid"}
不带 token → 401 {"error":"网关 token 无效或不属于该团队"}
伪造 token → 401
```

注意第一条里上游报出的 `****7890` 正是测试用假 key 的尾号——**这就是「容器手里没有 key、
但上游确实收到了库里的 key」的硬证据**。验证完成后已清除那把假 key。

## 五、真机抓到的一个 bug（值得记）

第一次重建后，容器里的 `DEEPSEEK_API_KEY` 变成了中文日志：

```
DEEPSEEK_API_KEY = db: 回填 5 条分享的 item_id…
```

原因：`llm-token.mjs` 用 `process.stdout` 输出 token，而 `db.mjs` 在 `openDb()` 时
`console.log` 了一行回填日志；`team-up.sh` 的 `$(...)` 把整段 stdout 都当成 token 塞进容器。
运行时的表现是「密钥无效」，跟网关八竿子打不着，很难倒查。

三处一起改了：

1. 两个 token 脚本先接管 `console.log → stderr`，stdout 只留最后一行；
2. `team-up.sh` 加**形状校验**（必须 `gl_<team>_*`），形状不对就当没配；
3. `market-token.mjs` 有同样的坑，一并修了——它只是运气好没赶上日志触发那一次。

## 六、运维要点

| 场景 | 做法 |
|---|---|
| 换团队的模型 key | `POST /secrets {team, deepseekApiKey}`。**不用重启实例**——网关每次请求现查表 |
| token 泄漏 | `POST /llm-token {team}` 轮换，旧 token 立即失效，实例自动重启拿新 token |
| 备份 | `dsh.db` **必须和 `deploy/orchestrator/secret.key` 一起备**。丢了 KEK，所有团队密钥都要重配（密文还在，但解不开） |
| 本地调试直连官方 | 显式设 `DSH_LLM_BASE_URL=https://api.deepseek.com/anthropic` + 真 key，`apply_team_secret` 会跳过网关 |
| 团队没配 key | 请求返回 401 `missing_credential`，dsh 显示「凭据缺失」，不会静默回落给别人 |
